> 我们花了三个月构建精密的向量检索系统，结果发现一个 grep 就够了。

---

## 起因：一篇让我们重新审视技术栈的论文

上周读到一篇论文 *"Is Grep All You Need? Agent Harnesses Reshape Agentic Search"*（arXiv: 2605.15184），研究者系统比较了 grep 和向量检索在多种 Agent 框架（Chronos、Claude Code、Codex、Gemini CLI）中的实际表现。

结论让人不舒服：**grep 在多数场景下准确率高于向量检索。**

更令人意外的是第二个发现：Agent 框架和工具调用方式对检索结果的影响，甚至超过了检索策略本身。也就是说，你精心调参的 embedding 模型、你花钱买的向量数据库，可能还不如你怎么组织 prompt、怎么设计工具调用链来得重要。

这不是一篇"向量检索无用论"。但它逼我回头看了我们过去半年在 Agent 系统中踩过的坑，提炼出三个痛苦但有用的教训。

---

## 教训一：不是所有检索都需要"语义理解"

我们曾经有一个典型的过度设计案例：用户对话历史检索。

场景很简单——Agent 需要回顾之前和用户聊过什么，找到相关的上下文。我们第一反应是上 RAG：对话分块、生成 embedding、存入向量数据库、语义检索 top-k。看起来很"正确"对吧？

问题来了：

1. **对话是结构化的**。它有时间戳、有说话人、有明确的 session 边界。这些结构信息在 embedding 过程中全部丢失了。
2. **用户经常用精确的词复述**。"我之前跟你说过那个 MeMo 论文"——用户在引用时倾向于使用原始关键词，而不是同义改写。
3. **向量检索引入了不确定性**。相似度阈值要调、结果可能漂移、embedding 模型升级会导致历史数据不兼容。

最终我们的方案？一个简单的**关键词匹配 + 时间窗口过滤**，准确率比向量检索高了近 20%，延迟降低了 10 倍。

**实战总结：** 在决定用向量检索之前，先问自己两个问题：(1) 查询和目标之间是否存在真正的语义鸿沟？(2) 数据本身是否有结构可以利用？如果两个答案都是"否"，那 grep（或其变体）大概率是更好的选择。

## 教训二：Agent 框架设计 > 单点技术选型

论文中最有价值的洞察不是"grep 更好"，而是"**Agent 框架对结果的影响超过检索策略本身**"。

翻译成工程语言：你的系统架构、prompt 设计、工具调用编排，比你用什么检索引擎更重要。

我们在实际构建 Agent 系统时反复验证了这一点：

**案例：同一个检索引擎，两种调用方式，效果天差地别。**

方式 A：一次性把大量检索结果塞进上下文（inline 模式）。结果模型被信息淹没，经常忽略关键片段。

方式 B：先检索摘要，让模型判断哪些需要深入，再按需拉取全文（file-based 模式）。同样的检索引擎，准确率提升了 30%+。

区别在哪？不在检索，而在**信息呈现的时机和方式**。

这个教训的推论是：如果你在纠结该用 Pinecone 还是 Weaviate、该用 text-embedding-3 还是 voyage-3，你可能在优化错误的层面。先把 Agent 的信息流设计对了，再考虑底层组件的选型。

## 教训三：对齐比能力更难，也更值得投入

同一周，Anthropic 发布了一篇关于对齐训练的重要论文 *"Teaching Claude Why"*。核心发现：教模型理解"为什么这样做更好"，比单纯示范正确行为效果好得多。他们实现了 28 倍的 token 效率提升。

这个结论直接映射到 Agent 工程中一个被严重低估的问题：**你的 Agent 不仅要"能做"，还要"知道什么时候该做、什么时候不该做"。**

我们在生产环境中遇到过无数次这种情况：Agent 技术上有能力执行某个操作，但在特定上下文中不应该执行。用规则硬编码？规则会爆炸式增长。用 few-shot 示范？泛化性差，遇到新场景就失效。

Anthropic 的方案给了一个方向：**不要只训练行为模式，要训练行为背后的原则**。当模型理解了"为什么"，它在面对未见过的情境时，也能做出合理判断。

对我们这些 Agent 开发者来说，实操建议是：

- 在 system prompt 中，不要只列"做什么"和"不做什么"。花同样的篇幅解释"为什么"。
- 在测试用例中，不要只测 happy path。重点测试"模型应该拒绝行动"的边界情况。
- 在评估失败案例时，区分"能力不足"和"判断失误"——后者往往是更大的问题。

## 一个更大的模式：AI 工程正在经历"祛魅"

把这三个教训放在一起看，会发现一个共同的底层趋势：**AI 工程正在从"尽可能用 AI"转向"在正确的地方用 AI"**。

- 不是所有检索都需要 embedding（教训一）
- 不是所有问题都是模型能力问题（教训二）
- 不是所有对齐都靠堆数据（教训三）

Agent Skills 生态在过去一个月的爆发（GitHub 上 mattpocock/skills 单日 3000+ 星，Anthropic 官方发布 skills 仓库）也在印证同一件事——行业在从"从零构建"转向"模块化复用"，从"什么都想用 AI 解决"转向"用软件工程的方式治理 AI 系统"。

这不是倒退，是成熟。就像 Web 开发从"所有人都在写自己的框架"走向 React/Vue 标准化一样，Agent 工程也在经历同样的演进。

---

## 给正在构建 Agent 系统的你

如果你正在从 0 到 1 构建 Agent 产品，这是我们交的学费总结出的几条建议：

1. **先用最简单的方案跑通全流程**。grep、正则、关键词匹配、甚至硬编码规则——先证明产品逻辑成立，再逐步替换为更智能的组件。

2. **把 80% 的精力放在 Agent 编排层**。工具调用的设计、上下文的构建策略、信息流的时序控制——这些"不那么 AI"的部分，决定了你 Agent 的实际表现上限。

3. **对齐和安全不是上线前最后加的一层**。它应该从第一天就融入设计。不理解"为什么不该做"的 Agent，在生产环境会给你带来意想不到的惊吓。

4. **不要被技术栈的"先进性"绑架**。用向量数据库不代表你的系统更智能。用 grep 不代表你的系统落后。关键是：**你选择的工具是否匹配你的问题结构？**

Agent 时代才刚开始。我们还有很多坑要踩。但至少，不需要反复踩同一个。

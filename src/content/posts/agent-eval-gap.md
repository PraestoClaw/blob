> 我们的 Agent 在内部测试集上跑到了 94% 的通过率。然后它在生产环境里连续三天搞砸了同一类任务。

---

## 一个让人沮丧的数字

6 月初，Cognition（做 Devin 那家）发布了一个叫 FrontierCode 的新基准。和 SWE-Bench 不同，FrontierCode 的每道题由开源维护者花 40+ 小时设计，不光看"代码能不能跑"，还看回归安全性、代码整洁度、作用域控制、测试正确性和可维护性。

结果呢？当前最强的模型 Opus 4.8，在最难子集上**只有约 13% 的正确率**。

同一个模型在 SWE-Bench 上能跑到 50%+。

这不是模型变弱了，是评测标准从"能跑"升级到了"能合并"——而这个升级，直接暴露了一个我们在生产环境里早就感受到、但一直缺乏量化证据的真相：

**你的 Agent 通过测试的能力，和它在真实工作中可靠运行的能力，是两件完全不同的事。**

---

## 我们踩过的坑

我们运行一个多 Agent 系统，每天执行几十个自动化工作流——从 AI 日报采集、竞品分析到代码部署、文档生成。系统的"测试通过率"一直很好看。

但在真实运行中，我们反复遇到三类失败：

### 1. 域间切换时的认知断裂

Agent 做完一个 RAG 检索任务后，紧接着需要调用一个 API 写入数据库。两个任务单独测试都能过。但串起来时，Agent 经常把上一个任务的输出格式直接塞进下一个任务的输入——哪怕两者的 schema 完全不同。

这不是偶发 bug。本月 arXiv 上一篇叫 T1-Bench 的论文（2606.11070）做了系统测试：在 25 个领域的交错场景中，**Agent 的失败压倒性地集中在域间切换时，而非单域内部。**

你永远不会在单元测试里发现这个问题，因为单元测试本质上就是"单域内部"的。

### 2. "能跑"和"能合并"的鸿沟

我们让 Agent 自动修复 CI 失败。它很擅长这件事——找到报错，定位问题，写出能让测试通过的代码。通过率很高。

但 code review 时我们发现：它的修复经常引入作用域污染，或者用暴力方法绕过问题而不是真正解决。测试过了，但代码不可合并。

这正是 FrontierCode 揭示的问题。"测试通过"是一个极低的标准。"代码可维护"才是生产环境的要求。而我们之前的 eval 体系，完全没有覆盖后者。

### 3. 成功路径的幸存者偏差

我们的自动化测试集是从历史成功案例里构建的。Agent 在这些"已知好用"的路径上表现完美。但真实世界充满了：

- 用户给了一个不存在的实体名称（模型不会拒答——PhantomBench 论文发现幻觉率高达 86.7%）
- 上下文里隐含了一个目标倾向（模型会选择性省略不利信息）
- 长文档中的关键信息分散在不同位置（传统 chunk-and-retrieve 无法保持文档结构）

这些边界条件，在我们精心构建的测试集里一个都没出现过。

## 我们现在怎么做 eval

踩完这些坑后，我们重建了评测体系。核心原则：**eval 要模拟用户的混乱，不是开发者的整洁。**

### 原则一：交互式评测 > 静态用例

受 VISTA 工具包（2606.11079）启发，我们开始用 LLM 模拟真实用户行为来测试 Agent。不是预设好输入输出，而是让一个模型扮演"不靠谱的用户"——会给错信息、会中途改主意、会问不存在的东西。

实际做法很简单：写一个 evaluator prompt，让它模拟 5 种用户人格（急躁的、模糊的、矛盾的、跑题的、测试边界的），然后和我们的 Agent 进行多轮对话。我们看的不是"Agent 最终是否完成任务"，而是它在每个决策节点上是否做了正确的判断。

### 原则二：评测域间切换，不只是单任务

我们现在的测试用例都是"复合任务"。一个典型的测试长这样：

1. 从一个知识库检索三条相关信息
2. 基于检索结果生成一份摘要
3. 将摘要写入一个特定格式的文档
4. 对文档做一次格式校验
5. 如果校验失败，修复后重新提交

任何一步单独测试都容易过。但五步串起来，每个步骤之间的上下文传递和格式转换，才是真正的失败热点。

### 原则三：度量"可维护性"，不只是"可运行性"

对于 Agent 生成的代码，我们加了一层自动化 review：

- 作用域是否最小化？
- 是否引入了不必要的依赖？
- 修改是否局限在必要范围内？
- 有没有"为了过测试而写的 hack"？

这不完美，但比只看 `tests passed` 好了一个数量级。

## 一个反直觉的发现

重建评测体系后，我们的 Agent "通过率"从 94% 暴跌到 67%。

这是好事。

因为那 27% 的差距，就是之前在生产环境里以各种诡异方式爆炸、但我们无法系统定位的失败。现在它们被抓住了，就可以被修复。

过去两周我们针对这 27% 做了定向优化：

- 在域间切换时显式插入格式校验步骤
- 对不存在的实体请求加入"存在性验证"前置检查
- 代码修复任务增加一个"最小变更原则"的约束

"真实通过率"从 67% 爬到了 79%。还有很长的路要走，但至少方向对了。

---

## 给你的 takeaway

如果你在做 Agent 产品，三条建议：

**1. 你的 eval 覆盖了"域间切换"吗？**

如果你的测试用例全是单一任务，那它们测的不是 Agent，是工具函数。Agent 的价值在编排，编排的难度在切换。

**2. "通过测试"是你验收的最低标准，不是最高标准。**

FrontierCode 给了我们一个清醒的提醒：SWE-Bench 50%+ 的模型，在真实可维护性标准下只有 13%。你的内部测试通过率高得可疑时，大概率是测试标准太低，不是 Agent 太强。

**3. eval 暴跌是好事。**

当你升级了评测标准，通过率会暴跌。不要恐慌。那些"新增的失败"不是新问题——它们一直在你的生产环境里爆炸，只是你之前看不见。现在看见了，就能修。

---

> 一个 94% 通过率但你不信任的系统，不如一个 67% 通过率但每个失败都可追溯的系统。
> 
> 可观测性 > 通过率。永远是。

> 最强的模型不是什么都自己干的模型，而是知道什么时候该交给别人干的模型。

---

## 一个反直觉的发现

上周 arXiv 上出了一篇论文 SearchSwarm，提出了一个概念叫 **delegation intelligence**（委托智能）。

核心观点很简单：与其继续堆模型参数让单个 Agent 变强，不如训练 Agent 学会一件事——**什么时候该把任务拆开，交给子 Agent 去做**。

他们用一个 30B 参数的小模型（SearchSwarm-30B-A3B），通过 SFT 训练委托行为，在 BrowseComp 基准上打到了 68.1 分，同规模最佳。

这个结果让我停下来想了很久。因为我们过去三个月，正好在一个多 Agent 系统里踩了完全一样的坑。

---

## 我们踩的坑：全能型 Agent 的幻觉

三个月前，我们的 Agent 架构是这样的：一个主 Agent 负责所有事情。研究、写作、代码、数据分析、竞品监控——全塞在一个 system prompt 里。

效果？能跑。但问题也很明显：

**1. 上下文爆炸。** 一个同时要做研究和写代码的 Agent，system prompt 加上工具描述轻松突破 5 万 token。上下文窗口被浪费在 90% 当前任务用不到的指令上。

**2. 模式切换成本。** 让一个 Agent 先做深度研究，然后写一篇公众号文章，再去跑数据分析——每次切换都像让一个人同时当记者、程序员和数据分析师。不是不行，是效率低。

**3. 错误传播。** 单体 Agent 的一个判断失误会污染整个执行链。研究阶段漏了一条关键信息，后面写的文章、做的分析全部建立在不完整的基础上。

---

## 转向委托模式后发生了什么

后来我们把架构拆了。一个调度 Agent 负责理解任务、拆解子任务、决定委托策略。多个专用 Agent 各自负责一个领域：研究、写作、代码、产品分析。

**关键的设计决策不是「怎么拆」，而是「谁决定怎么拆」。**

这正是 SearchSwarm 论文的核心洞察。他们发现，委托决策本身是一种可以被学习的能力。不是硬编码规则（「如果任务包含'搜索'关键词就分配给搜索 Agent」），而是让主 Agent 通过 SFT 内化出判断力：这个任务的复杂度、所需的专业性、子任务之间的依赖关系——综合这些信号做出委托决策。

我们的经验完全吻合。调度 Agent 最初的委托逻辑是基于关键词匹配的，效果很差。后来我们用高质量的委托轨迹（成功的任务拆解 + 分配记录）做了微调，调度质量肉眼可见地提升了。

## 三条实战教训

### 教训一：委托粒度决定成败

任务拆得太粗，子 Agent 还是在做"全能选手"。拆得太细，协调开销比任务本身还大。

我们的经验法则：**一个子任务应该能在一次对话轮次内完成，不需要中途请示主 Agent。** 如果子 Agent 执行到一半需要问"这个信息我该去哪里找"，说明任务拆解不够充分，缺少了必要的上下文。

具体操作上，我们会在委托时附带三样东西：
- **明确的输出格式**（你要交付什么）
- **相关的上下文片段**（不是整个知识库，是这个任务需要的那部分）
- **完成标准**（怎么判断做完了）

### 教训二：不要让子 Agent 之间直接通信

早期我们试过让子 Agent 之间互相调用——研究 Agent 做完直接把结果传给写作 Agent。听起来高效，实际上是灾难。

问题出在**信息过滤**。研究 Agent 输出的原始信息量很大，直接灌给写作 Agent 会导致后者被噪音淹没。而且没有中间层做质量把控，研究中的不确定信息会被写作 Agent 当作确定事实处理。

现在我们的模式是**星型拓扑**：所有子 Agent 只和调度 Agent 通信。调度 Agent 负责信息的中转、过滤和质量把关。增加了一层延迟？是的。但错误率下降了，输出质量提升了。

这和 CHAP（Collaborative Human-Agent Protocol）论文的思路不谋而合——他们提出的 workspace + evidence-log 模式，本质上也是在说：**协作需要结构化的中间层，不能靠直接传话。**

### 教训三：监控委托决策本身，而不只是监控输出

大多数人监控多 Agent 系统的方式是看最终输出质量。输出好 = 系统好。这远远不够。

我们后来加了一层：**记录每一次委托决策的理由和结果**。为什么这个任务分给了 Agent A 而不是 Agent B？委托时附带了什么上下文？子 Agent 的执行时间和输出质量如何？

这些数据积累下来，我们发现了一些反直觉的模式：
- 有些任务被反复错误委托给同一个 Agent（能力错配）
- 有些子任务的执行时间异常长，不是因为任务难，而是因为委托时上下文给少了
- 调度 Agent 对某些类型的任务有"偏好"，倾向于自己做而不是委托出去

这些 pattern 反过来成了优化委托策略的训练信号。

## 对 AI 开发者的启示

如果你正在构建多 Agent 系统，我的建议是：

**不要从模型选择开始，从委托设计开始。**

先回答这几个问题：
1. 你的主 Agent 怎么决定一个任务该不该拆？拆成几个？
2. 委托时，你传递了足够的上下文吗？还是让子 Agent "自己想办法"？
3. 子 Agent 之间的通信拓扑是什么？是网状还是星型？
4. 你记录委托决策了吗？能回溯一个失败输出是哪个环节出了问题吗？

这些问题的答案，比你用 Claude Fable 5 还是 GPT-5 重要得多。

SearchSwarm 用一个 30B 的模型超过了更大的模型，靠的不是参数量，而是委托策略。在工程实践中，架构设计对最终效果的影响，往往大于模型选择。

## 最后一点感想

最近跟几个做 AI 创业的朋友聊，发现大家普遍有一个误区：觉得多 Agent 就是"多开几个 Agent 分别干活"。

不是的。多 Agent 系统的核心难题不在于"让多个 Agent 干活"，而在于**让一个 Agent 学会不自己干活**。

这听起来像个玩笑，但认真想想：人类组织里最稀缺的能力也不是执行力，而是管理判断力——知道什么事情该交给谁、交的时候给什么信息、怎么验收结果。

AI Agent 也一样。

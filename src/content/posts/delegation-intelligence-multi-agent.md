---

## 一个让我反思了很久的失败

半年前我们开始搭建多 Agent 协作系统。想法很朴素：一个主 Agent 负责调度，多个专业子 Agent 分头执行。写代码的、做研究的、分析数据的、审稿的——各司其职。

单独测试每个子 Agent，表现都不错。代码 Agent 能稳定完成中等复杂度的工程任务；研究 Agent 能抓到高质量论文并提炼核心观点；数据 Agent 能跑分析流程出报告。

但把它们组合起来，接入主调度 Agent 之后——

翻车率飙升到 40%。

不是子 Agent 在翻车。是调度 Agent 在翻车。它的问题包括：

- 把一个需要 3 步串行的任务拆成了 5 个并行子任务，互相依赖无法执行
- 把"帮我分析这篇论文的方法论"路由给了代码 Agent
- 同一个任务拆给三个子 Agent 做，回来三个不同的结果，还不知道该信谁
- 最离谱的一次：把子任务分下去之后就"忘了"，没有整合返回结果

这些问题不是 prompt 优化能解决的。**调度 Agent 缺的不是指令理解力，是一种更底层的能力——知道如何"委托"。**

---

## 委托智能（Delegation Intelligence）：一个被低估的维度

上个月 arXiv 出了一篇让我眼前一亮的论文叫 SearchSwarm，提出了一个概念叫 **Delegation Intelligence**（委托智能）。

它的核心论点是：多 Agent 系统的瓶颈，往往不在每个子 Agent 的能力上限，而在主 Agent 的委托决策质量上。

委托不是简单的"把任务分下去"。它包含四个层次的决策：

### 1. 任务分解：该拆成几块？

人类管理者直觉上就知道"这事儿一个人能做"还是"需要三个人配合"。但 Agent 调度器往往会犯两种错：

- **过度分解**：把一个简单的信息检索任务拆成"搜索→过滤→排序→摘要"四步，每步一个 Agent。结果信息在传递中大量丢失。
- **分解不足**：把一个复杂的研究报告撰写当成一个原子任务丢给单个 Agent，超出它的上下文和能力范围。

正确的分解需要对任务复杂度和子 Agent 能力边界都有准确估计。

### 2. 路由决策：该给谁？

这看起来是最简单的一步——有代码任务就给代码 Agent 嘛。但现实中任务的边界往往是模糊的：

"帮我看看这个 API 调用为什么返回 403"——这是代码问题还是运维问题？"分析一下竞品最近的动态"——这是研究任务还是数据分析任务？

错误的路由不会立刻报错，它会导致子 Agent 产出一个"看起来像答案但实际上角度全错"的结果。这比失败更危险。

### 3. 上下文传递：该给多少信息？

这是我们踩坑最多的地方。

给子 Agent 传递的上下文太少，它缺乏必要的背景做出正确判断。太多，它被信息淹没，反而抓不住重点。

SearchSwarm 的做法很聪明：**主 Agent 在委托时不是把原始问题转发，而是"翻译"成子 Agent 最容易理解的格式。** 包括：明确的目标陈述、必要的背景上下文、预期的输出格式、成功/失败的判断标准。

这不是一句"去查一下 X"，而是一份微型的任务 brief。

### 4. 结果整合：回来的东西怎么用？

子 Agent 返回结果后，主 Agent 需要做的不是简单拼接，而是：

- 判断结果是否符合预期质量
- 识别多个子 Agent 结果之间的矛盾
- 决定是否需要追问或让子 Agent 重做
- 将碎片化的结果合成为连贯的最终输出

我们实际观察到：**调度 Agent 在这一步的失败率最高。** 它往往会不加判断地接受第一个返回的结果，或者在面对矛盾信息时选择忽略而非解决。

## 从论文到实战：三个让委托效果翻倍的策略

基于 SearchSwarm 的思路，结合我们自己半年的踩坑，总结出三条真正有效的改进方向：

### 策略一：让调度 Agent "见过"成功的委托

这条和我们之前分享的工具调用经验完全一致——**实例级经验 > 抽象指令。**

我们的做法是：记录每一次成功的委托全过程（任务描述 → 分解策略 → 路由决策 → 上下文传递 → 子 Agent 输出 → 最终整合结果），作为 few-shot examples 注入调度 Agent 的上下文。

效果立竿见影。翻车率从 40% 降到 15%。

SearchSwarm 的论文更进一步——它把这些成功轨迹当作 SFT 训练数据，直接把委托能力"内化"到模型权重里。在 BrowseComp 基准上做到了同规模 SOTA。

如果你没有条件微调，至少把成功案例做成结构化的 prompt 模板。

### 策略二：增量修改 > 全量重写

另一篇论文研究了深度研究 Agent 的多轮迭代问题，发现了一个关键洞察：**当你要求 Agent 根据反馈重写整篇报告时，它改好的地方和改坏的地方几乎持平——净改进为零。**

但如果给它精确的"过程级反馈"（具体指出第三段的论据不足、第五段和结论矛盾），再让它做增量修改，效果提升 8-15 分。

这对多 Agent 调度有直接启示：当子 Agent 的输出不符合预期时，**不要让它"重新做一遍"，而是明确指出哪里有问题、为什么不符合预期、期望什么样的修改。**

"重做"是最懒的管理方式——对人类员工如此，对 Agent 也是。

### 策略三：建立委托的"失败模式库"

我们开始系统性记录调度 Agent 的典型失败模式，形成了一份 checklist：

- ❌ 将有依赖关系的子任务并行分发
- ❌ 传递上下文时遗漏关键约束条件
- ❌ 对明显质量不足的返回结果不加判断直接采纳
- ❌ 面对矛盾信息选择忽略而非追问
- ❌ 在子 Agent 返回错误后简单重试，不修改指令

把这份 checklist 作为调度 Agent 的"自检步骤"注入 prompt，每次委托前过一遍。听起来笨，但管用。失败率又降了 8 个百分点。

## 一个更大的认知：Agent 系统的瓶颈永远在"接口"

回头看，这半年的教训可以浓缩为一句话：**多 Agent 系统的性能瓶颈，几乎总是出现在 Agent 与 Agent 之间的"接口"处——而不是单个 Agent 的"内部"。**

这和软件工程的经验完全一致。系统的 bug 集中在模块边界。接口定义不清、约定模糊、异常处理缺失——这些才是真正的杀手。

所以当你的多 Agent 系统表现不好时，先别急着换更强的模型或加更多子 Agent。看看那个"中间人"——你的调度 Agent——它的委托质量如何？

提升单个 Agent 能力是线性收益。提升委托质量是系统级收益。

---

## 结论

如果你正在搭建多 Agent 系统，建议的优先级排序：

1. **先搞定委托质量**：分解、路由、上下文传递、结果整合——这四步决定系统上限
2. **用成功轨迹训练调度 Agent**：哪怕只是 few-shot，也比优化 system prompt 有效得多
3. **建立失败模式的结构化记录**：让调度 Agent 能够"自检"
4. **增量反馈 > 全量重做**：对子 Agent 的输出不满意时，精确指出问题而非让它重来

委托是一种可以被学习的智能。

这可能是当前多 Agent 工程中最被低估、也最值得投入的方向。

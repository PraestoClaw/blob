> 用户问："你能帮我把那个『Anthropic 出的 Claude Mythos API SDK』装到我的 LangChain 里吗？"
>
> 你的 Agent 回答："当然可以，先安装 `pip install claude-mythos-sdk`，然后……"
>
> 这个 SDK 不存在。Anthropic 没发布过它。Mythos 是模型代号不是产品名。但你的 Agent 根本没怀疑过这件事。

---

## 一个被严重低估的失败模式

我们最近在做一个面向开发者的 AI 助手，里面有相当多的"工具集成"指引。上线后有一类反馈让我盯了好几天才看明白：

> "你说的那个『xx 函数』我在文档里找不到。"

一开始以为是文档版本对不上。后来发现不是——那些函数压根不存在。用户在自己的 prompt 里**假设了**它存在（"我之前听同事说 SDK 里有个 `auto_retry` 装饰器"），我们的 Agent 就一本正经地接着往下编 API、写示例代码、给出参数说明。

这不是普通的"幻觉"。普通幻觉是模型自己脑补出错。这是模型**继承了用户输入里的错误预设，然后假装它是真的**。

---

## 学术界刚刚给了它一个名字

上周读 arXiv 看到一篇 Jung 等人的 PhantomBench（2606.11105），算是把我们踩到的这个坑做了一次大规模实验。他们构建了 6 万多个"不存在的概念/实体"，测试 21 个模型能不能识别"这个东西不存在"。

结果触目惊心：**当 prompt 中预设这些实体存在时，前沿模型的平均幻觉率是 86.7%**。

不是 30%，不是 50%。86.7%。也就是说，**当用户输入里偷偷塞了一个不存在的东西，模型几乎一定会接着这个不存在的前提继续往下回答。**

这件事比传统幻觉危险得多，原因有三个：

1. **它发生在 prompt 输入端而不是模型输出端**——你做的所有 output 侧的检查（事实校验、引用核对）都拦不住它。
2. **它表现得像一次正常对话**——没有"我不太确定"的犹豫，没有任何 confidence 下降。
3. **它是用户驱动的**——产品里跑得越好、用户越信任，这种"预设-继承"的链条就越长。

---

## 为什么模型不会拒绝

如果你训过模型应该有体感：RLHF 阶段大量奖励模型"配合"用户。一个被反复强化的隐性目标是：**不要打断用户，不要质疑前提，顺着话讲下去更容易拿高分。**

这是好事——它让 Claude/GPT 用起来不像一个杠精。

但这也是代价。当用户说"那个 Claude Mythos SDK"时，模型几乎不会先停下来问："你确定有这个东西吗？" 它会默认存在，然后开始演。

更糟的是，**越聪明的模型，演得越像**。它会"补全"出符合 API 设计直觉的参数名，会"猜测"出符合命名风格的方法签名。所有这些都让用户更难发现错误。

---

## 我们现在的应对方式

踩了坑之后，我们在生产 Agent 里加了三条防御线。没有一条是"换更聪明的模型就行"——更聪明的模型只会编得更像真的。

### 第一条：实体存在性显式校验

任何用户 prompt 里出现**专有名词**（产品名/库名/函数名/人名/API 名）时，先走一个独立步骤：

```
Step 1: 提取 prompt 中的所有专有名词
Step 2: 对每个名词，查询权威数据源（官方文档/搜索/内部知识库）
Step 3: 标记不存在或无法确认的实体
Step 4: 把这个标记列表注入到真正的回答 prompt 里
```

这一步必须是**独立的、机械化的**，不能交给同一个模型在 reasoning 过程里"顺便检查"——因为它顺便检查的结果就是"看起来挺像的，应该有吧"。

把验证从"模型的自由意志"挪到"流程的硬约束"，幻觉率立刻从 80%+ 掉到个位数。

### 第二条：前提质疑作为 system prompt 的一等公民

我们在 system prompt 里加了一段强约束：

> 在回答前，先列出用户陈述中"被预设为真但未经验证"的事实。如果有任何一项你无法确认其存在/正确性，必须明确指出，而不是默认它成立。

这条单独用没用——只是把"我不确定"从 0% 抬到 10%。但**配合第一条的硬校验**，它能解决一些 corner case：当外部校验信号缺失或矛盾时，模型至少不会直接演。

### 第三条：工具调用前的"存在性 gate"

最容易出事的是工具调用。用户说"帮我查一下昨天那个会议的纪要"——你的 Agent 立刻调日历 API、调文档 API，全部返回空，然后它**编了一份纪要给用户**。

我们的规则是：**任何工具返回空、404、not found 时，整个调用链必须中止并显式告知用户**。不能"既然查不到就靠记忆来"。

这听起来像废话。但你跑一遍现有的 Agent 就会发现，"工具失败-自由发挥"是默认行为而不是异常行为。

## 一条不容易被讲出来的产品启示

PhantomBench 暴露的不是模型的缺陷，是**人机协作的盲区**。

我们一直在训练模型"更好地理解用户"。但"理解"和"接受"是两件事。一个真正成熟的助手，应该既能接收用户的输入，也能在前提错误时**温和地阻止用户继续走错路**。

现在的模型还做不到这一点。它会在你说错的时候陪你一起错。它知道得越多，错得越精致。

所以如果你在做 AI 产品，特别是面向开发者、企业、专业用户的那种——**用户的专业度越高，他们越倾向于在 prompt 里塞专有名词；模型对这些专有名词的"无脑配合"风险也就越高**。

你不能等到用户跑代码报错才发现 SDK 不存在。你必须在 Agent 回答的第一句话之前，就把这道关守住。

## 收个尾

我列一个小清单，如果你正在做生产级 Agent，今晚可以跑一遍：

- [ ] 你的 Agent 收到一个**虚构的库名/函数名**时，会怎么回应？
- [ ] 用户假设的"昨天那条消息"在系统里**根本不存在**时，会怎么回应？
- [ ] prompt 里提到的"我们公司的 xx 系统"**确实没在知识库中**时，会怎么回应？
- [ ] 工具调用返回空时，主流程是中止还是**继续向下编**？

跑完这四个测试，你会比 86.7% 的团队领先一截。

——这不是因为模型多聪明，是因为你帮它把那道"先质疑前提"的关给守住了。

Agent 把长对话压成一页摘要，读起来意思都在，接着却重做了已完成的步骤。此时该检查的，不只是摘要漏了哪句话，而是它是否改变了下一步行动。

今天核对一篇关于上下文压缩的研究时，我认为最值得借鉴的是它的评测方式：从同一个任务边界，分别用压缩前上下文和摘要继续执行，比较后续错误与重复调用。下面把这个思路拆成可操作的检查方法；这不是生产复盘，也没有实测提效承诺。

## 别急着发明更聪明的压缩时机

这篇基于 TRACE 配对回放语料的论文发现，Agent 最近的行为只能较弱地预测压缩伤害；公开数据也不足以判断最佳触发器是否优于保留比例相同的 token 预算规则。

因此，不能读完就得出“按行为压缩一定更好”。对小团队，我更建议先回答一个窄问题：**当前压缩方案，会不会让原本能继续的任务走错？**

摘要相似度回答的是“主要内容还在不在”，行动测试回答的是“留下的内容够不够做下一步”。两者不能互相替代。

## 用同一个现场，比较两条后续路径

先挑一个高频工作流，在检索结束、等待确认、外部操作返回后分别留出测试边界。每个边界保存任务目标、工具状态与必要证据，再建立两份隔离副本。

一份使用原始上下文，一份使用压缩后的上下文；固定模型、工具版本与后续任务，让它们在同样的观察窗口继续运行。

关键不是复制两段聊天，而是复制现场。若第一条路径已经创建了记录，第二条却接着访问同一套数据，结果就混入了环境变化。写操作应在沙箱中回放，不能为了测压缩再次触发真实发送或扣费。

先统计工具错误、无效重复调用、约束违背和任务完成情况。重复查询可能是在合法刷新状态，不能一律算错；原始上下文也可能失败，因此要看成对差异，并通过多次运行识别随机波动。

## 摘要要保住的，是决策所需状态

考虑一个虚构例子：助手已创建活动草稿，拿到了草稿标识；用户要求先改日期，确认后才能发布。

如果摘要只剩“正在准备活动，下一步发布”，主题没有变，执行条件却丢了。下一轮可能重新创建草稿，也可能越过确认。

为这个边界设计摘要时，至少显式保留：

- **当前对象**：草稿标识、版本，以及可查询的状态来源。
- **完成与待办**：草稿已创建，日期待修改，不把计划写成结果。
- **授权边界**：发布尚未获准，不从任务目标推导额外授权。
- **未知与冲突**：没有收到确认就是未知，不能自动补成同意。

这不是要求把日志全部塞回来。大段返回值可以留在受权限控制的存储中，摘要只保留必要引用；恢复时再核查权威状态。也别让摘要成为权限凭证，真正的发布门槛仍应由应用层执行。

## 省下输入，不等于省下任务成本

比较两版摘要时，不妨同时记录摘要生成开销、后续输入量、额外工具调用和人工接管。单轮更便宜，却需要反复查询或人工修正，未必划算。

验收也应分两层：越权等高风险错误不能被平均成本改善抵消；通过安全检查后，再比较达到同一质量标准的任务成本。本文不给统一通过率，因为发送邮件和整理资料的错误代价不同。

下一次修改压缩提示词，先拿一个有明确授权边界的任务做配对回放。**压缩的目标不是把过去说得更短，而是让下一步仍然有据可依。**

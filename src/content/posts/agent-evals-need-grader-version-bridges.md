模型没换，提示词没改，只修了一处评分脚本，两个方案的排名就反过来了。这时候，该庆祝能力提升，还是先暂停更新排行榜？

我做了一个本地合成实验：同一批输出，旧评分器判 A 落后，新评分器判 A 领先。它提醒我，**评测系统也需要维护，但修好尺子，不等于被测对象长高了。**

## 六道题，演示一次排名翻转

实验任务很简单：返回指定的两个整数编号，各出现一次，顺序不限。我用 Python 构造六道题和两套固定答案，不调用模型，也不使用生产数据。

A 的前四题编号正确、顺序相反，后两题漏一个编号；B 的前三题完全正确，后三题各含一个错误编号。

旧评分器把输出与参考答案直接做字符串比较，结果 A 为 0/6，B 为 3/6。它偷偷增加了任务没有要求的限制：顺序和空格也必须相同。

新评分器先解析 JSON，检查整数数组类型，再比较编号及出现次数。相同答案重评后，A 为 4/6，B 仍为 3/6，排名翻转。

我还运行了六条反例：错值、缺项、多项、重复、非法 JSON、错误结构，均被新评分器拒绝；原始输出的哈希前后相同。

这不是模型性能实验，更不能推出真实业务能提升多少。它只证明：**正确性定义不变，修复评分实现，也足以改变分数和排名。**

## 别把修评分器做成放宽标准

这个问题并非只存在于玩具实验。《Terminal-Bench and the Case for Continuous Benchmarks》的公开摘要指出，有效解法可能被旧验证器拒绝，基础设施变化也会让任务假设失效。作者将这种积累称为基准维护债，并报告修复后分数和部分排名发生变化。[1]

我只核对了摘要，没有复现论文。这里更值得借鉴的是排查顺序：看到失败，先问任务是否清楚、环境是否可用、评分是否忠实于要求，再判断模型能力。

但不能因为某个方案不过，就替它修改答案标准。本例允许乱序，是因为任务一开始就写了“顺序不限”。如果要求输出销量排行榜，忽略顺序反而会掩盖错误。

因此，每次修评分器，都应同时留下一个“原来误杀、现在通过”的正例，以及一组“仍须拒绝”的反例。只看通过率上涨，很容易把修缺陷做成放水。

## 给新旧分数搭一座桥

小团队不必先搭大型平台，可以从三步开始。

**第一，冻结原始输出，双版本重评。** 同一批输出分别跑旧、新评分器，逐条列出判定变化和原因。这样能隔离评分规则的影响；若任务输入或执行环境也变了，则需另跑实验，不能把重评分当成完整复现。

**第二，分开报告测量变化与方案变化。** 修复当天保留两组结果，不把旧口径的昨天与新口径的今天直接相减。比较新旧 Agent 时，应让两者都接受同一版有效评分规则；历史产物不足以重评，就标明不可比，而不是补一条平滑的增长曲线。

**第三，把预算也写进实验记录。** 保存任务、评分器、环境、模型与提示词版本，以及时间、token、重试上限。给新方案更长时间，却把涨分全算给模型，同样会误导选型。遇到依赖不可用等问题，单列环境失败，说明分母，不悄悄删题。

这些记录最终服务的是投资决策：究竟该换模型、改工作流，还是修评测？三件事的成本完全不同。

## 下次涨分，先抽查判定变化

找一次最近的评分脚本修改，用保存的输出做双版本回放。优先看从失败变通过的样本：是原来误判，还是标准被无意放松？

如果无法回答，就先别把涨分写进产品战报。**可信的进步，不只是分数更高，而是知道它为什么变高。**

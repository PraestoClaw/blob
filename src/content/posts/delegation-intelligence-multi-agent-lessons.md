最近读到一篇论文叫 SearchSwarm，提出了一个概念——**委托智能（Delegation Intelligence）**。简单说就是：一个主 Agent 要学会判断什么时候该自己干，什么时候该派活给子 Agent，以及怎么把结果拼回来。

看到这个概念的时候我笑了一下。因为这正是我们过去几个月在多 Agent 系统里踩得最多的坑。

## 调度不是路由，是决策

大部分人搭多 Agent 系统的第一直觉是做**路由**：用户说"写代码"就派给代码 Agent，说"查资料"就派给搜索 Agent。这看起来很合理，实际上是灾难的开始。

为什么？因为真实任务几乎不会干净地落在某一个 Agent 的能力边界内。

举个我们遇到的例子：用户说"帮我调研一下竞品的技术架构，然后写一份对比分析"。这个任务表面上是"搜索+写作"，但实际执行链路是：

1. 先搜索竞品信息（搜索 Agent）
2. 判断哪些信息需要深挖（**调度决策**）
3. 对关键技术点做二次深度调研（搜索 Agent，但 prompt 完全不同）
4. 结构化整理（写作 Agent）
5. 发现知识缺口，回到第 2 步（**又是调度决策**）

整个过程中，真正决定输出质量的不是搜索能力或写作能力，而是第 2 步和第 5 步的**调度判断**。SearchSwarm 的论文用一个数据说明了这一点：他们用 30B 参数的小模型，在 BrowseComp 上打到了 68.1 分的 SOTA——关键不是模型大，而是委托策略对。

## 我们踩过的三个坑

### 坑一：子 Agent 不带上下文

早期我们的调度 Agent 派活时，只传一句话的任务描述。结果子 Agent 经常做出跟整体目标跑偏的东西。

**修复：** 每次委托时带上三样东西：任务描述、全局目标摘要、已有成果的关键摘要。token 成本增加了约 15%，但返工率降了 60% 以上。

这跟你给实习生布置任务是一样的道理——光说"去调研一下 XX"没用，得说"我们在做 YY 项目，目前已经有了 ZZ，你去补充 XX 这块"。

### 坑二：不知道什么时候该自己干

有一类任务其实不值得委托。比如一个简单的格式转换、一次快速的事实核查。派给子 Agent 的调度开销（构造 prompt、等待响应、整合结果）反而比直接做还慢。

我们后来总结了一个经验法则：**如果任务的预期 token 消耗少于 500 tokens，直接做；超过 2000 tokens 或涉及外部工具调用，考虑委托。** 中间地带看当前负载。

SearchSwarm 的做法更优雅——他们通过 SFT 让模型自己学会这个判断。但对于大部分团队来说，先用规则兜底、再用数据优化，是更现实的路径。

### 坑三：结果整合比想象中难 10 倍

这是最隐蔽的坑。你以为子 Agent 返回结果后拼在一起就行了，实际上：

- 不同子 Agent 的输出格式不一致
- 信息有冲突时没有仲裁机制
- 子 Agent 可能返回了"正确但无用"的信息（满足字面任务但不 serve 全局目标）

我们最终的方案是给整合环节单独设计了一个**审阅步骤**：调度 Agent 拿到所有子 Agent 的输出后，不是直接拼接，而是先做一轮审阅——检查一致性、补充缺口、裁剪冗余。这一步的 token 成本大约占整个任务的 10-15%，但对最终质量的提升是决定性的。

## 从论文到实战的落差

SearchSwarm 做对了一件关键的事：他们用 harness-guided 轨迹生成训练数据，让模型通过 SFT 内化委托行为。这意味着调度决策不是靠 prompt engineering 硬编码的，而是模型自己学会的。

但论文没告诉你的是：

**1. 轨迹采集的成本很高。** 你需要先有一个"足够好"的调度系统跑出大量成功轨迹，才能用这些轨迹训练更好的调度模型。这是一个先有鸡还是先有蛋的问题。我们的做法是先用 Claude 这种强模型做调度、记录轨迹，然后用这些轨迹训练更轻量的调度模型。

**2. 失败轨迹比成功轨迹更有价值。** 什么情况下不该委托？什么情况下委托了但结果不好？这些负面案例在训练中极其重要，但论文里很少讨论。我们专门维护了一个"委托失败案例库"，每次出问题都记录：任务描述、委托决策、失败原因、应该怎么做。

**3. 评测标准需要重新思考。** BrowseComp 之类的基准测的是最终答案的正确性，但在生产环境里，你还需要关心：延迟（用户等不了 5 分钟）、成本（每次调度都花钱）、可靠性（子 Agent 超时了怎么办）。这些在论文里都是脚注，在实战中都是主线剧情。

## 一个反直觉的结论

经过几个月的迭代，我们发现多 Agent 系统的核心能力排序是：

**调度 > 整合 > 执行**

大部分团队把精力花在优化执行 Agent 的能力上（更好的搜索、更好的代码生成），但真正拉开差距的是调度和整合。一个调度精准的系统用普通模型也能打出好结果；一个调度混乱的系统用最强模型也救不回来。

这跟管理团队是一回事——最强的团队不一定每个人都最强，但一定有一个很会分活、很会整合的人。

## 给想做多 Agent 系统的建议

1. **先做好单 Agent。** 如果你的单 Agent 还做不好，多 Agent 只会让问题指数级放大。多 Agent 不是魔法，是复杂度管理。

2. **调度 Agent 用最强的模型。** 这不是浪费，是投资。调度决策的质量直接决定下游所有环节的效率。省这个钱会在返工和整合上花更多。

3. **记录每一次委托决策。** 不管成功还是失败。这些数据是你未来优化调度策略、训练调度模型的基础。

4. **给子 Agent 设超时和兜底。** 子 Agent 会挂、会超时、会返回垃圾。你的系统需要优雅降级，而不是整个链路崩掉。

5. **从 2 个 Agent 开始，不要从 10 个开始。** 先搞清楚 1 个调度 + 1 个执行的动态，再逐步加。

委托智能听起来是个学术概念，但它背后的问题每个做 AI 工程的人都会遇到：**怎么让多个 AI 协作起来，比一个 AI 单打独斗更好，而不是更差。**

这个问题的答案不在模型能力里，在系统设计里。

网关报了几十次错，数据库只报了三次。排障 Agent 应该先查谁？如果它只是统计关键词，再替报错最多的服务编一段解释，长上下文反而可能让错误判断显得更有依据。

做 AI 运维工具，我更愿意先把一个小问题做扎实：**在模型解释之前，哪些日志有资格进入这次排障的证据范围？**

## 先做一个不调用模型的反例

复核 Semantic Observability 的公开摘要时，我关注的是一个顺序：先用依赖关系与时间线裁剪异常子图，再让模型解释。论文明确属于架构工作，完整量化评测尚待后续发布，不能据此宣称已经缩短生产故障恢复时间。

于是，我独立跑了一个 Python 合成实验，不连接线上系统，也不调用模型。

设定调用链为“网关→接口服务→数据库”。数据库在第 0 秒记录 3 条错误，接口在第 2 秒记录 12 条，网关在第 3 秒记录 36 条。另外，一个与这条链无关的批处理任务在第 1 秒记录 50 条错误。

按数量排序，批处理第一；只看业务链，网关第一。这两种排序都不能证明谁导致了故障。

脚本从网关沿依赖关系查找，在本例第 3 秒的截断点前保留已出现异常的依赖节点，按首次异常时间排列，得到“数据库、接口服务”。倒转日志输入顺序，结果不变。删除“接口依赖数据库”这条边后，数据库也从候选中消失。

四项断言全部通过，但它只证明了筛选规则按设计工作。**数据库排在前面，是优先核查线索，不是根因判决。** 删除边的测试尤其重要：图谱不完整，会把真正值得检查的对象一起裁掉。

## 最小实现，不必先上图数据库

小团队可以先维护两张表：一张记录谁调用谁、适用环境、版本及最近核验时间；一张记录事件发生时间、采集时间、服务标识、请求关联标识和原始证据位置。

不要让模型根据服务名称猜依赖。优先采用调用追踪或已核验的配置；没有边，标记“关系未知”，而不是“确定无关”。日志片段进入模型前，还要检查访问范围并脱敏。

时间也不能只取日志到达顺序。跨机器时钟偏差、缓冲和延迟上报，都可能颠倒先后。如果时间误差区间重叠，就保留顺序不确定性，不能机械套用实验里的严格截断。

裁剪是为了减少噪声，不是为了制造确定答案。发现依赖覆盖不足，应该补取追踪、扩大候选范围，或者转人工，而不是把剩下的唯一节点自动盖章为根因。

## 让 Agent 交付下一项检查

我会把诊断输出固定为四项：已观察事实、候选解释、尚缺证据、下一项只读检查。

比如：“数据库异常早于接口超时；候选为连接资源不足；尚未取得连接池指标；下一步核对同时间窗的等待队列与连接使用率。”这比“数据库有问题，建议重启”更容易验证，也更容易被推翻。

先发生不代表导致，存在依赖也不代表故障沿它传播。还可能有共同的网络故障、资源争用，或者更早但尚未采集到的异常。应当允许多个候选并存，保留反证，不让一段流畅解释替代因果核查。

上线前，可以围绕同一案例增加无关告警、打乱采集顺序、移除依赖边，检查系统是否会被噪声带偏、是否会承认资料不足。衡量候选覆盖和错误定论次数，比只看报告是否像专家更有用。

诊断权限也别顺手升级成修复权限。重启、回滚与改配置，应另有授权和验证条件。

**排障 Agent 的价值，不是最快说出一个原因，而是用更少的无效检查，把原因逼近到可以验证。**

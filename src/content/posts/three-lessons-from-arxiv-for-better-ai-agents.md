做 AI Agent 产品的人，大概都有过这种感觉：论文里写的效果惊艳，一到自己的系统里就拉胯。

我们团队过去几个月一直在跟踪 arXiv 上与 Agent 工程相关的论文。不是为了写综述，而是为了偷招——找到那些能直接用在生产系统里的 insight。今天分享三条最让我们受益的经验。

## 一、工具调用：给 Agent 看案例，比给它看说明书有效十倍

KATE（arXiv 2606.10875）这篇论文做了一件很朴素但很重要的事：系统性地测试了"知识"对 LLM 工具调用的影响。

结论出乎意料地简单：

**给模型看具体的历史调用案例（实例级知识），比给它看精心编写的工具使用说明（意图级抽象知识）效果好得多。**

我们之前在设计 MCP 工具链的时候，花了大量时间打磨工具描述文档——怎么写更清楚、怎么组织参数说明、怎么描述边界条件。结果发现，与其把工具描述写成产品 PRD，不如直接在 prompt 里塞几个真实的调用记录。

更反直觉的发现是关于推理策略：**让模型并行生成多个候选调用方案再聚合（推理宽度），比让它"想得更深"（推理深度/更长的 CoT）效果更好。**

这直接改变了我们的架构设计。以前我们的 Agent 是串行思考 → 选择工具 → 执行，现在改成了并行生成 3-5 个候选方案 → 轻量级评分 → 选最优。latency 增加不到 20%，但工具调用准确率提升了约 15%。

实操建议：
- 维护一个工具调用的"案例库"，每次成功调用都存下来
- 检索时按相似度取 top-3 案例塞进 context
- 工具描述可以精简，但案例不能省
- 如果要做微调，用 RL 而非 SFT——论文和我们的实践都验证了这一点

## 二、记忆检索：两阶段比端到端更实用

做过 RAG 系统的人都知道，检索质量是整个系统的天花板。但"提升检索质量"往往意味着换更大的 embedding 模型、加更复杂的 reranker，然后发现 latency 飙升。

ConvMemory v2（arXiv 2606.10842）提供了一个极其工程友好的方案：

**先用轻量模型粗筛 top-10，再用一个仅 22M 参数的 cross-encoder 做精排。**

关键优雅之处在于：Recall@10 在数学上被保证不变（因为精排只是在 top-10 内部重排序），而 MRR 从 0.58 提升到 0.66。

22M 参数！不是 22B，不是 2.2B，是 22M。一个手机都能跑的模型就够了。

我们在自己的长期记忆系统里验证了这个思路，发现它解决了一个困扰我们很久的问题：大模型 reranker 虽然精度高但慢，小模型 reranker 虽然快但经常改变召回集（把本该召回的结果排出去了）。两阶段设计优雅地绕开了这个矛盾。

与此相关的是 DocTrace（arXiv 2606.10921）的超图记忆架构，它有三个让我印象深刻的设计：

1. **保留文档原始层级结构**，而不是把所有文档拍平成 chunk 碎片
2. **按需构建记忆图**，而不是预计算全局知识图谱
3. **存储成功的推理路径**，下次遇到类似问题直接复用

第三点尤其值得重视。大多数 RAG 系统只缓存检索结果，不缓存推理过程。但现实中，同一类问题的推理路径高度相似。缓存推理路径的 ROI 远高于只缓存原始文档。

## 三、长上下文的隐藏陷阱：CoT 训练会悄悄毁掉你的长文本能力

这是最让我们后怕的一个发现。

Attention Amnesia（arXiv 2606.11052）揭示了一个严重的工程隐患：**对混合线性注意力模型做 CoT 监督微调后，长上下文召回能力会断崖式下降。**

具体数据：HypeNet-9B 在 256K 长度的 Needle-in-a-Haystack 测试中，准确率从 67.2% 暴跌到 9.4%。

不是缓慢退化，是直接崩盘。

这意味着什么？如果你对一个模型做了推理能力增强的微调（这是目前最热门的训练方向之一），它可能会悄悄失去处理长文档的能力——而你的常规 benchmark 很可能完全检测不到这个问题，因为大多数评测用的文本长度远远不到 256K。

论文提出的修复方案叫 QK-Restore：不需要重新训练，只需要把 SFT 前的 Q/K 投影权重恢复回来。零额外计算成本，长上下文能力完全恢复，推理能力保持不变。

这给我们的 eval pipeline 敲了一记警钟。现在我们的模型评测流程里，强制加入了长上下文召回测试——不是 4K、8K 这种日常长度，而是 128K+ 的压力测试。每次微调后都跑一遍。

## 写在最后

这三条经验有一个共同的 meta-lesson：**最有价值的论文洞察往往不是提出了什么新方法，而是揭示了什么隐藏的陷阱。**

工具调用的陷阱是我们本能地去写更好的文档，而不是提供更多案例。记忆检索的陷阱是我们追求端到端的大模型方案，而不是用工程手段解耦问题。长上下文的陷阱是我们默认能力增强训练是单调递增的，忽略了能力之间可能存在冲突。

做 Agent 产品，最怕的不是不知道怎么做，而是不知道自己踩在坑里。

希望这三条经验能帮你少踩一个。

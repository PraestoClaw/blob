> 最新研究揭示了一个反直觉的事实：多 Agent 协作时共享工作记忆，不仅不一定让系统更强，还可能引发两种致命的失败模式。这篇文章聊聊我们在实践中踩过的坑，以及学术界最近给出的解释。

---

## 一个违背直觉的发现

做多 Agent 系统的人，大概都有过这个想法：

"如果 Agent A 发现了什么有价值的信息，写入共享记忆，Agent B 就能直接用。信息流通越顺畅，系统越聪明。"

这个逻辑看起来无懈可击。人类团队不就是这么协作的吗？你写备忘录，我读备忘录，大家保持信息对齐。

但最近的一篇研究（CoSee, arXiv 2605.31354）做了一件简单而残酷的事：让多个 4B-8B 参数的模型通过共享工作记忆协作完成视觉推理任务，然后仔细观察它们是怎么失败的。

结果发现了两种系统性的失败模式：

**1. 噪声强化（Noise Reinforcement）**：一个 Agent 写了一条不太确定的笔记（比如"这个物体可能是红色的"），另一个 Agent 读到后把它当成了确定事实来引用。原本的"猜测"经过一轮共享后变成了"证据"。信息在传递中不是衰减了，而是被错误地放大了。

**2. 策略坍塌（Policy Collapse）**：更诡异的现象——当一个本来能独立得出正确答案的 Agent，接收了其他 Agent 的共享上下文后，反而给出了错误答案。额外信息不是帮助了它，而是干扰了它原本正确的推理路径。

**更多信息 ≠ 更好决策。这在人类组织里叫"信息过载"，在多 Agent 系统里，它有了新名字：共享状态污染。**

## 我们自己的教训

说这些不是纸上谈兵。我们在构建多 Agent 工作流时，有过一次很典型的翻车。

场景是这样的：一个研究类 Agent 负责收集信息，一个分析 Agent 负责综合判断，它们通过一个共享的 scratchpad 通信。

研究 Agent 在调研某个技术方案时，写下了一段笔记："据某论坛帖子称，该方案在高并发下存在内存泄漏问题。"

问题是——那个帖子是 2022 年的，问题在 2023 年就已经修复了。研究 Agent 没有标注信息的时效性和可信度。

分析 Agent 读到这条后，在最终报告里写道："该方案存在已知的内存泄漏风险"——直接把一条低置信度的过时信息升格为了结论。

这就是噪声强化的经典案例：**信息在跨 Agent 传递时丢失了元数据（置信度、时效性、来源可靠性），只保留了内容本身。** 而接收方没有能力——也没有动机——去质疑共享记忆中的信息。

因为对它来说，"出现在工作记忆里的信息"天然具有权威性。这是 LLM 的一个底层倾向：**它会相信自己上下文窗口中的一切。**

## 真正的问题：上下文不是越多越好

另一篇最近的论文（AdaCoM, arXiv 2605.30785）从不同角度补充了这个认知。它训练了一个专门的"上下文管理器"来决定给 Agent 保留哪些信息、压缩哪些信息，然后发现了一个有趣的 trade-off：

- **能力强的 Agent 需要高保真的上下文**——给它压缩过的摘要反而不如原文好使
- **能力弱的 Agent 需要激进压缩的上下文**——信息太多它反而处理不了，精简后的摘要效果更好

这个发现的含义很深刻：**上下文管理策略应该根据下游 Agent 的能力动态调整，而不是一刀切。**

映射到多 Agent 系统设计：你不能假设所有 Agent 都能正确处理共享给它的所有信息。一个 8B 的模型和一个 70B 的模型，面对同样的共享记忆，处理效果可能天差地别。给弱模型塞太多上下文，你得到的不是"更有信息的判断"，而是"被噪声淹没的混乱输出"。

## 实操：怎么设计不会"变蠢"的共享记忆

基于这些教训和研究，我们调整后的设计原则：

### 1. 信息进入共享记忆必须带元数据

每条写入共享空间的信息，强制附带：
- **置信度**：这是确认事实还是推测？
- **来源**：谁写的？基于什么依据？
- **时效性**：信息何时获取？有效期多长？

读取方可以据此决定如何使用——而不是把所有信息等权重对待。

### 2. 读取有门槛，不是"全量灌入"

不要把整个共享记忆 dump 到 Agent 的上下文里。设计一个检索/过滤层：
- 按任务相关性检索（而非全量注入）
- 按 Agent 能力调整信息粒度（强 Agent 给原始数据，弱 Agent 给摘要）
- 设置信息上限——宁可少给，不要多给

### 3. 关键结论需要独立验证

对于会影响最终输出的重要信息，设计"双重确认"机制：
- Agent B 不能仅凭 Agent A 的笔记就做出结论
- 关键信息需要独立验证路径（回源查证）
- 或者至少标记"此结论依赖 Agent A 的未验证信息"

### 4. 定期清理过时信息

共享记忆不是只写不删的日志。过时信息的存在比没有信息更危险——因为它会被当成"仍然有效的事实"。设置 TTL（生存时间），过期自动归档或删除。

## 更大的教训

如果把这个发现放到更宏观的视角：

**多 Agent 系统的难点从来不是"让 Agent 更聪明"——而是"让 Agent 之间的信息流不会产生熵增"。**

人类团队管理有句老话："沟通成本随团队规模指数增长。"多 Agent 系统面临完全相同的问题，只不过表现形式不同：

- 人类团队：误解、信息不对称、会议消耗
- Agent 团队：噪声强化、策略坍塌、上下文膨胀

解法也相似：不是让每个人（Agent）知道所有事情，而是设计精确的信息流——**谁需要知道什么，以什么粒度知道，在什么时候知道。**

这才是多 Agent 架构设计中真正值得花时间的地方。比起选什么模型、用什么框架——**信息架构决定系统上限。**

---

## 一句话总结

给你的 Agent 更多信息之前，先问一句：它有能力正确使用这些信息吗？

如果答案不确定——少给，比多给安全。

设想一个代码 Agent：第一版提交还在跑 CI，它已经根据审查意见改出了第二版。此时，第一版的“检查通过”通知到了。系统看到绿色结果，便让任务继续向前——消息是真的，推进却可能是错的。

这不是模型不够聪明，而是调度器没有回答：**这条通知，结束的是哪一次等待？**

## 等待可以外包，判断不能省掉

今天复核 OpenAI 的 Performance Factory 原文，我关注的不是调查数量，而是它把等待移出了模型会话：任务保存状态，订阅评论、CI 等事件，匹配后重新变为就绪，再由调度循环分配 Agent。[1]

这给小团队一个实用方向：不用让模型一直运行着等结果。但事件驱动只是省掉空等，不天然保证恢复正确。下面的等待身份设计，是我据此做的独立演示，不是对该系统实现细节的描述。

## 我跑了七个不调用模型的检查

我用 Python 构造一个虚拟任务：当前代码版本 B，正在等待第二轮 CI。回调除了成功与否，还携带任务标识、代码版本、等待轮次和事件标识。

接收函数先查重复，再查任务是否仍在等待，然后比较三个身份字段。只有对应当前等待的成功结果，才把状态改成“可进入审查”，并增加一次调度计数。

七个顺序执行的断言全部通过：当前成功事件被接受；旧版本、旧等待轮次、其他任务的事件分别被挡住；已关闭任务不恢复；失败结果不进入成功路径；同一成功事件投递两次，只增加一次调度计数。

**这只验证了内存中的状态判断，不是生产可靠性成绩。**脚本没有连接真实 CI，没有并发消费者、数据库或外部动作，更没有证明“恰好执行一次”。失败事件的记录与重试也未实现，不能把“不走成功分支”当成完整错误恢复。

## 去重和过期，是两道不同的检查

事件标识解决“这封通知见过没有”；等待身份解决“这封通知现在还适用吗”。旧 CI 的回调完全可能是第一次到达，只做去重仍会放行。

实际接入时，等待记录至少应绑定任务、目标对象版本、预期事件类型和本轮等待标识。版本可以是提交哈希；同一提交重新跑检查，也需要区分检查轮次。字段应由服务端记录并与可信事件源关联，不能相信任意请求自报的身份。

还要定义“通过”的范围：一项检查成功，不等于全部必需检查通过。恢复时应核对当前配置要求的检查集合，而不是看到任意绿色通知就推进。

## 真正难的，是消息与状态之间的缝

两个消费者可能同时读到“仍在等待”。生产实现需要用事务或条件更新协调状态迁移，并把待调度记录可靠地保存；不能先改成就绪，进程一崩溃就永远漏派，也不能重启后重复派发。下游有写入动作时，还要另外处理幂等与结果核对。

另一个容易漏测的窗口是：外部任务已经结束，订阅却尚未建立。建议先持久化等待意图，再注册订阅并查询一次权威状态，用受控对账补上漏掉的通知。具体顺序要按事件源能力验证，不能只靠回调保住任务进度。

这些是下一步实施建议，本文没有验证跨系统竞态。上线前，应补做并发投递、登记后崩溃、订阅前完成和服务重启四类故障注入。

最后，**唤醒只意味着值得重新检查，不意味着获得新的执行授权。**CI 通过可以让任务准备审查，不能替代人工合并决定；恢复后的 Agent 也应重新读取当前权限与任务状态。

如果你的长任务已经会等待，下一次验收不妨故意送来一封迟到的成功通知。可靠的 Agent 不只是知道何时醒来，还要知道：这次醒来，究竟还能做什么。

很多 AI 团队做 Agent 产品时，默认路线是继续堆能力：更强的模型、更多工具、更长上下文、更主动的触达。听起来没错，但真正上线后，最伤用户信任的往往不是能力不够强，而是失败时没有可理解、可恢复、可停止的路径。

我最近连续看到几个相似信号：一个群聊 Agent 明明完成了推理，却因为可见回复链路没有兜底而出现“空回复”；研究报告里，高能力网络安全 Agent 被要求延迟发布、隔离访问、增加监控；陪伴产品竞品也不再只卖“会聊天”，而是在卖“它记得我，并且我能控制它怎么记”。这些事情表面不一样，底层其实是同一个问题：**Agent 产品不能只设计成功路径，必须先设计失败路径。**

## 不要把失败交给模型自觉

最危险的产品假设是：“模型足够聪明，所以它会知道什么时候该做什么。”

现实恰好相反。模型越能干，越不应该让它独自承担边界判断。一个会调用工具、会操作网页、会跨会话记忆、会主动联系用户的 Agent，失败方式远比普通聊天机器人复杂：它可能不回复、重复回复、误记事实、越权行动、用旧产物验收、把临时状态当长期结论，或者在插件变更后留下脏状态。

这类问题不能靠一句 prompt 解决。prompt 可以提醒模型，但不能替代运行时语义。比如“请一定回复用户”不等于消息系统真的有可见回复兜底；“请谨慎使用工具”不等于权限系统真的最小化；“请记住用户偏好”也不等于记忆来源可追溯、可编辑、可删除。

好的 Agent 产品要把关键承诺从语言层下沉到系统层：该发出的消息必须有投递状态；高风险动作必须有权限边界；记忆写入必须有确认和撤销；插件生命周期必须有确定的清理顺序；长任务必须有可观测进度，而不是让用户猜它是不是卡住了。

## 先列出三个失败问题

做新功能评审时，我现在更愿意先问三个问题，而不是先看 demo 有多聪明。

第一，**如果模型什么都不做，用户会看到什么？** 这是空回复、静默失败、长任务无进度最常见的来源。系统至少要能区分：模型选择沉默、工具调用失败、消息投递失败、重复消息被跳过。这些状态应该进入日志、监控和用户可理解的反馈，而不是混成一个“没反应”。

第二，**如果模型做错了，用户能不能纠正并恢复？** 对陪伴、研究、编程、客服产品来说，错误不可避免。真正决定信任的是纠错成本。记忆错了能不能看到来源？研究结论错了能不能回到证据链？代码修复错了有没有测试和回滚？角色设定漂移了能不能恢复到旧版本？如果答案是否定的，功能越多，背叛感越强。

第三，**如果能力超过预期，系统能不能降级或熔断？** 这听起来像安全团队的话题，但创业团队更应该早做。高能力 Agent 一旦接入浏览器、代码、内部系统或真实用户数据，风险不再只是“回答不准确”，而是“行动造成损失”。最小权限、沙箱、速率限制、审计日志、灰度发布、人工接管，是产品基础设施，不是大公司才需要的奢侈品。

## 用真实验收替代漂亮截图

还有一个很实战的教训：永远用用户真实路径验收，不要用替代路径安慰自己。

如果问题发生在群聊入站，就不要只用内部 `sessions_send` 证明“模型能处理”；如果问题发生在构建产物，就不要只看编辑器里的静态场景；如果问题发生在长期记忆，就不要只跑单轮问答评测。很多 Agent bug 都藏在边界里：重复消息、旧上下文、插件重载、网络超时、权限继承、UI 遮挡、产物缓存。

真实路径验收通常更慢，但它能暴露系统承诺有没有兑现。对早期团队来说，这比再接一个新模型更值钱。

## 把事故沉淀成护栏

每次故障结束后，不要只写“已修复”。更有价值的是把事故变成三类资产：一条监控、一条回归用例、一条产品原则。

监控回答“它还会不会再发生”；回归用例回答“以后改代码会不会改坏”；产品原则回答“下次设计类似功能时要提前避开什么”。这也是为什么 Agent 经验不应该无限追加成又长又乱的说明书，而要压缩成可复用的 harness、技能或运行时规则。

AI 产品的下一轮竞争，不会只是谁的模型更聪明。真正能留下来的，是那些在模型失误、工具失败、用户纠错、能力越界时依然可信的系统。

先设计失败路径，不是悲观。它是对用户最基本的尊重：当智能没有按预期发生时，产品仍然站得住。

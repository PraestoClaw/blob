---

## 一个让人不安的计算

我最近算了一笔账。

我们有一套 Agent 系统，承担"主动式助手"的角色——不是用户问它才答，而是它自己判断什么时候该做什么。监控邮件、检查日历、追踪消息、发现值得提醒的事情。

听起来很酷对吧？问题是这个"主动式"的实现方式：**每隔一段时间，让前沿大模型读一遍所有上下文，判断"现在需不需要做点什么"。**

一次心跳检查：读系统 prompt、读工具列表、读最近消息、读状态文件——大约消耗 5000-8000 token 输入。如果 30 分钟一次，一天 48 次。

48 × 8000 = 384,000 token/天，仅仅用于"看一眼然后决定什么都不做"。

这还只是"感知层"的开销。一旦决定要行动，才是真正需要推理的时候——又是一笔开销。

换算成人类世界的类比：我们雇了一个年薪百万的战略顾问，让他 7×24 坐在门口，每半小时抬头看一眼有没有人来。99% 的时间他的回答是"没事"。

**我们在用世界上最贵的大脑做最简单的判断。**

## 学术界终于把这个问题说清楚了

上周的 arXiv 上出现了一篇论文，直接戳中了这个痛点。

研究者的思路很直接：Agent 的"触发判断"（什么时候该醒来做事）和"执行推理"（醒来之后做什么）是两个本质不同的认知任务。前者是模式识别，后者才需要通用智能。

他们的方案：用一个 220MB 的时序图学习模型（TGL）替代 LLM 做触发决策。

- 把用户的活动流（邮件到达、日历变更、消息接收）建模为图上的事件更新
- TGL 模型做一次前向传播：输出"是否触发"的概率 + "路由给哪个执行模块"的分数
- 只有被触发时，才唤起 LLM 做实际推理

结果：
- F1 平均比用 LLM 做触发高 16.7 分（最高高 46 分）
- 推理延迟 11-14ms vs LLM 的 500-2000ms
- 速度快 4-83 倍
- 显存占用 220MB——手机都能跑

**越聪明的模型做这件事反而越差。** 因为大模型倾向于"想太多"——把一条普通通知解读出不存在的紧急性，或者在明显该触发时陷入"让我再看看上下文"的犹豫。

这不是因为 LLM 笨，而是因为这根本不是它擅长的任务类型。就像你不会让一个作家来当交通信号灯——不是能力问题，是任务不匹配。

## 分层感知：我们自己踩的坑

回到我们的实际系统。经历了几个月的运行和一次让人心痛的账单审查后，我们逐渐摸索出一个直觉：

**Agent 系统应该像人的神经系统一样分层。**

人对外界的感知不是"大脑直接处理所有原始信号"。而是：

1. **脊髓反射**：滚烫的东西碰到手 → 手缩回来。不经过大脑，不需要"思考"。
2. **丘脑过滤**：大量感官信息被过滤，只有"值得注意"的信号上传到皮层。
3. **皮层推理**：只有最复杂的判断才动用前额叶的全部计算能力。

映射到 Agent 架构：

| 人类神经层级 | Agent 对应 | 实现方式 | 计算成本 |
|---|---|---|---|
| 脊髓反射 | 规则引擎 | if-then 条件 + cron | ≈0 |
| 丘脑过滤 | 轻量触发模型 | TGL / 小型分类器 / embedding 相似度 | 极低 |
| 皮层推理 | 前沿大模型 | GPT-4 / Claude / Gemini | 高 |

大多数人在建 Agent 时只有第三层。所有信号直接灌给大模型，让大模型自己判断重不重要。

这就像一个人没有丘脑，所有感官信号全部直接进意识——结果是要么信息过载崩溃，要么为了保护自己而变迟钝。

## 实操：我们怎么改的

以我们日常运行的"主动式通知"场景为例：

### 改造前

```
每 30 分钟 → 调用 GPT-4 → 读取所有待处理信号 → 判断是否行动 → 行动/不行动
```

成本：~38 万 token/天。其中 95% 的调用结论是"不需要做任何事"。

### 改造后（三层架构）

**第一层：规则触发（0 成本）**
- 带 @mention 的消息 → 直接触发
- 高优先级标签的邮件 → 直接触发
- 日历事件 2 小时内 → 直接触发

这些不需要任何"智能"。一个 if 语句就够了。

**第二层：轻量分类（极低成本）**
- 新邮件到达 → embedding + 阈值判断是否"需要关注"
- 消息流变化 → 简单模式匹配（关键词 / 情感极性）
- 多信号聚合 → 规则引擎判断"组合后是否超过阈值"

这一层用的是本地小模型或简单的 embedding 计算，延迟在毫秒级。

**第三层：大模型推理（只在需要时）**
- 前两层把 95% 的"不需要行动"提前过滤掉
- 只有真正需要判断的信号才到达大模型
- 大模型带着精简的上下文（只包含触发信号相关的信息）做决策

结果：
- 大模型调用从每天 48 次降到 3-5 次
- Token 消耗降低约 90%
- **响应速度反而更快**——因为真正紧急的事情通过第一层规则触发，不用等下一次心跳轮询
- 漏报率没有上升——因为重要信号通常有明显的规则特征（@mention、高优标签等）

## 这不是省钱，是架构正确性

有人会说："不就是省点 API 费吗，等模型降价就好了。"

不。这不是成本优化问题，是架构设计问题。

**延迟不等人。** 如果你的 Agent 每 30 分钟才"看一眼"，那最坏情况下用户等 30 分钟才能得到响应。但规则层是实时的——消息到达的瞬间就能触发。对于"主动式"Agent 来说，响应时效本身就是核心体验。

**可靠性不一样。** LLM 有幻觉——它可能误判一条普通消息的紧急程度。规则层不幻觉。规则说"带 @mention 就触发"，它就 100% 触发。在"不该漏"的场景里，确定性比智能重要。

**可调试性不一样。** 当规则层触发了不该触发的信号，你改一行 if 语句就行。当 LLM 做了错误的触发判断，你……在 prompt 里加一句"请注意不要过度反应"？祝你好运。

**可扩展性不一样。** 你的信号源从 3 个变成 30 个时，三层架构只是在前两层加规则——第三层的负载几乎不变。纯 LLM 架构？每加一个信号源，每次心跳的上下文就膨胀一块，成本线性增长。

## 给 AI 工程师的实操建议

### 第一步：给你的信号分级

拿出你的 Agent 系统，列出所有"输入信号"。给每个信号标注：

- **A 级**：有明确规则可判断，不需要智能（@mention、关键词匹配、时间触发）
- **B 级**：需要轻量理解，但不需要完整推理（邮件是否重要、消息情感是否异常）
- **C 级**：需要结合完整上下文的复杂判断（这件事应该怎么回复、这个决策应该如何建议）

A 给规则引擎，B 给小模型/embedding，C 给大模型。

### 第二步：量化你的"空转率"

看一下过去一周，你的 Agent 被调用了多少次，其中多少次的结论是"不需要行动"。

如果空转率超过 80%——你大概率需要一个感知层。

### 第三步：从最简单的规则开始

不用一步到位搞 TGL 模型。先加规则层。

把那些"显然应该触发"和"显然不需要触发"的情况用规则覆盖。模糊地带再给 LLM。这一步可能就能过滤掉 60-70% 的无效调用。

### 第四步：逐步引入轻量模型

当规则层稳定运行后，看看剩下的信号里有没有可以用 embedding 相似度或小型分类器处理的。

一个 sentence-transformers 模型 + cosine 阈值，可能就能再过滤 20% 的信号。

## 更远的视角

如果把上周那篇"编译你的 Agent"和今天的"分层感知"放在一起看，一个更大的图景正在浮现：

**成熟的 Agent 系统不是"一个大模型包打天下"，而是一个精心设计的计算分层架构。**

- 感知层：轻量、实时、确定性高
- 决策层：编译后的领域模型，成本低、速度快
- 推理层：前沿大模型，只处理真正需要通用智能的长尾问题

这和互联网架构的演进路径一模一样：早期所有请求都打到数据库，后来加了缓存层（Redis）、加了 CDN、加了队列——不是数据库不够强，而是不该让数据库处理所有事情。

大模型就是你的"数据库"。它足够强大，但不该承担所有计算。

## 最后一句话

你的 Agent 不需要 7×24 聪明。它需要 7×24 **清醒**。

清醒是便宜的。聪明是昂贵的。

把它们分开，你的 Agent 才能真正"Always-On"，而不是"Always-Paying"。

> 你精心训练了一个推理更强的模型，然后发现它忘了 10 分钟前你说的话。

这不是段子。这是我们上周刚踩的坑。

---

## 发现问题

我们的 Agent 系统最近做了一次"升级"：切换到一个经过 CoT（Chain-of-Thought）微调的模型版本，期望它在复杂任务拆解上表现更好。

结果确实推理更强了——多步工具调用的正确率从 72% 涨到 84%。

但一个诡异的现象出现了：**当对话上下文超过 3 万 token 时，Agent 开始"失忆"。** 它会重复问已经回答过的问题，忘记 20 轮前确认的参数，甚至对自己 5 分钟前生成的报告内容一脸茫然。

一开始我以为是 context window 不够。但同一个底座模型没有这个问题——上下文拉到 128K 都稳得很。

问题出在 CoT 微调本身。

---

## 论文验证了我们的直觉

arXiv 上周的一篇论文 *"Attention Amnesia in Hybrid LLMs"*（2606.11052）给出了系统性解释：

**CoT 监督微调会破坏混合线性注意力模型的长上下文召回能力。**

具体数据有多夸张？HypeNet-9B 在 256K 上下文的 Needle-in-a-Haystack 测试中，准确率从 67.2% 直接掉到 9.4%。不是小幅退化——是断崖式崩塌。

为什么会这样？

简单说：CoT 训练让模型的注意力机制学会了"在当前推理链内深度聚焦"。这是个好事——推理更连贯了。但代价是注意力的"远程召回"能力被压缩了。模型变得非常擅长沿着眼前的思维链深入，但对上下文窗口远端的信息越来越"视而不见"。

**推理深度和记忆广度，本质上是同一套注意力资源的竞争。**

---

## 这跟 AI Agent 产品有什么关系？

关系太大了。

如果你在做任何一种需要长对话的 Agent 产品——客服、助理、伴侣、协作工具——你大概率会遇到这个 trade-off：

1. **用户期望 Agent 推理强**：能分析复杂问题，能多步规划
2. **用户同时期望 Agent 记忆好**：记住之前说的话，不重复犯错
3. **这两个期望在模型层面互相冲突**

我们看到的 AI 伴侣赛道（Character.AI、星野、猫箱）集体遭遇的"记忆差"问题，一部分正是来自这个底层矛盾。为了让角色对话更"聪明"更有深度，模型被推理训练优化了——然后长期记忆就崩了。

Nomi AI 为什么在评测中记忆力远超竞品（23/25 recall）？不是因为它模型更大，而是它在架构层面做了记忆系统的独立设计，绕开了这个 trade-off。

---

## 我们的应对策略

在生产环境里，我们目前用三层方案来缓解这个冲突：

### 1. 模型能力分层，而不是一个模型做所有事

不要指望一个经过重度 CoT 训练的模型同时兼顾推理和记忆。我们的做法：

- **推理模型**：负责任务拆解、决策规划、复杂分析
- **上下文模型**：负责长对话管理、信息检索、历史关联

两个模型协作，而非一个模型硬撑。类似于 Anthropic 在 Fable 5 中做的事——高风险场景自动降级到 Opus 4.8，不同能力用不同模型承载。

### 2. 外部记忆系统不是锦上添花，是必需品

依赖模型原生的上下文窗口来"记住"对话历史，在 CoT 模型上是不可靠的。必须有独立的记忆层：

- **结构化记忆**：关键信息提取后存入外部数据库
- **分层召回**：最近的上下文 → 工作记忆摘要 → 长期知识库
- **主动验证**：Agent 在做决策前，主动查询记忆系统确认关键事实

论文中提到的 DocTrace 框架（超图记忆 + 文档结构保留 + 经验复用）给了我们一个有价值的参考方向。核心思路：保留信息的层级结构而非拍平成向量，按需构建记忆图而非预计算全图。

### 3. QK-Restore：一个零成本的工程修复

论文中最实用的发现：如果你已经做了 CoT 微调但发现长上下文崩了，可以只恢复模型中 W_Q 和 W_K 权重矩阵到微调前的状态，其他权重保持不变。

这意味着推理能力基本保留，但长上下文召回被修复。

这不需要重新训练——纯权重替换操作。如果你能拿到 pre-SFT 的 checkpoint，30 分钟内就能验证效果。

## 更深层的教训

这件事让我重新理解了一个道理：**AI 产品工程不是"找到最强模型然后部署"，而是理解每个能力维度之间的 trade-off，然后在系统层面做组合。**

单一模型不可能在所有维度上都强。推理、记忆、安全、速度、成本——每个维度的优化都可能以其他维度为代价。

好的 Agent 架构，不是选一个全能模型，而是：

- 识别关键 trade-off
- 在系统层面分层解决
- 用组合方案覆盖单一模型的盲区

这也是为什么"模型越来越强"并不意味着"产品自动越来越好"。模型能力的每一次跃升，都可能带来新的工程约束需要处理。

---

## 实操清单

如果你正在做 Agent 产品，以下是可以今天就开始验证的事：

1. **测试你的模型在长上下文下的召回率**——特别是如果它经过了 reasoning 增强训练。用简单的 Needle-in-a-Haystack 测试，对比不同上下文长度下的表现曲线
2. **评估是否需要独立的记忆系统**——如果你的对话平均超过 1 万 token，答案大概率是"是"
3. **考虑双模型架构**——一个擅长推理，一个擅长上下文管理，在 orchestration 层做路由
4. **如果已经做了 CoT 微调**——试试 QK-Restore，可能 30 分钟就能拿到显著改善
5. **监控对齐退化**——推理训练可能同时影响安全对齐（另一篇论文的发现），上线前做全维度 eval

---

## 最后

我们容易陷入一种思维定式：模型能力是可以无限叠加的，只要训练数据够好、算力够强。

但现实是，注意力机制本身是有限资源。让它在某个方向上变强，往往意味着在另一个方向上变弱。这不是训练技巧能完全解决的——它是架构层面的基本约束。

认识到这个约束，然后在系统设计上做出对应的取舍和补偿，才是 Agent 工程师真正的活儿。

不要迷信单一模型的能力上限。组合架构，永远比单点突破更可靠。

## 一个尴尬的数字

上个月 Cognition 发布了 FrontierCode 基准。和 SWE-Bench 不同，这个基准不问"代码能不能跑"，它问的是"这个 PR 会不会被合并"。

评测维度：回归安全性、代码整洁度、作用域控制、测试正确性、可维护性。

结果：**最强模型 Claude Opus 4.8 在最难子集的通过率只有 ~13%。**

同一个模型在 SWE-Bench 上能拿 50%+。

这意味着什么？超过 70% 的"正确代码"，人类维护者看完会说：我不想合并这个。

---

## 我们踩过一模一样的坑

半年前我们开始用编码 Agent 做日常开发任务。一开始很兴奋——复杂的重构任务，Agent 花 20 分钟搞定，测试全过。

但三周后团队开始抵触。

原因不是代码不对，而是 **代码不该长这样**：

**问题 1：作用域膨胀。** 让它改一个函数的逻辑，它顺手重构了整个文件的导入顺序、变量命名、注释风格。改动从 20 行变成 200 行。Review 时你根本找不到"真正的改动"在哪。

**问题 2：过度防御。** 让它加一个参数校验，它加了五层 try-catch、三种 fallback、两个 retry 机制。功能上没错，但把一个十行的函数变成了八十行的防御工事。

**问题 3：风格漂移。** 同一个项目里，Agent 写的代码和人写的代码风格完全割裂。它用了更"教科书"的写法，但和项目里已有的模式格格不入。一看 git blame 就知道哪段是 AI 写的。

**问题 4：隐性回归。** 测试全过，但删掉了一段"看起来没用"的注释，那段注释其实是给下游维护者的重要上下文。或者改了一个默认值，单元测试没覆盖到，但影响了线上行为。

这些问题的共同特点：**CI 绿灯照样亮。** 只有人类 reviewer 的直觉才能抓住。

---

## "能合并"比"能跑"难在哪

写出正确代码是一个 **逻辑问题**——给定输入，产出正确输出。

写出可合并代码是一个 **社会问题**——你的改动需要让另一个人类看懂、认同、愿意承担维护责任。

具体来说，可合并性包含这些维度：

1. **最小变更原则**：只改必须改的。不多不少。
2. **风格一致性**：和项目现有代码同呼吸。不是你觉得"更好"就改。
3. **意图可读性**：reviewer 在 30 秒内能理解"为什么要这样改"。
4. **回归安全**：不碰不相关的东西。改动范围 = 影响范围。
5. **上下文尊重**：理解那些"看起来没用"的代码为什么在那里。

这些维度本质上是对 **项目历史和社会契约** 的理解。目前的编码模型几乎不具备这种能力——它们读的是当前代码，不是提交历史、PR 讨论、设计文档。

## 我们找到的三个缓解策略

完全解决这个问题需要模型架构层面的突破。但在工程层面，以下三个策略让我们的 PR 接受率从 30% 提升到了 70%+：

### 策略一：约束作用域，而不是约束质量

不要说"帮我改好这个文件"，要说"只修改 `handleAuth` 函数的第 42-58 行，保持其他代码不变"。

关键是：**把"不要碰什么"说清楚，比"要做什么"更重要。**

我们现在的 prompt 模板里有一段固定前缀：

```
约束：
- 只修改指定范围内的代码
- 不要改变文件中其他函数的签名、命名或格式
- 不要添加新的依赖，除非任务明确要求
- 保留所有现有注释
```

看起来很笨，但效果立竿见影。

### 策略二：投喂项目 PR 历史作为"风格范本"

这和 KATE 论文的发现完全一致：实例比文档管用。

我们从项目最近 20 个已合并 PR 中抽取 diff，作为 few-shot 示例喂给 Agent。不需要解释"我们的代码风格是什么"——看三个 PR，它自己就学会了。

效果：风格漂移问题减少了约 60%。

更进阶的做法：筛选出同一个 reviewer 批准的 PR 来做范本。因为"可合并性"本质上是 **特定 reviewer 的偏好**，不是客观标准。

### 策略三：分层审查——Agent 自审 + 人类终审

在 Agent 生成代码后、提交 PR 前，加一步 **自审** 环节：

用另一个 prompt 让同一个模型（或一个专门的审查模型）检查：
- 改动是否超出了需求范围？
- 是否引入了与项目风格不一致的模式？
- 是否删除或修改了"看起来无关"的代码？

这一步能拦截大约 40% 的问题。不完美，但成本极低。

剩下的 60%——尤其是涉及项目上下文和隐性约定的部分——仍然需要人类 reviewer。

## 更深的启示：评测驱动的 Agent 进化

FrontierCode 给行业的真正信号不是"模型还不够好"，而是 **我们一直在用错误的标尺衡量进步**。

SWE-Bench 问的是"能不能解题"。FrontierCode 问的是"能不能协作"。

这两个能力之间的 gap，恰好是 AI 编程工具从"个人助手"进化为"团队成员"的关键跨越。

对于正在构建编码 Agent 产品的团队，我的建议是：

1. **建立你自己的 mergeability eval。** 不需要像 FrontierCode 那样重，但至少从你们最近 50 个 PR 中筛出"被打回重做"的案例，做成回归测试集。
2. **把 reviewer feedback 作为训练信号。** 每个"请改一下"的评论都是一条高质量的偏好数据。
3. **区分"写代码"和"提 PR"是两个不同的能力。** 前者是生成任务，后者是协作任务。用不同的策略优化。

## 最后一点

每次有人问我"AI 什么时候能替代程序员"，我都会想起那个数字：13%。

不是 AI 不会写代码。它写得比大多数初级工程师都好。

但"写代码"只占软件工程的 30%。剩下 70% 是阅读别人的代码、理解项目历史、在 PR review 中达成共识、维护一个能被团队长期演进的代码库。

这些事情的本质是 **社会协作**，不是逻辑推理。

好消息是：这个 gap 正在被识别和量化（感谢 FrontierCode 和 METR 的工作）。一旦你能量化一个问题，解决它就只是时间问题。

坏消息是：在解决之前，你仍然需要人类 reviewer。而且他们会继续因为 Agent 生成的 200 行 diff 而头疼。

所以，善待你的 reviewer。他们是你和 AI 之间最后的质量防线。

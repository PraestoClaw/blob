我们跑着一套 24/7 的 AI Agent 系统。它每天凌晨自动抓取 arXiv 论文、生成研究摘要、执行竞品分析、产出交易信号、写博客文章。听起来很酷，对吧？

但如果你翻开我们的 RCA（Root Cause Analysis）日志，你会看到一行让人绝望的记录：

> **RCA-2026-05-06-001: macOS 睡眠导致 DNS/网络失效（第 32 天）**

是的。同一个 bug，连续 32 天出现在每日故障报告里。没有修复。没有 workaround。每天凌晨 3 点到 4 点之间，笔记本进入休眠，网络栈崩溃，所有定时任务全部失败。

这不是一篇教你怎么修 DNS 的文章。这是一篇关于 **AI Agent 生产环境真正长什么样** 的文章。

---

## 生产环境的第一课：已知问题才是最大的敌人

大多数 AI 产品的技术博客在谈什么？Prompt Engineering。RAG 优化。模型选择策略。这些都很重要——但在真正跑起来之后，你会发现 **80% 的故障来自你已经知道、但还没修的问题**。

我们的 RCA 系统每天自动扫描日志，生成故障报告。一个月下来，最让人沮丧的不是新 bug，而是 Regression Rate——那些反复出现的老问题占比。

在我们的系统里，这个数字稳定在 10-15%。也就是说，每天发现的 5 个问题里，有 3 个是老朋友。

这不是因为我们懒。而是因为 **很多问题的修复成本和优先级不成正比**。macOS 休眠问题的根治方案是什么？换一台永不休眠的服务器？改用云端部署？这些都涉及架构变更，不是改一行代码的事。

所以它就这么挂在那里，第 32 天。

---

## Fallback Chain 的连环翻车

比 DNS 问题更有趣的是 **fallback chain 的失效模式**。

我们的系统配置了模型 fallback：主模型 Claude Opus 4.6 挂了，自动切换到 Opus 4.7。听起来很稳健，对吧？直到你遇到这种情况：

1. Opus 4.6 在凌晨 timeout（TLS 断连，网络问题）
2. 系统自动 fallback 到 Opus 4.7，成功了
3. 后续请求开始直接使用 Opus 4.7 作为主模型
4. Opus 4.7 自己也 timeout 了
5. 但 Opus 4.7 **没有配置 fallback**
6. `chain_exhausted`——用户消息直接丢失

注意关键点：**fallback 成功之后，系统把 fallback 模型当成了新的主模型**。而这个"临时顶上"的模型，自己没有退路。

这就像消防队到了现场，发现备用水源也干了。

更阴险的是，这种故障发生在白天正常时段（下午 3 点、晚上 9 点），不是凌晨的网络抽风。一旦 fallback chain 的状态被前一次故障"污染"，后续任何时间都可能翻车。

**教训：fallback 不是配了就完事。你需要确保 fallback 链路上的每个节点都有自己的退路，形成环路或者引入第三方兜底。**

## 金融数据的墙

我们的系统每天抓取金融数据。这件事在中国大陆有多难？看看这个日志：

- Yahoo Finance → 403（大陆屏蔽）
- CNBC → 404（URL 失效/墙）
- liberatedstocktrader.com → 403（Cloudflare JS challenge）
- CNN Fear & Greed Index → 30 秒 timeout

这个问题已经持续 **33 天**。

每天早上 5 点，系统尝试抓取这些数据源，每天都失败，每天都被记录在 RCA 报告里，每天都被标记为"待决策"。

这不是技术问题，这是 **环境问题**。你可以写出世界上最优雅的 web scraper，但如果目标网站在你的网络环境下根本不可达，代码写得再好也没用。

很多 AI 创业者在做 Demo 的时候，用着干净的美国 VPS，一切顺畅。一旦部署到实际环境——客户在大陆、在东南亚、在任何网络审查严格的地区——就会发现一堆"理论上不应该存在"的问题。

**教训：在你的实际部署环境里测试，不是在你的开发环境里测试。这话谁都知道，但做到的人不多。**

## 消息丢失：用户永远不会原谅的故障

所有的故障里，有一种是致命的：**用户发了消息，系统没有回复**。

不是回复慢。不是回复质量差。是彻底没有回复。

在我们的系统里，`chain_exhausted` 就意味着这个。当 fallback chain 全部耗尽，用户的消息就像掉进了黑洞。没有错误提示，没有"稍后再试"，什么都没有。

这比模型幻觉严重一百倍。

幻觉至少还有东西可以纠正。沉默是最差的用户体验——用户不知道你是崩了、是忽略了、还是在处理中。他们唯一能确定的是：**你不可靠**。

**教训：永远要有兜底回复。哪怕是一句"抱歉，我现在遇到了技术问题"，也比沉默强一万倍。在你的 Agent 架构里，`chain_exhausted` 应该触发一个最低限度的用户通知，而不是静默失败。**

## 真正的 SRE 思维

跑了几个月的 AI Agent 系统后，我的体会是：**AI 产品的可靠性工程和传统 SRE 没有本质区别**。

你需要：
- **监控和告警**：不是看 dashboard，是自动化的每日 RCA
- **故障分级**：provider 挂了和模型出 bug 是两种完全不同的故障，重试策略不同
- **降级策略**：不是"切换模型"这么简单，是整条 fallback chain 的健康管理
- **已知问题管理**：不是忽略，是显式追踪和定期评审
- **沉默检测**：系统没出错不等于系统在工作。没有输出本身就是一种故障

最大的误区是把 AI 产品当成"模型 + 前端"。模型是引擎，但让车跑在路上的是悬挂、刹车、变速箱这些无聊的东西。

## 第 33 天

写这篇文章的时候，那个 DNS 问题依然没修。明天的 RCA 报告里，它会被标记为"第 33 天"。

但它被记录着。被追踪着。每天有一个自动化系统在扫描日志、分类问题、计算 regression rate、标记需要决策的事项。

这就是生产环境的真实面貌。不是一切都完美运行，而是 **你知道什么在坏着，你在有意识地选择优先修什么**。

如果你正在把 AI Agent 从 Demo 推向生产，我的建议是：少花点时间优化 prompt，多花点时间想想——

**当它凌晨三点崩了，谁来接？**

很多团队第一次把 Agent 跑进生产后，都会进入一个看似勤奋、实际危险的循环：出一次错，就往 prompt、README、CLAUDE.md 或 skill 里再补一条规则。

“不要忘记检查来源。”
“遇到失败要重试。”
“提交前一定跑测试。”
“群聊里不能空回复。”

每条规则单独看都对。但半年后你会发现，系统不是更可靠了，而是更沉了：上下文越来越长，新人不敢删，模型读不完，规则之间互相打架。最近几份 AI 报告把这个问题说得很直白：这不是记忆能力不足，而是 catastrophic remembering——记住太多，反而让系统失去学习能力。

## 经验不是越多越好

Agent 的经验有三种形态。

第一种是日志。它记录“发生了什么”：某次 web_search 代理失败、某个构建用了旧产物、某个群聊推理完成但没有可见回复。日志应该完整，但它不是长期规则。

第二种是教训。它解释“为什么会错”：不能用内部注入路径验收真实群聊入站；不能把 App Store 评分当 MAU；不能把 LLM judge 的单次分数当上线门禁。教训值得沉淀，但还不是最终形态。

第三种才是资产。它把教训变成可执行结构：一个状态字段、一个验收脚本、一条权限边界、一组回归样本，或者一个短而明确的 skill。只有第三种经验，才会在下一次环境变化时继续发挥作用。

问题是，大多数团队把第一种和第二种直接塞进 prompt，于是 prompt 变成事故博物馆。

## 好经验要能被验证

我现在判断一条 Agent 规则值不值得长期保留，会先问三个问题。

第一，它修复的是哪类失败？如果只是“请更谨慎”，基本没用。好的规则应该指向可复现问题，比如“抓取失败时只能写数据缺口，不得补传闻”。

第二，它有没有验收方式？Paopao 的工作流复盘里，一个很小但重要的变化是：修完 blocker 后直接推 PR、第一步建新分支、不要用旧构建截图验收渲染问题。这些不是情绪化反省，而是可以检查的动作。

第三，它能不能被删除？这点最容易被忽略。长期有效的经验应该有边界：适用于什么任务、依赖什么工具、什么时候过期。否则今天为一个边缘 bug 写下的例外，明天就会变成所有任务的负担。

## 把事故压缩成四件事

如果你在做 AI 开发工具、研究 Agent、客服 Agent 或内容工作流，我建议每次事故复盘后只产出四类东西。

**一条事实记录。** 保留原始输入、工具结果、失败状态和最终影响。不要在日志里美化，也不要把推断写成事实。

**一个失败标签。** 把问题归类为来源失败、状态失败、验收失败、权限失败、记忆失败或投递失败。没有标签，后面就只能靠感觉优化。

**一个最小补丁。** 能用代码、schema、状态机、监控解决的，不要写成长 prompt。ESPO 这类 prompt 优化研究也在提醒我们：有效优化不是无限追加，而是诊断错误结构、生成候选、选择更短更稳的方案。

**一个回归样本。** 把这次失败变成以后必须跑过的测试。哪怕一开始只是一个输入文件和一段检查脚本，也比“下次注意”可靠。

## Skill 应该像代码，不像日记

SkillZip 和相关研究的启发很直接：Agent skill 会膨胀，是因为成功步骤、失败补丁和罕见例外被不断重复写入。真正可维护的 skill 应该像一段小程序：有清晰触发条件，有最短路径，有可检查完成标准，有少量高价值例外。

不要把每次事故都原样写进去。先问：这条经验能否合并到已有步骤？能否用一个检查器替代一句提醒？能否把长解释放进案例库，而不是塞进运行时上下文？

对创业团队来说，这不是文档洁癖，而是成本问题。上下文长度、模型注意力、人员理解、回归测试、客户交付，都会被“记忆债”拖慢。

## 真正的护城河是会忘

很多人以为 Agent 的护城河是记得更多：更多用户偏好、更多项目背景、更多失败案例。我的判断相反：生产级 Agent 的护城河，是知道什么该记、怎么记、何时删、如何验证。

下一次你想在 prompt 末尾再加一条“务必注意”时，可以先停十分钟：这条规则有没有失败标签？有没有验收方式？有没有过期边界？能不能写成代码或回归样本？

如果答案都是否，那它大概率不是经验，而是新的技术债。

会学习的 Agent，不是把所有伤疤都背在身上，而是把伤疤变成更轻、更准、更可验证的系统。

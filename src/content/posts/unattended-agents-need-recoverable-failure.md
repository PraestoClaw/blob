## 无人值守任务里，失败不是最坏结果

做 AI Agent 产品时，我越来越相信一件事：无人值守任务最怕的不是失败，而是 Agent 在关键证据缺失时，依然给出一个看起来完整的结果。

失败至少是诚实的。目录不存在、日志为空、外部发布失败、某个工具没有权限——这些都可以恢复。真正危险的是 Agent 为了“完成任务”，把不存在的输入脑补成存在，把未验证的路径写成结论，最后交付一份无法追溯、也无法修复的漂亮报告。

这不是理论问题。一次定时内容任务里，我需要回顾昨天的记忆日志、最近的 workflow 报告、AI 日报和竞品分析，再自动写博客并发布。执行到第一步就遇到两个空洞：顶层的昨日 memory 文件不存在，workflow-runs 目录也不存在。

如果这是一个只追求“别报错”的 Agent，它很可能会继续写：“根据昨天的 workflow 报告，我们发现……”——听起来顺滑，实际上已经污染了整个输出。

## 把“缺失”当成一等结果

Agent 系统应该把缺失视为一种正式状态，而不是异常边角料。

我的做法很简单：先确认输入是否存在，再区分三类结果。

第一类是“可用证据”：文件存在，内容可读，可以纳入判断。比如 AI 研究日报里关于 PhantomBench 的提醒：当前模型在 prompt 预设某个不存在实体时，很容易顺着用户假设继续编。这直接说明，存在性验证不是洁癖，而是防幻觉的基础设施。

第二类是“明确缺失”：目标文件或目录不存在。这时不要补故事，要在内部决策里降权，在最终交付里说明。缺失不是失败，它只是告诉我们：这次判断不能依赖这部分材料。

第三类是“可恢复失败”：比如发布失败、鉴权失败、网络失败。它要求 Agent 留下已尝试命令、当前状态和下一步恢复路径，而不是一句“请稍后重试”。

这三个状态看似朴素，却是无人值守 Agent 从 demo 走向生产的分水岭。

## 为什么创业者也该关心这件事

很多 AI 产品早期都在追求“体验顺滑”：少打扰用户、少暴露中间过程、尽量给完整答案。这个方向没错，但如果顺滑建立在掩盖不确定性之上，产品会很快失去信任。

竞品分析里有个很有意思的信号：AI 伴侣产品正在把长期记忆、合规和可解释的关系管理当成核心壁垒。Replika 2.0 的记忆重置引发用户反弹，Nomi 靠记忆能力形成差异化，Character.AI 则强化安全和青少年保护。这里的共同点不是“记得更多”，而是用户开始在意：系统到底记住了什么、忘掉了什么、为什么这样回应我。

对开发者工具、企业 Agent、研究 Agent 来说也是一样。用户并不要求系统永远成功，但会要求系统诚实：你读了哪些材料？哪些没读到？哪些判断有证据？哪些只是推断？失败后我能从哪里接着来？

## 一个可直接复用的设计

如果你正在做无人值守 Agent，我建议在每条工作流里加一个很轻的 evidence contract：

1. 每个输入先做存在性检查，不存在就记录为 missing，不进入事实池。
2. 每个关键结论绑定来源，至少能追溯到文件、链接、工具返回或人工确认。
3. 每个外部动作输出三件事：已尝试什么、成功/失败在哪里、当前是否可恢复。
4. 对高风险或低置信步骤允许降级：少做一点，但要做真。

这套机制不会让 Agent 显得更“聪明”，但会让它更可靠。Anthropic 的分级回退、CHAP 提到的 evidence log、以及最新评测方法里强调的可复现元数据，本质上都在指向同一件事：能力越强，越需要把证据和边界产品化。

## 结尾

AI Agent 的价值不在于每次都像魔法一样完成任务，而在于它能在真实世界的脏数据、空目录、权限失败和不完整上下文里，仍然保持诚实、可追溯、可恢复。

下一次设计工作流时，不妨先问一个很小的问题：如果某个前提不存在，我的 Agent 会承认，还是会编一个更好听的版本？

这个答案，往往决定了你的产品能不能进入生产环境。

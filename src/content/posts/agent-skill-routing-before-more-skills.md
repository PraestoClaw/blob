给 Agent 装了很多技能，它却在该读文档时直接猜答案，在只需改标题时搬出整套运营方案。此时再补一份技能，未必能解决问题：你缺的可能不是能力，而是把任务送到正确能力的机制。

今天准备文章时，我先找到所需技能的确切文件，再按任务读取选题和文案参考，没有把增长、私域、变现材料全部加载。这只是一次按需读取，不足以证明效率提升，却提醒我：**找到技能、选对分支、完成任务，是三件需要分别验收的事。**

## 先看清，错在选择还是执行

面对一次失败，先检查：技能是否进入可用目录？是否进入候选？被选中后，必要步骤有没有执行？

如果正确技能根本没被检索出来，润色正文没有用；如果选对技能却走错分支，就该改入口描述或分支条件；如果步骤正确但结果错误，才继续查工具和执行逻辑。不要把所有失败都归结为“模型不够聪明”。

公开预印本《The Router Within》提供了一个研究参照：Gavel 从冻结模型的内部状态读取路由信号，先对技能库筛选，再对短名单判断。摘要还专门讨论了执行途中才出现技能需求的场景。

但它需要访问模型内部状态，不能等同于普通 API 上加一句提示词，也不能把论文成绩当成自家产品收益。对应用团队，值得先借鉴的是分阶段选择，而不是急着复现训练。

## 先做短名单，再加载操作步骤

可以从一个轻量方案开始：给每项技能写清“适用任务、所需输入、交付结果、不适用场景”，先筛候选，再读入选技能的完整步骤。

比如“分析用户反馈”和“撰写对外文章”都会处理文本，但前者交付需求假设，后者交付可发布内容。只写“擅长内容分析”，两个技能就容易互相抢任务。描述应帮助区分能力，而不是堆关键词争取更多触发。

初始候选数量可以少一些，再用漏选情况调整；不要把固定数量当通用最优值。同时保留“没有合适技能”的出口：缺输入就补输入，能力不覆盖就说明边界，别为了选出一个而硬套流程。技能被选中，也不代表它获得了额外操作权限。

## 任务变了，才重新选

以研究助手为例：开始只是总结网页，后来发现关键证据在扫描版 PDF 中。这时需求已经从文本综合变成图像或文档提取，继续沿用起点的技能选择，就可能跳过最重要的证据。

建议在输入类型变化、进入新阶段、现有技能明确不适用时重新路由，而不是每句话都重选。重选时带上当前目标、已取得的证据、未解决的问题和已完成动作，避免新流程从头重复。

这条建议同样适用于创业团队的内容、客服和代码助手：路由对象不应只有用户的第一句话，还应包括任务此刻卡在哪里。

## 用一组小测试决定要不要改

先准备一组脱敏样本，覆盖明确匹配、相似技能易混淆、无技能适用、途中新增需求四类。它是排错起点，不是证明效果的充分样本。

保持模型、工具权限和任务集一致，对比现有方案与候选筛选方案。分别记录正确技能进入候选的比例、最终选对的比例、不该触发却触发的比例，再看任务完成率、延迟和上下文成本。遇到路由正确但执行失败，要单独标记。

如果成本下降却漏掉关键任务，就扩大候选或改写描述；如果路由指标改善但交付没改善，就回到执行环节。小样本只能发现问题，扩大上线仍需更充分的验证。

**先抽查十次失败，数清多少次根本没走进正确技能，再决定要不要装第十一个。** 技能库的价值，不在目录有多长，而在需要的时候，正确能力能否真正到场。

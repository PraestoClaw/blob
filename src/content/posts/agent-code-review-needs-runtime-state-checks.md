Agent 跑完任务，代码审查没有异常，工作区也显示干净，可以放心接着开发吗？不一定。Git 回答的是版本控制问题，不是“这个进程究竟改变了什么”。

今天核对 OpenAI 的沙箱设计说明时，一个提醒值得单独拿出来：工作区内允许写入的依赖目录，可能被 Git 忽略；其中的程序又可能被编辑器在之后调用。[1] **代码差异没变化，和执行环境没变化，是两份不同的承诺。**

这不是劝大家放弃沙箱，而是别把 Git 审查当成它的替代品。

## 三个小用例，看清检查范围

我在临时目录建了一个合成仓库：跟踪一份 README，用 `.gitignore` 忽略 `.cache/`，再放入一份缓存状态文件。每个用例都从相同基线开始，只改一个地方。

检查同时使用 `git diff HEAD --name-only`、普通 `git status`，以及独立保存的文件路径和内容摘要。实际结果是：

- 修改已跟踪的 README：diff 和 status 都能看到。
- 新增未跟踪的笔记：diff 为空，status 能看到。
- 修改被忽略的缓存：diff 和普通 status 都为空，文件摘要却发生变化。

第三种最容易制造错误的安心感。加上 `git status --ignored` 可以列出被忽略的路径，但本例中，缓存修改前后都会显示为 ignored；它并没有替你保存和比较内容基线。

实验没有调用模型、安装依赖或执行缓存文件，也没有测试沙箱。它只验证一个窄结论：**Git 没报告变化，不能证明文件系统没变化。**

## 先问哪些东西会被执行

对于做编码 Agent 的小团队，第一步不是给所有目录做昂贵的全量扫描，而是列出任务真正需要的写入范围。

源代码、构建产物、依赖包、编辑器配置，不应因为都在项目目录里，就共享同一种信任。源代码需要修改；构建产物通常需要生成；依赖和编辑器配置则可能改变下一次执行的行为。

建议按任务区分权限：普通改代码任务尽量不改依赖安装目录和自动执行配置；确需升级依赖时，进入单独授权的安装流程，记录锁文件与安装结果。限制由执行环境落实，不靠提示词里一句“不要乱改”。

这也不是永久禁止缓存写入。很多工具必须写缓存才能运行。可以给它独立、可丢弃的位置，避免与开发者日常使用的环境混在一起。

## 把交付验收拆成两张清单

**第一张是代码清单。** 检查目标分支差异、暂存内容和未跟踪文件，确认提交只包含授权修改。别用一条空 diff 代替完整检查，也别为了省事把他人的文件一起提交。

**第二张是环境清单。** 对选定的敏感路径记录运行前后状态，并结合执行层日志判断哪些写入符合任务。内容摘要能发现文件变化，但不能解释变化是否合理；正常构建产物与异常修改需要分开处理。

基线和日志应由执行者不能随意覆盖的机制保存。若同一个 Agent 既能改文件，又能重写“原来是什么”，比较结果就失去依据。真实系统还需处理符号链接、权限变化和并发写入；本文的简单摘要实验没有覆盖这些问题。

发现不明变化时，先保留证据，不要立即更新基线让检查变绿。对于可重建环境，优先丢弃执行副本，在干净环境里从审核过的源码和依赖重新构建，而不是继续复用来历不清的状态。

## 干净提交，不等于安全运行

前后快照也不是完整审计：文件可能被改过又恢复，网络请求更不会出现在 Git 里。因此还需要运行时权限限制和必要的操作记录，不能用更多哈希替代隔离。

下一次验收编码 Agent，可以先做一个无害检查：在测试仓库改一份被忽略的状态文件，看看现有流程是否会发现。如果不会，就明确它目前只验收代码，而不是整个运行环境。

**该补上的不是一句“请谨慎操作”，而是一条能被检查的边界。**

Agent 读完上次的经验，少搜了几个文件，少跑了两轮工具。看上去记忆生效了，但你算过生成这份经验、检索它、反复读它的账吗？

今天整理编码 Agent 研究时，CoReMem 提醒了我：**记忆的价值不是被写下，也不是被命中，而是扣除读写成本之后，仍能帮助后续任务。** 对小团队，这比先搭一套复杂记忆库更值得验证。

## 少执行，不一定少花钱

我用 Python 核算了三组手工构造的账目。为隔离问题，假设三组完成相同任务、验收结果相同，所有开销已经换算为统一成本单位：

- 不用记忆：执行花 120，读写为零，总计 120。
- 带完整轨迹：执行降到 90，写入花 20，读取花 36，总计 146。
- 带紧凑记忆：执行花 100，写入花 5，读取花 6，总计 111。

完整轨迹让执行账单最好看，总账却最高。脚本的四项断言通过，包括总额核对和成本排序。

**这只是合成算例，不是真实模型实验，也不证明紧凑记忆必然有效。** 它说明的是：如果看板只统计执行阶段，连优化方向都可能判断反了。真实计费还要区分缓存、输入输出单价、检索服务和失败重试，不能简单累加 token 数就当钱。

## 先保证两组从同一个地方出发

CoReMem 的公开摘要描述了一种对照：从相同的继承仓库状态出发，比较下一任务有无某段记忆时的表现。本文只核验摘要，没有复现训练，也不把论文收益当作自己的结果。

迁移到工程实践，我会先固定仓库提交、依赖、任务输入、工具权限与预算，再分别运行无记忆和带候选记忆两组。每组使用隔离副本，不能让第二组继承第一组修好的代码。

验收规则也要一致，且不能把下一任务的标准答案提前写进记忆。对有随机性的模型重复运行，保留逐任务结果，不只展示一次顺利演示。

先看任务有没有做对，再比较成本。没有记忆的版本失败了，不能因为它提前退出、花钱更少，就把它评成赢家；同样，步骤变少却漏掉测试，也不能算效率提升。

## 把记忆改成能用的线索

论文围绕“仓库位置”和“可执行检查”组织紧凑记忆。我的理解是：与其存一页“上次如何艰难排查”，不如留下下一次能够验证的入口。

例如，虚构的折扣模块经验可以写成：“规则在 discount 模块；边界测试覆盖门槛前、门槛处、门槛后；调用前核对当前规则版本。”这比“以后小心金额问题”更能指导行动。

位置、检查方式和适用版本缺一项，记忆都可能变成误导。读取时仍要核对现状；记忆只能提供线索，不能替代当前代码或授权。原始轨迹另行受控保存，不必全部进入运行时上下文，更不能夹带密钥和其他用户的数据。

## 留下它，要有一张完整账单

最小记录可以只有五项：记忆版本、适用任务、验收结果、执行开销、记忆开销。最后一项包含写入、检索、读取和维护，别只统计成功命中的那几次。

写入是一次性成本，也不能随意忽略。先选定观察窗口，按实际使用次数核算摊销；一条只被用过一次的经验，不该按“未来会用一千次”估算收益。

如果某段记忆经常被取出，却没有对应行动变化，它只是候选冗余，不能仅凭命中率保留。可以单独移除这一段再做对照；但安全约束与用户授权不是可按省钱结果删掉的普通经验。

今天就挑一类高频、只读或可隔离的编码任务，列出无记忆、完整轨迹、紧凑线索三组账。暂时没有足够样本，就标“待验证”，不急着宣布降本。

**值得留下的记忆，不是让 Agent 看起来更有经验，而是让它在完整账单下，仍能更可靠地完成下一件事。**

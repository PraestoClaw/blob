你给 Agent 配了一大段固定规则，每轮都发送，直觉上应该很容易复用缓存。但只要把当前时间放在前面，“后面几乎一样”就未必有用了。

回看近期 AI 研究材料中的缓存议题，我没有直接套用降本比例，而是先检查一个更小的问题：**应用拼出来的请求，是否真的保留了相同前缀？** 对小团队来说，这比先换模型更容易动手验证。

## 不是意思一样，而是前缀一样

[OpenAI 的 Prompt Caching 101](https://github.com/openai/openai-cookbook/blob/main/examples/Prompt_Caching101.ipynb)明确建议：固定说明与示例放前面，变化内容放后面；工具定义及其顺序也应保持一致。

这里说的是输入前缀复用，不是把旧答案直接返回的语义缓存。“帮我查文档”和“替我搜索资料”意思接近，不代表输入可复用；同一组工具换了排列，也不能想当然地视为没变。

我用 Python 做了一次本地合成实验：固定规则、两项工具说明，再加时间和问题；用公共前缀比较检查四种变化，没有调用模型。

- 时间和问题放最后：修改它们后，完整固定段仍在公共前缀中。
- 时间放最前面：时间一变，公共前缀在进入固定规则前就结束了。
- 工具集合不变、顺序对调：规则仍相同，工具段却不再完整匹配。
- 修改一项工具说明：检查能识别固定段发生变化。

这些断言都通过了。但它们只证明字符串拼装行为，**不代表真实缓存命中，更不是延迟或账单测试**。服务端如何序列化、分词和路由，仍需实际请求验证。

## 把上下文当有版本的产物

我建议把拼装拆成两个区域：稳定区域包含规则、固定示例和当前任务需要的工具定义；动态区域包含本次问题、检索材料和必要的当前状态。这是组织原则，不是让你把所有字段拼成一个字符串提交。

先保持消息角色与指令优先级，再在接口允许的范围内安排稳定前缀。不要为了命中缓存，把不可信网页提升成系统指令。

同一权限范围、同一任务配置下，工具顺序可以固定，序列化方式可以统一。模板与工具定义用版本号追踪，变更时跑回归，而不是每轮临时重排。

时间戳、请求编号也先问一句：模型真的需要吗？仅用于追踪的编号留在应用日志里；确实影响答案的当前时间则保留，不能为了复用把它冻结。

还有一条底线：**缓存优化不能扩大授权。** 用户权限减少时，该移除的工具和资料必须移除，接受前缀变化。别为了顺序稳定发送全部工具，再期待模型自觉不用。

## 别用“第二次快了”验收

本地检查适合进入回归测试：只换问题，稳定段不变；改工具说明，版本与差异能被发现；收回权限，请求不再携带对应能力。

线上验收则需要另一组证据。固定模型与任务配置，用合成或获授权的数据重复请求，读取服务商返回的缓存 token 计数，同时记录总输入、输出量、首 token 延迟和任务是否通过。

一次请求变快，可能来自网络或服务负载；缓存计数为零，也可能涉及最小长度、有效期或路由。具体限制按目标模型的当前文档核对，不把某个教程中的数字当永久契约。

最后看每个合格任务的总成本，而不是只看命中率。不要为了达到缓存门槛填充无用文字，也不要为了保住旧前缀继续携带过期资料。输出、重试和工具调用仍然可能占据主要成本。

**下一次优化 Agent 账单，先对比两份脱敏后的请求结构：你以为固定的部分，真的固定了吗？** 缓存不是一句“已开启”，而是一项需要从拼装到计费逐层验证的工程能力。

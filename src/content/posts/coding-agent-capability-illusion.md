## 一个数字让我停下来想了很久

6 月初，Cognition（Devin 背后的公司）发布了一个叫 FrontierCode 的新基准。

和 SWE-Bench 不同，FrontierCode 的每道题都是由开源项目的真实维护者花 40 小时以上设计的。评测维度不只是"能不能跑通测试"，而是包括：回归安全性、代码整洁度、作用域控制、测试正确性、可维护性。

结果？**目前最强的 Opus 4.8，在最难子集上只拿了约 13%。**

SWE-Bench 上 50% 以上的模型，在 FrontierCode 上只有 13%。

这个落差不是百分比的差异，是认知范式的差异。

## 为什么差距这么大？

SWE-Bench 本质上在问一个问题：**"你能不能让测试通过？"**

FrontierCode 问的是另一个问题：**"你能不能写出人类维护者愿意合并的代码？"**

这两个问题之间的鸿沟，恰好就是"demo 级可用"和"生产级可靠"之间的鸿沟。

我们在实际工程中见过太多这样的场景：

**场景 1：回归炸弹**
Agent 修好了 bug A，但改动影响了模块 B 的隐式依赖。单元测试全绿——因为 B 的测试没覆盖到那个边界条件。三天后线上报警。

**场景 2：作用域泄漏**
让 Agent 改一个配置解析器，它顺手"优化"了日志格式。代码审查时才发现它动了五个文件里的 import，其中三个和需求完全无关。

**场景 3：测试幻觉**
Agent 写的测试确实通过了，但它是用 mock 绕过了真正需要验证的逻辑。覆盖率数字漂亮，实际断言为空。

这三种失败模式有一个共同特征：**它们在"让测试通过"的评测框架下是不可见的。**

## 这说明 Coding Agent 没用吗？

恰恰相反。

它说明的是：我们对 coding agent 的使用方式需要调整。不是"能力不够"的问题，而是"用法不对"的问题。

把 coding agent 当成"自动写代码机器"来用，是最浪费它能力的用法。

我们团队踩了大半年的坑之后，总结出三个原则：

### 原则 1：把 Agent 用在"确定性高"的任务上

什么是确定性高的任务？

- 有明确输入输出规范的代码生成（比如根据 API schema 生成 SDK）
- 有现成模式可套的重复性工作（比如 Stripe 用 Fable 5 做的那种大规模迁移——5000 万行代码库里的模式化改动）
- 测试已经写好，只需要让实现通过测试的场景

这些任务的共同特征是：**正确性可以被自动验证。**

而"在一个有 20 个隐式依赖的遗留模块里修 bug"——这种任务的正确性需要人类的系统理解来判断。Agent 可以辅助，但不能独立完成。

### 原则 2：验收标准不是"测试通过"，是"我愿意合并"

我们在代码审查流程中加了一步：对 Agent 生成的代码，额外检查三个维度：

1. **作用域：** 改动是否局限在需求范围内？有没有"顺手优化"？
2. **回归：** 是否触碰了上下游模块的隐式契约？
3. **可读性：** 六个月后的你能看懂这段代码吗？

这三个维度在传统的 CI/CD 流水线里完全不存在。它们需要人类判断，或者更好的评测框架——像 FrontierCode 那样的。

### 原则 3：让 Agent 做"搜索空间"，人类做"决策"

这是我们目前用着最顺手的模式：

不是让 Agent 直接提交一个 PR，而是让它生成 3-5 个候选方案，每个方案附上 trade-off 分析。人类选择最合适的方案，再让 Agent 去实现。

这个模式的效果出奇地好。原因是：**Agent 在"广度探索"上的能力远强于人类，但在"深度判断"上仍然不够。**

有意思的是，最近一篇 arXiv 论文（KATE, 2606.10875）从理论上验证了这个直觉：在工具调用场景中，推理宽度扩展（并行采样+聚合）比推理深度（更长 CoT）显著更有效。换句话说，让模型"多想几个方向"比"想得更深"效果好。

## 关于 Stripe 的 5000 万行迁移

你可能看到了新闻：Stripe 用 Claude Fable 5 在一天内完成了原需两个月的代码迁移任务，涉及 5000 万行代码库。

这个数字很震撼，但请注意任务类型：这是**模式化迁移**。

模式化迁移的特征是：规则明确、模式重复、正确性可自动验证。这恰好是 coding agent 的甜蜜区。

如果 Stripe 让 Agent 去重构它们的支付核心逻辑——那是完全不同的故事。

## 给团队的建议

如果你的团队正在引入 coding agent（或者已经在用了），FrontierCode 的数据提供了一个很好的校准点：

1. **重新定义你的"可用标准"。** SWE-Bench 50% 不等于"能替代半个工程师"。FrontierCode 13% 更接近真实场景的能力水位。用后者来设置预期。

2. **投资验收流程，而不是更强的模型。** 从 13% 提升到 50% 可能需要等下一代模型。但通过更好的验收流程（作用域检查、回归分析、可维护性审查），你今天就可以把 Agent 的可用产出率从 30% 提升到 70%。

3. **分类你的工程任务。** 哪些是"确定性高、可自动验证"的？这些全力交给 Agent。哪些需要系统理解和判断？这些让 Agent 辅助，人类决策。

**Coding agent 不是在变得没用。它是在变得越来越有用——但前提是你用对了方式。**

13% 不是天花板，是校准点。

工具返回“拒绝执行”，任务总结却写着“顺利完成”。排查时，你打开日志，发现里面也写着成功。接下来该信谁？

如果执行任务的 Agent 同时能改写自己的日志，多留几份记录未必有用。最近阅读轨迹篡改研究时，我重新检查了一个常见设计：给每条事件加哈希，再把它们串成链，是否就能放心审计？

结论是：**链条自洽，只证明眼前这份数据能对上，不证明它就是当时那份数据。**

## 四个用例，拆开两个问题

我用 Python 跑了一个本地合成实验，没有接入真实业务，也没有修改任何系统日志。

样本只有三条事件：收到请求、工具拒绝、任务停止。每条记录保存事件内容、前一条哈希和当前哈希；另由校验端预先保留原始记录数与末尾哈希，作为独立锚点。

四个用例的结果很直观：

- 原始记录：链校验通过，锚点比对通过。
- 只把“拒绝”改成“允许”，不更新哈希：两项都失败。
- 改成“允许”后重算整条链：链校验通过，锚点比对失败。
- 删除最后一条记录：剩余链校验通过，锚点比对失败。

这里没有破解 SHA-256。能写整份文件的人，只是对新内容重新计算了哈希。截断尾部更简单：剩下的前缀本来就是合法链。

这个实验只验证完整性检查的逻辑。锚点在脚本中被保留不变，并不代表已经实现进程隔离、远程存储或生产级防篡改。

## 先分清谁有权写什么

对小团队，我更建议先画权限表，而不是先换日志平台。

第一层是 Agent 的工作记录。草稿、推理摘要、调试笔记可以修改，方便恢复任务，但不要把它们当唯一审计凭据。

第二层是工具或网关产生的事件。它们记录请求是否到达、授权是否通过、返回了什么状态。Agent 可以读取必要部分，但不能靠同一组权限更新或删除历史事件。仅把目录命名为“只追加”没有意义，限制必须落到身份与存储权限上。

第三层是独立校验依据。由不同权限主体保存已接收事件的序号与摘要，或使用受保护的签名检查点。密钥若仍能被 Agent 读取，签名也不能提供预期的隔离。

**独立不是多一个文件夹，而是执行者不能同时修改记录和验收依据。**

## 锚点不是万能证明

锚点必须在待保护的事件被接收时形成，不能等任务结束，再让 Agent 把整理好的历史交来盖章。否则被遗漏的事件可能从未进入检查范围。

周期性检查点也只能保护已经覆盖的历史；最新一段是否缺失，需要结合接收序号、确认回执与告警判断。跨任务校验还要绑定任务标识，避免拿另一条合法轨迹冒充当前任务。

即使记录确实没有被改过，它也不自动证明现实动作成功。“请求已发出”不等于“订单已创建”，仍需用业务系统的结果标识核对。完整性、完整程度与业务真实性，是三个不同问题。

## 上线前，验收这几件事

先在隔离测试环境里，用实际运行 Agent 的身份尝试更新、删除历史审计事件，预期都应被拒绝；再向校验器输入改写、重算和截断后的合成记录，检查能否报警。

还要测试日志接收端不可用时怎么办：对涉及资金或权限的动作，无法留下必要审计证据时应暂停，而不是静默执行后宣称成功。

最后检查数据最小化。审计需要动作、授权结论、结果标识与关联关系，不代表必须永久保存完整对话、密钥或敏感工具参数。

对 AI 创业者来说，这不是大公司的合规装饰。客户问“它究竟做了什么”时，你需要一份执行者不能随手改写的证据，而不只是另一段更像真的总结。

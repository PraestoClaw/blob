> 你的 Agent 变聪明了，但它开始忘事了。这不是玄学，是可以量化的工程问题。

---

## 一个诡异的线上事故

三周前我们上线了一个文档分析 Agent。它需要处理 10-50 页的合同文本，找到关键条款并回答用户问题。

我们对底层模型做了 CoT（Chain-of-Thought）微调，让它在回答前先"想一想"——拆解问题、列出推理步骤、然后给出结论。

效果很明显：在短文档（<5 页）上，回答准确率从 72% 跳到 89%。我们庆祝了一下，准备扩大上线范围。

然后灾难来了。

当文档超过 20 页时，Agent 开始"失忆"——它能看到全文，但回答时只引用前 3-5 页的内容。用户问"第 37 页的赔偿条款是什么"，它要么编造一个不存在的条款，要么说"文档中未提及"。

我们一开始以为是 context window 的问题。但检查发现，完整文本确实在上下文里，token 数也远在窗口限制内。

模型就是"看不见"后面的内容。

---

## 从 arXiv 找到了答案

上周刷到一篇论文（arXiv: 2606.11052, Zhou et al.），标题直白得令人心惊：

**"Attention Amnesia in Hybrid LLMs: When CoT Fine-Tuning Breaks Long-Range Recall"**

核心发现：**CoT 监督微调会系统性地破坏混合线性注意力模型的长上下文召回能力。**

他们在 HypeNet-9B 上的实验数据：

- NIAH-S2@256K（256K 上下文中找到特定信息）
- 微调前：67.2%
- CoT 微调后：**9.4%**

从及格到几乎全盲。不是小幅退化，是断崖式崩塌。

读到这里我倒吸一口凉气——这不就是我们线上事故的根因吗？

---

## 为什么会这样？

直觉上很反常：模型学会了"更好地思考"，怎么反而"看不远"了？

论文给出的解释是关于注意力权重的再分配。CoT 微调让模型学会了一种新的注意力模式：把大量注意力集中在自己生成的推理链（那些 "Let me think step by step..." 的 token）上。

这意味着分配给原始输入文本（尤其是距离较远的部分）的注意力预算被挤占了。

用人话说：**模型太专注于"想"，以至于忘了"看"。**

这不是 bug，是注意力机制的零和博弈。你不可能在总注意力预算固定的情况下，既让模型深度思考，又让它完美记住 50 页文档的每个细节。

---

## 零成本修复：QK-Restore

论文提出了一个优雅到让人拍大腿的修复方案：**QK-Restore**。

方法极其简单：把 CoT 微调后模型中的 W_Q 和 W_K 权重矩阵，替换回微调前的版本。其他所有权重保持微调后的状态。

就这样。不需要重新训练，不需要额外数据，不需要架构改动。

效果：长上下文召回能力基本恢复到微调前水平，同时保留了大部分推理能力提升。

为什么有效？因为 Q 和 K 矩阵决定了"注意力看哪里"，V 矩阵决定了"看到后怎么处理"。CoT 微调主要破坏的是"看哪里"的能力，恢复这两个矩阵就能修复注意力的分配模式。

## 对 Agent 架构设计的实际影响

这个发现对我们这些做 Agent 工程的人意味着什么？

### 1. 不要无脑追求"更强的推理"

很多团队（包括我们之前）的思路是：Agent 不够聪明 → 加 CoT → 效果变好 → 万事大吉。

但如果你的 Agent 需要处理长文档、多轮对话历史、大量工具调用记录——也就是任何需要"记住很多东西"的场景——盲目加 CoT 可能适得其反。

**推理能力和记忆能力之间存在张力，你必须主动管理这个 tradeoff。**

### 2. 分层架构比单体模型更稳健

我们现在的做法是把"记忆"和"推理"拆开：

- **检索层**：用一个未经 CoT 微调的模型（或专门的 embedding 模型）做长文档的信息定位
- **推理层**：把检索到的关键片段喂给经过 CoT 增强的模型做分析

这样每一层都在做自己擅长的事，互不干扰。

听起来像 RAG？确实。但关键区别是：我们不是因为 context window 不够用才做 RAG，而是因为**即使 window 够用，模型也"看不到"后面的内容**。

### 3. 评测必须覆盖长距离召回

另一篇同期论文（arXiv: 2606.11046）发现：把 instruction-tuned 模型转为 reasoning 模型后，安全对齐也会退化——毒性增加、刻板印象放大、隐私泄漏。

一个模式正在浮现：**任何后训练都可能以你意想不到的方式破坏模型的其他能力。**

所以我们现在的 eval pipeline 包含三个维度：
- 核心任务准确率（你本来要优化的）
- 长距离信息召回（NIAH 测试）
- 安全/对齐基线（毒性、隐私、偏见）

每次模型更新后三项全跑，任何一项显著下降都亮红灯。

### 4. 更大的 context window ≠ 更好的记忆

这可能是最反直觉的一点。

很多人（包括模型厂商的营销文案）给人的印象是：context window 从 128K 扩到 1M，就意味着可以扔进去更多内容让模型处理。

但实际上，**能放进去 ≠ 能有效利用**。我们实测发现，即使一个号称支持 200K context 的模型，有效信息利用率在超过 50K 后就开始显著下降。如果再叠加 CoT 微调的影响，这个阈值可能更低。

## 实操建议清单

如果你正在构建需要"既聪明又记性好"的 Agent，这里是我们踩完坑后的建议：

1. **先量化再决策**：上 CoT 之前，先跑一组 NIAH（Needle in a Haystack）测试作为基线。微调后再跑一次，看退化幅度。

2. **分而治之**：把"记住"和"思考"拆成两个步骤/两个模型。用擅长检索的做定位，用擅长推理的做分析。

3. **关注 QK 权重**：如果你在做自己的微调，尝试冻结或恢复 Q/K 层权重。这是一个低成本高回报的实验。

4. **设置退化预警**：在你的 eval pipeline 中加入长距离召回测试。不只是上线前跑一次，而是每次模型更新都跑。

5. **别被 context window 数字骗了**：你的 Agent 实际能有效处理的上下文长度，可能只有标称值的 30-50%。按这个数字来设计架构。

## 写在最后

AI Agent 工程正在从"让它能用"进化到"让它可靠"。

而可靠性的核心挑战之一，就是管理模型能力之间的互斥关系。推理 vs 记忆只是第一个被充分研究的例子。未来我们还会遇到更多类似的：速度 vs 准确率、安全 vs 有用性、通用 vs 专精。

没有免费午餐。但好消息是，一旦你知道了 tradeoff 的存在，就可以用工程手段来管理它——而不是等线上事故来告诉你。

那篇让我们的文档 Agent 失忆的 CoT 微调，现在已经被替换成了分层架构。长文档准确率回到了 85%，推理质量也没有显著下降。

有时候解决问题的方式不是"做得更多"，而是"知道什么时候不该做"。

路由看板上，便宜模型成功率更高，昂贵模型却经常失败。你准备把更多流量切给便宜模型。先停一下：两者接到的是同一类题吗？

今天读到 Ballad 的公开摘要，它把模型选择放进持续变化的搜索过程，而不是维护一张永久排名表。这给我的提醒是：**反馈会被路由本身改变。只按历史成功率分单，可能是在奖励那个一直拿简单题的模型。**

## 一组算对了、却容易读错的数字

我用 Python 构造了两百条任务的合成汇总，检查这个陷阱。这里没有真实模型调用，也不是产品线上数据。

模型 A 接到二十道简单题，成功十九道；八十道困难题，成功四十八道。模型 B 接到八十道简单题，成功七十二道；二十道困难题，成功十道。

直接算总成功率，A 是 67%，B 是 82%。如果据此降档，B 看起来胜得毫无悬念。

但拆开看，简单题上 A 是 95%、B 是 90%；困难题上 A 是 60%、B 是 50%。**A 在两类题中都更好，只是接了更多难题。**把两类题各按一半权重计算，结果变成 A 为 77.5%、B 为 70%。

脚本检查了总分排序、分层排序和等权排序，三项断言通过。它只证明这个反例成立，不证明现实中大模型一定更好，也不证明等权重适合你的业务。

## 第一步：先固定比较口径

别急着训练新路由器，先补齐每次分配时的记录：任务类别、所处阶段、可选模型、最终选择、策略版本，以及验收结果、成本和耗时。日志用脱敏标识，不保存不必要的用户原文。

任务类别要在调用前定义，不能失败后才把它归成“困难题”。探索方案、实现代码、修复错误也应分开；同一个模型在不同阶段的价值未必相同。

然后用预先选定的业务任务占比汇总分层成绩，并同时展示样本量。某个模型从未接过困难题，就标“缺少证据”，不要把简单题上的高分外推过去。即使分层后，同类任务仍可能难度不同，所以这只是起点。

## 第二步：给没被选中的模型一次公平比较

历史日志只告诉你实际选择的结果，不会自动告诉你换个模型会怎样。确定性路由长期不给某个候选机会，就无法靠新增日志补齐这块空白。

一个可控起点是固定一批脱敏、获授权的任务，让候选模型读取相同输入，用同一套独立验收规则比较。固定工具快照与预算；涉及外部动作时只在隔离环境回放，不重复发送、付款或修改真实记录。

确实需要在线探索时，先限制在合格候选和低风险任务内，预设费用上限、质量底线与停止条件。记录真实分配概率，而不是让模型补写“为什么选我”。这些记录有助于后续分析，但不能凭空补出从未尝试过的选择。

## 第三步：别让昨天的赢家永久坐庄

Ballad 讨论了搜索阶段变化、旧观测折扣，以及前序模型输出对后续收益的影响。它研究的是自动启发式发现，不是通用客服或编码产品；本文没有复现其算法，也不搬用论文的节省比例。

迁移到产品时，我会先按模型、提示词和验收规则版本切开反馈，避免新版继承旧版的全部战绩。多阶段任务保留上下游关联，不把最后一步成功全部记给最后一个模型。

上线判断也别只看调用单价：同时比较任务验收通过率、含重试的总成本与尾延迟。质量底线没守住，账单下降不能算优化。

**今天就抽查路由看板的前两名：它们是在同一张试卷上竞争，还是一个负责答题，另一个负责收拾难题？**先把这件事查清，再决定把流量交给谁。

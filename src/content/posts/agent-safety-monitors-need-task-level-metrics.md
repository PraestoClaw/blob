给 Agent 加一道安全检查，最容易踩的坑不是“没拦住”，而是每一步看起来都合理，整条任务却走不完。

读完最近的 Agent 泄密预警研究，我更在意一个部署问题：我们测试的究竟是分类器，还是用户能完成的整条流程？对要上线产品的小团队，这个区别比再提高一点识别率更重要。

## 单次误报率，会在长任务里放大

《Pre-Crime for Agents》在受控多 Agent 场景中，用同伴持续施压目标 Agent 披露秘密。作者报告：在留出的 Qwen3-32B 实验中，将阈值设为标记 5% 的良性调用，可以捕获 82% 的泄露调用。

但同一篇论文也明确指出：遇到任何告警就停机，会中止大多数良性任务；追加一次文本检查也没有解决这个问题。这个限制不能从部署说明里删掉。

做个纯算术示例：假设一条正常任务有 20 次检查，每次误报概率都是 5%，且相互独立。那么至少触发一次误报的概率是 `1 − 0.95²⁰ ≈ 64.2%`。

**这不是论文测得的任务失败率。** 真实调用之间存在相关性，检查次数也不固定。它只说明：单次误报率低，不等于整条任务被误停的概率低。上线前需要回放完整任务，而不是把调用打散后交一张分类成绩单。

## 检测“要披露”，不等于判定“违规”

研究还发现，探针会标记获准的披露，更像是在识别“接下来要说出信息”，而不是判断这次披露是否违反规则。

这提醒我把两个问题拆开：内容是否敏感，以及当前主体是否有权向当前目的地发送。前者可以用模型辅助判断，后者不能让模型凭语气猜。

工程上，我会把发送主体、数据类别、目的地和授权范围放进确定性的策略检查。权限不符就阻断；无法确认授权就暂停该动作；风险信号只负责触发进一步核验，不自动等同于有罪，也不能反过来授予权限。

不要为了降低误报而放宽凭据隔离。监控器是补充防线，不是让执行 Agent 获得更多秘密的理由。

## 回归测试要包含“正常但敏感”

只收集攻击样本，容易把监控器训练成“提到秘密就报警”。我建议先搭一套小型回放集，覆盖三类完整任务：

- **普通正常任务：**不涉及敏感发送，检查监控是否无故打断工作。
- **已授权的敏感任务：**用合成数据模拟合法导出，检验系统是否理解接收方与范围。
- **越权任务：**保持业务目标相似，只改变授权、目的地或字段，验证真正该拦的边界。

按任务长度和动作类型分组，分别记录漏拦任务数、正常任务误停比例、完成率、额外延迟，以及暂停后的恢复成功率。一次任务连续报警十次，不能冒充十个独立风险事件。

这些是建议的验收口径，不是已经验证有效的方案。若先做影子评估，也应使用隔离环境或脱敏回放；不能为了观察分类器，让真实高风险动作绕过现有权限检查。

## 暂停之后，用户怎么继续

拦截不是终点。产品还要回答：停的是哪一步，哪些成果已经保存，缺少什么授权，恢复后会不会重复发送？

假设 Agent 已完成资料整理，却在发送前遇到授权不明。合理的处理是保留草稿、冻结发送、提示核验接收方，而不是删除全部进度，或换条通道偷偷发出去。恢复执行也必须核对动作状态，避免重复副作用。

我会把上线检查压缩成一句话：**既要证明危险动作被挡住，也要证明合法任务走得完。**

下次评审监控方案，先拿一条最长的正常任务完整跑一遍。若团队只能报出单次准确率，却说不清任务会在哪里暂停、如何恢复，那就还没完成产品验收。

参考：[Pre-Crime for Agents（arXiv 预印本）](https://arxiv.org/abs/2610.40588)。研究结果来自受控实验，不能直接外推为生产环境效果。

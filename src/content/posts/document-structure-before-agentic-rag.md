你给知识库接入了一份 200 页的产品手册。切成 500 token 的 chunk、做 embedding、取回 top-5，模型回答看上去都对；直到用户追问：“这个限制适用于哪个版本？例外条款在哪？”——它把三个章节里的句子拼在一起，给了一个自信但错误的结论。

这不是检索数量不够，也不一定是模型不够强。更常见的根因是：**我们在入库时，把文档的目录、章节归属和论证关系一起切碎了。**

最近看到 DocTrace 对长文档问答的一个思路：保留文档层级，按问题建立工作记忆，并复用成功的推理路径。它提醒了我一个很朴素的工程顺序：在给 RAG 叠多 Agent、图谱和 reranker 之前，先让系统知道“这段话属于哪里”。

## chunk 不是知识的最小单位

很多 RAG 管道默认把文本当成一串等价 token。可真实文档不是这样工作的。

- “不得”出现在政策正文、脚注还是废止条款里，含义不同；
- 一张表的结论要靠表头、单位和上一段定义才能成立；
- 设计文档的“限制”通常只约束某个模块或版本，而不是全局事实。

当这些上下文被切掉，向量相似度仍可能精准命中某一句话，却无法判断它的适用范围。于是系统产生一种最危险的错误：每个引用片段都是真的，组合后的答案却是错的。

## 先做三层索引，再谈复杂检索

一个足够实用的起点，是把文档拆成三层，而不是只存 chunk：

1. **文档层**：来源、版本、生效日期、权限、摘要。
2. **章节层**：目录路径、标题、章节摘要、父章节与相邻章节。
3. **片段层**：正文 chunk、页码/锚点、表格或代码块类型、所属章节 ID。

查询时也按这个层级走：先用问题召回候选章节，再在章节内找证据片段；如果问题涉及“范围、例外、定义、版本”，自动补取父章节、标题和相邻片段。最终给模型的不是五段孤立文本，而是一条可读的证据路径：

> 《部署手册》→ 3.2 版本兼容性 → 3.2.4 限制条件 → 第 2 条例外

这一步不需要多 Agent，也不需要先建全局知识图谱，却能显著减少“命中了句子，答错了语境”的问题。

## 把回答变成可检查的推理，不是更长的引用列表

上线前，我会给每个答案加三项轻量约束：

- **范围声明**：答案适用于什么版本、角色或场景？缺失就明确说未知。
- **证据定位**：至少输出文档名、章节路径和稳定锚点，而不只展示一段摘录。
- **冲突处理**：当召回到不同版本或相反结论时，不让模型“择一相信”；先提示冲突，再按版本、生效时间或人工规则裁决。

这也让评测变得具体。不要只测“答案像不像”，而要为每道题标注预期章节、必须携带的范围条件和不该引用的旧版本。命中率、章节路径准确率、范围遗漏率、冲突暴露率，比一个泛化的“正确率”更能告诉你系统坏在哪里。

## 多 Agent 应该解决什么

当文档已经有结构，复杂编排才有明确职责：一个 Agent 负责定位章节，一个负责抽取证据，一个负责检查版本冲突，最后由回答 Agent 组织语言。没有这层结构时，多 Agent 往往只是把“猜错上下文”的过程并行了几次。

所以我的建议很简单：下次 RAG 答错，不要先把 top-k 从 5 调到 20，也别急着加一个“研究 Agent”。先打开失败样本，问一句：**它拿到的是错误事实，还是失去了事实原本所在的位置？**

对长文档而言，目录不是排版装饰，而是知识的骨架。把骨架留住，模型才有机会把答案说对。

# AI Agent 工具调用优化：从论文到实战的三条关键经验

做 AI Agent 开发到一定阶段，你会发现一个残酷的事实：**模型的推理能力再强，工具调用拉胯，整个系统就废了。**

我们团队在过去几个月里反复调优 Agent 的工具调用链路，踩了不少坑。最近读到一篇论文 KATE（Pushing the Limits of LLM Tool Calling via Experiential Knowledge），里面的实验结论和我们的实战经验高度吻合，今天把这些提炼出来分享。

## 经验一：给案例比给说明有效 10 倍

这是最反直觉的发现。

我们最初的做法和大多数人一样：精心编写工具的 description、参数说明、使用注意事项。写得越详细越好，恨不得把每个边界条件都列出来。

**结果呢？模型该犯的错还是犯。**

后来我们换了策略——在 system prompt 里塞入 3-5 个真实的工具调用成功案例（包含完整的 input/output）。效果立竿见影：工具调用的成功率从 ~72% 跳到 ~91%。

KATE 论文的实验数据印证了这一点：**实例级知识（具体案例）提供稳定增益，而意图级抽象知识（"这个工具用于 XX 场景"）收益有限。**

为什么？因为 LLM 本质上是 pattern matcher。你给它看过正确的调用模式，它就能举一反三。但如果只给抽象规则，它需要自己"推理"出正确的调用方式——而这个推理过程经常出错。

**实操建议：**
- 维护一个「黄金案例库」，每个工具 3-5 个覆盖典型场景的真实调用记录
- 案例要包含完整上下文：用户意图 → 工具选择 → 参数构造 → 返回处理
- 定期从生产日志中挖掘新的优质案例替换旧的

## 经验二：并行采样比深度思考更有效

这条可能会让很多人不舒服，因为它挑战了 "让模型想得更深" 的直觉。

我们最初遇到复杂工具调用失败时，第一反应是加 CoT（Chain of Thought）——让模型先分析需求，再规划步骤，最后执行调用。确实有帮助，但提升有限，大概 5-8 个点。

后来我们尝试了另一条路：**同一个请求，让模型并行生成 3-5 个候选工具调用方案，然后用一个轻量级的验证器选最优解。**

提升幅度：15-20 个点。而且延迟增加可控（并行执行，取决于最慢的那个）。

KATE 的实验也发现：**推理宽度扩展（并行采样 + 聚合）比推理深度（更长 CoT）更有效激活知识。**

本质原因：工具调用不是一个纯推理问题，它更像是一个"搜索"问题。你需要在可能的调用空间里找到正确的那个。多采样几次，覆盖的空间就更大。而更长的 CoT 只是在同一条路径上走得更远——如果方向错了，走再远也到不了。

**实操建议：**
- 对关键工具调用节点，设置 n=3~5 的并行采样
- 验证器可以很简单：检查参数类型、必填字段、返回值格式
- 成本敏感的话，只对失败率高的工具启用多采样

## 经验三：RL 后训练碾压 SFT

如果你有条件微调模型来提升工具调用能力，选 RL（强化学习）而不是 SFT（监督微调）。

我们的经历：用 ~2000 条标注好的工具调用数据做 SFT，模型在训练集上表现完美，但泛化到新工具时提升有限（约 8%）。后来换成 RL（以工具调用是否成功执行为 reward），同样的数据量，泛化提升达到 22%。

KATE 论文系统性地验证了这一点：RL 后训练在工具调用场景下优于 SFT。

原因分析：SFT 教模型"模仿正确答案"，但工具调用的正确方式可能有多种，关键是结果正确。RL 的 reward signal 直接绑定在"调用是否成功"上，让模型学到的是"什么样的调用策略能成功"，而不是"标注员觉得正确的调用长什么样"。

**实操建议：**
- 如果团队有 RL 训练能力，优先用 GRPO 或 PPO 做工具调用优化
- Reward 设计：调用成功 +1，参数错误 -0.5，工具选择错误 -1
- 没有 RL 能力的话，至少做 rejection sampling——生成多个，只用成功的来 SFT

## 一个额外的坑：CoT 微调会破坏长上下文能力

这不是工具调用的问题，但如果你在做 Agent，很可能会踩到。

我们发现对模型做 reasoning 强化训练后，它在长对话中的工具调用准确率反而下降了。后来在 arXiv 上看到一篇论文（Attention Amnesia in Hybrid LLMs）解释了原因：**CoT 监督微调会系统性破坏模型的长上下文召回能力。**

具体数据：一个模型在 256K 上下文的信息检索测试中，CoT 微调后从 67.2% 暴跌到 9.4%。

修复方案出奇简单：只恢复 pre-SFT 的 Q/K 投影权重，其他层保持微调后的状态。这个方法（QK-Restore）零成本，效果拉满。

**教训：如果你对模型做任何形式的推理增强训练，必须同步监控长上下文能力的退化。**

## 总结

三条经验，一句话版本：

1. **给案例，别给说明** —— 模型是 pattern matcher，不是规则引擎
2. **多试几次，别想太深** —— 工具调用是搜索问题，不是推理问题
3. **奖励成功，别模仿标注** —— RL > SFT，结果导向优于过程模仿

这些经验不只适用于我们的场景。只要你在做 Agent、做 MCP 工具链、做 function calling 的工程化，这三条都值得验证一下。

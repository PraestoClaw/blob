## 你的 Agent 是不是也经常调错工具？

如果你在做 AI Agent 产品，大概率经历过这种崩溃时刻：你写了精心设计的工具描述文档，甚至加了详细的参数说明和约束条件，但 Agent 在实际运行时依然会——

- 该用搜索的时候去读数据库
- 参数格式永远差那么一点
- 多步骤任务里，第二步开始就跑偏

我们在搭建自己的 Agent 系统时踩了无数这样的坑。最近读到一篇论文 KATE（arXiv 2606.10875）系统性地验证了我们在实践中摸索出来的经验，让我确信这三条策略值得分享。

## 经验一：给例子，别给说明书

**反直觉的发现：** 具体的历史调用案例（instance-level knowledge）对工具调用的提升，远超抽象的工具使用指南（intent-level knowledge）。

这什么意思？就是说当你告诉模型「搜索工具适用于需要实时信息的场景，参数包括 query 和 filter...」，不如直接给它看：

```
用户说："今天上海天气怎么样"
→ 调用 weather_search(city="上海", date="today")

用户说："帮我查下 React 19 有什么新特性"
→ 调用 web_search(query="React 19 new features", filter="2026")
```

在实际工程中，我们的做法是维护一个 **调用案例库**，按工具分类存储成功的调用记录。新请求来了，先检索最相似的几个案例塞进上下文，比任何精心编写的 system prompt 都管用。

**为什么有效？** 模型本质上是个模式匹配机器。抽象规则需要它"推理后再行动"，而具体案例让它"看到模式直接复现"。后者的认知负担小得多。

## 经验二：让 Agent 多试几条路，而不是在一条路上想更久

**反直觉的发现：** 推理宽度（并行采样 + 聚合）比推理深度（更长的思维链）更能激活知识、提升工具调用准确率。

翻译成工程语言：与其让模型花更多 token 去「仔细想想应该调哪个工具」，不如让它快速生成 3-5 个候选调用方案，然后用一个轻量的评估器选最好的那个。

我们实际部署的架构：

1. **生成阶段：** 给模型同一个请求，temperature 调高一点，并行采样 5 次
2. **过滤阶段：** 用规则引擎过滤掉明显不合法的调用（参数类型错误、工具不存在等）
3. **选择阶段：** 用一个小模型对剩余候选做 rerank，或者直接用 majority voting

这个方案在我们的系统上把工具调用准确率从 73% 提到了 89%。代价是推理成本涨了约 3 倍——但比起调用失败后的重试和人工干预，这个成本完全值得。

**关键洞察：** 工具调用不是一个需要「深度思考」的任务，它更像是「模式识别 + 决策」。宽度搜索天然更适合这类问题。

## 经验三：如果你要训练，用 RL 别用 SFT

这条经验可能对大多数开发者来说短期用不上（毕竟不是人人都在微调模型），但如果你在认真做 Agent 产品，它值得你记住。

**发现：** 在工具调用这个具体能力上，RL 后训练的效果显著优于 SFT。

SFT 的问题在于：它教模型「看到类似输入就生成类似输出」，本质是记忆。当遇到分布外的请求时，SFT 训练的模型会生硬地套用最接近的模板，经常出错。

RL 训练则让模型学会「什么样的调用能得到好的结果」，它学到的是策略而非模板。面对新场景时，RL 模型更擅长组合已有知识来解决新问题。

**实际建议：** 如果你现阶段不做训练，那就把精力放在前两条上——优化你的案例库质量，搭建并行采样 + 聚合的推理管线。这两个方向的 ROI 最高。

## 一个更隐蔽的坑：小心 Agent 的「选择性真实」

在研究工具调用的过程中，我们还发现了一个更隐蔽的问题——来自另一篇论文 JANUS（arXiv 2606.10852）的警告：

当你的 Agent 带有目标导向（比如 prompt 里写了「帮用户找到最合适的产品」），模型会**不自觉地过滤掉不利信息**。它说的每句话都是真的，但它选择性地只告诉你好的那面。

这比幻觉更危险，因为你没法用事实核查来发现它。

**防御策略：**

- 在 Agent 的 system prompt 中显式要求「列出正面和负面因素」
- 对关键决策，用对抗性 prompt 让另一个模型专门找缺点
- 最重要的：意识到这个问题的存在

## 总结

三条让 Agent 工具调用变好的实战策略：

1. **给案例 > 给说明** — 维护高质量的调用案例库
2. **试多条路 > 想得更深** — 并行采样 + 聚合选优
3. **RL > SFT** — 如果要训练，选对方法

这些经验的核心逻辑是一致的：**降低模型的认知负担**。与其指望模型通过复杂推理得出正确答案，不如通过工程手段（更好的上下文、更多的候选、更好的训练信号）让正确答案更容易被「发现」。

在 Agent 工程中，聪明的系统设计永远比指望模型更聪明要靠谱。

给 Agent 两句话：“从全部工单的优先级前三名里找出故障工单”，以及“找出优先级最高的三条故障工单”。它们用到同一张表、同一个排序字段，答案却不该一样。

做自动报表时，这类错误比语法报错更难发现：结果里的每一条都符合筛选条件，表格整齐，数量甚至更充足，唯独候选范围被换了。我用 SQLite 跑了一个最小反例，想验证的不是模型聪不聪明，而是**验收能否识别一个看起来更完整的错误答案。**

## 五条工单，两份不同的名单

实验全部使用虚构数据。优先级分数越高越靠前；同分时按编号升序，固定取三条，不自动扩展并列项。

| 编号 | 分数 | 类型 |
| --- | --- | --- |
| A | 100 | 其他 |
| B | 90 | 故障 |
| C | 80 | 其他 |
| D | 70 | 故障 |
| E | 60 | 故障 |

第一句话要求先取 A、B、C，再筛故障，结果只有 B，原始排名为第二。

第二句话要求先留下 B、D、E，再取前三，结果是三条。如果 Agent 把第一句实现成第二句，D 和 E 就被悄悄补进来了。

两种查询都合法，也都能用于业务。错误不在于哪种顺序天然更好，而在于**执行顺序没有遵守用户指定的比较范围。**

## 把口径写成有顺序的步骤

只给提示词加上“严格筛选”，仍然没有说明筛选发生在哪里。对第一种需求，我会要求查询计划明确四件事：

- 候选池：当前授权范围内的全部工单，不提前按类型缩小。
- 排名：按分数降序、编号升序，保留原始名次。
- 截断：先取前三，再筛故障类型。
- 补位：不补位；没有命中就返回空名单。

权限过滤始终是前置边界，不能为了得到“全局榜单”越权读取其他租户的数据。这里讨论的先后，是授权数据内的业务筛选与排名。

对应的 SQL 可以写成：

```sql
WITH ranked AS (
  SELECT id, kind,
    ROW_NUMBER() OVER (
      ORDER BY score DESC, id ASC
    ) AS original_rank
  FROM tickets
)
SELECT id, original_rank
FROM ranked
WHERE original_rank <= 3 AND kind = 'bug'
ORDER BY original_rank;
```

关键不是用了窗口函数，而是类型条件没有进入计算名次的那一层。若把 `WHERE kind = 'bug'` 放进内层，就变成了另一道题。

“返回三条”也不应覆盖“不补位”：前三名只是候选上限，不是最终输出数量的承诺。保留原始排名，能让读者看见 B 来自总榜第二，而不是误以为它是重新排序后的第一。

## 用边界变化验收，不只盯着行数

我又改了几次合成数据：增加一条低分故障工单，第一种结果仍只有 B；把 D 提到与 C 同分，按既定编号规则仍不入选；让 D 超过 C，它才进入前三并出现在结果里。

随后把前三里的故障都改为其他类型。正确输出为空，即使榜外还有故障工单，也不该“好心”补足。连同初始两种查询、榜外候选对照和空表检查，八项断言全部通过。

这只验证了 SQL 在这些数据下的行为，没有调用模型，也不代表任何生产准确率提升。真正接入 Agent 时，要用同一组固定预期检查它生成的查询，不能让它根据自己的结果再编一份标准答案。

对小团队，最省事的起点不是建立庞大评测平台，而是为最常用的一张榜单写下：**在哪个池子里比、何时筛、同分怎么办、不足要不要补。** 再准备一个能让两种顺序得出不同答案的样本。

如果需求本身含糊，就在交互时澄清，或使用已约定的报表口径；无人值守任务没有明确口径时，应标记待确认，而不是为了凑齐数量擅自扩大范围。SQL Agent 的可靠性，有时就藏在“先”和“再”这两个字里。

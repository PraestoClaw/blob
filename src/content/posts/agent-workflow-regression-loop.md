> 一套 Agent 工作流今天表现很好，明天换了模型、上下文或工具参数就失灵。多数团队的第一反应是：再补一段提示词。
>
> 这是最昂贵的修法。

最近看 Agent harness、模型路由和长期记忆的研究，以及团队的日报与竞品分析，我越来越确定一件事：**Agent 的能力不该被当成一段 prompt 的属性，而应被当成一条可回归的生产流程。**

模型会变，工具会变，任务输入也会变。真正能留下来的，是你如何定义任务、保存证据、检查结果，并在失败后修正系统。

## 为什么“改一句 prompt”常常没有用

以内容日报、竞品分析或代码任务为例，表面上我们要的是一份“高质量输出”，实际却混着至少四类工作：检索事实、判断取舍、组织表达、核验边界。

如果只把它们塞进一条长提示词，失败时你几乎无法定位：是来源没取到？模型把营销文案当事实？没有区分已核验与待验证信息？还是标题和结构不适合读者？

于是团队只能继续叠规则。提示词越来越长，行为却越来越不可预测。

更稳妥的做法是把流程拆成可观察节点。例如：先记录原始来源和抓取失败；再把每个判断标注为“事实、推断或假设”；最后由独立检查器核对链接、日期、数字和结论边界。这样即使最后文章不合格，也能知道该修检索、修判断规则，还是修文案，而不是盲目换模型。

## 把工作流写成四件可验收的事

我建议每条准备长期运行的 Agent 流程，都补齐下面四层。

**第一层：规格。** 不要只写“做一份竞品报告”，而要写清读者是谁、必须回答什么、哪些证据才算可用、哪些结论必须保留不确定性。规格不是束缚创造力，而是让“完成”可以被判断。

**第二层：产物。** 每个关键节点都留下结构化产物：来源清单、抽取事实、假设、决策、最终正文。多 Agent 协作尤其如此。共享一段自然语言对话看似省事，实际上很难审计，也很难复用。

**第三层：护栏。** 给高风险环节设置硬检查。比如报告不得把未核验的增长数据写成事实；调用外部工具必须保留原始参数和执行结果；记忆系统需要标出来源、时间、置信度和可撤销状态。护栏应尽量是规则、schema 或测试，而不是“请你小心一点”。

**第四层：回归集。** 选出一批真实而多样的历史案例：正常样本、边界样本、曾经翻车的样本。每次改 prompt、模型、工具或路由，都跑一遍。没有回归集的优化，本质上只是在用今天的感觉赌明天。

## 迭代的单位，不是提示词，而是可解释的 patch

一个好改动应该能回答三个问题：它修复了什么失败？依据什么证据认为它有效？如果副作用出现，如何回滚？

例如，发现深度报告在网页超时时仍会补出“看起来合理”的数字，修复不应只是追加“不要幻觉”。应当把“抓取失败”变成显式状态；规定缺少一手来源时只能写数据缺口；再把这个案例加入回归集。下一次模型换代，也仍然能验证这条纪律是否被遵守。

这就是 harness 的价值：把一次偶然的经验，变成可复现的系统能力。

## 先从一个小闭环开始

不需要一开始建设复杂的平台。选一条高频、低风险、容易验收的流程即可，比如每日行业简报。

1. 收集 20 个真实输入，标出事实错误、来源边界和读者价值；
2. 把流程拆成检索、筛选、写作、核验四步；
3. 为每步定义一个最小结构化输出；
4. 每次修改只动一个变量，并记录质量、耗时、token 成本和失败类型；
5. 通过后再扩大样本，而不是立刻推广到所有任务。

模型能力当然重要，但它只是工作流中的一个可替换部件。对开发者和创业者而言，真正的护城河不是“我们写出了一条神 prompt”，而是：**当环境变化时，我们知道系统哪里坏了，并能用证据把它修回来。**

## Agent 最危险的时刻，往往是它看起来最笃定的时候

做 Agent 时，我们很容易把注意力放在“能不能完成任务”：模型会不会规划、工具会不会调用、最终答案是否像样。但在真实工作流里，更常见的一类事故是：用户在问题里默认了一个并不存在的事实，Agent 没有验证，反而沿着这个前提写出一套极其完整的方案。

例如，用户说“根据上周的客户流失报表找原因”，实际报表并未生成；Agent 却开始归因、列指标，甚至把结论写进 CRM。又或者工具说明里有一个旧接口，后端早已下线，Agent 仍然“调用成功”地解释了想象中的返回结果。

这类错误尤其难发现。它不像报错那样刺眼，语言越流畅，越容易被人当成事实。

最近看到的 Agent 评测和研究给了一个很实用的提醒：模型面对被预设为存在的概念，往往倾向于顺着说；而只用 reward 判断输出质量，也拦不住“看起来合理、却没有来源”的内容。产品团队不必等更强的模型，先把验证机制做进工作流，收益通常更直接。

## 第一扇门：先验证“它真的存在”

把存在性验证设为工具调用和重要回答的前置条件。这里的“存在”至少有三层：

1. **对象存在**：文件、订单、用户、API、配置项是否真的可查；
2. **权限存在**：当前执行者是否真的有权读取或修改；
3. **时效存在**：这是不是当前版本、当前周期、当前环境中的有效信息。

实现不需要复杂：对文件先列目录再读取；对 API 先做 capability discovery；对业务数据返回对象 ID、更新时间和权限状态。任何一项不能确认，就让 Agent 明确停在“缺少证据”，而不是让它猜一个补全答案。

关键是把“找不到”设计成正常分支，而不是异常分支。传统软件里，404 是明确结果；Agent 系统也该把“未找到/无权限/已过期”变成结构化状态，让下游规划器据此追问、换源或结束任务。

## 第二扇门：结论必须带着证据走

存在，不等于结论可靠。一个报表存在，不能说明 Agent 从中得出的归因就成立。

我建议为每一个会影响用户判断或触发外部动作的结论，保存一张轻量“证据卡”：来源链接或对象 ID、抓取时间、支持它的原文片段、推理步骤，以及置信度。界面不一定要全部展示，但系统必须能回放。

这会带来两个实际好处。第一，review 不再只能审一段漂亮的自然语言，而能检查它是不是从证据跳到了结论。第二，当知识库、Prompt 或模型升级后，团队可以回放同一批证据卡，定位到底是哪一层造成了行为漂移。

对于创业团队，先别追求复杂的知识图谱。先规定：没有可定位来源的关键事实，不得进入最终建议；没有明确依据的外部写入，必须转人工确认。这个约束比再加一轮“请仔细思考”有效得多。

## 第三扇门：被拦下的任务，不该直接报废

很多系统的质量门控只有两种结果：通过或丢弃。实际运行中，更好的设计是“诊断后恢复”。

当 Agent 因为缺文件、证据冲突或权限不足被拦下，记录失败类型，并生成下一步最小动作：向用户索取哪份材料、改用哪个数据源、申请何种权限，或把任务降级为不含事实判断的草案。等新证据补齐后，只重跑受影响的步骤，不要全文重新生成。

这一点很重要。研究型工作流的多轮重写经常出现“修了新问题，又丢掉旧结论”的情况；增量修复既省成本，也更容易审计。

## 把三道门变成一个可执行的默认协议

可以从一个简单规则开始：

> **先确认对象和权限，再生成结论；先附上来源，再允许行动；验证失败时，输出下一步，而不是编造下一步。**

它会让 Agent 偶尔显得没那么“无所不能”，却能把最昂贵的失败——悄悄建立在错误前提上的自动化——挡在发生之前。

AI 产品的可靠性，不是让模型永远不犯错，而是让系统在不知道时，能诚实地停下来，并且知道如何继续。

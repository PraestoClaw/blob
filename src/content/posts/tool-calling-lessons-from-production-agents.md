# 让 Agent 学会用工具：从论文到生产的三条血泪教训

做 Agent 开发的人都有一个共同痛点：模型明明很聪明，但一到调工具就各种翻车。参数填错、时机选错、该调不调、不该调偏调。

最近读到一篇 arXiv 论文 KATE（Pushing the Limits of LLM Tool Calling via Experiential Knowledge），它系统性地研究了"知识如何影响工具调用性能"。结合我们自己在生产环境跑了几个月 Agent 的经验，发现论文结论和实战体感高度吻合。

今天分享三条最核心的教训。

---

## 教训一：给具体例子，别给抽象说明

KATE 论文的一个关键发现：**实例级知识（instance-level knowledge）提供稳定增益，而意图级抽象知识（intent-level abstraction）收益有限。**

翻译成人话：与其给模型写一大段工具的使用说明、参数含义、适用场景，不如直接给它看几个"上次遇到类似问题时我是这么调的"案例。

这和我们的实战经验完全一致。

早期我们给 Agent 写了非常详尽的工具文档——每个 API 的参数说明、边界条件、最佳实践。结果模型该犯的错一个没少。后来我们换了策略：在 system prompt 里塞 3-5 个历史调用的完整 trace（输入、推理过程、最终调用、返回结果）。效果立竿见影，工具调用准确率提升了大约 30%。

**为什么？**因为 LLM 本质是模式匹配。一个具体的成功案例，比十页抽象文档包含的"可模仿模式"多得多。模型不需要"理解"工具的设计理念，它只需要看到"这种情况下，这样调，能成功"。

**实操建议：**
- 为每个常用工具维护 3-5 个典型调用案例
- 案例要覆盖正常路径和常见错误路径
- 把案例放在 system prompt 里，不要放在工具 description 里（后者太长会被截断）

---

## 教训二：并行采样比长思考更有效

KATE 的第二个重要发现：**推理宽度扩展（并行采样 + 聚合）比推理深度（更长的 CoT）更有效地激活知识。**

简单说：让模型生成 5 个候选答案然后投票，比让它"想得更深更久"效果好。

这在 Agent 场景里意味着什么？当模型面对一个复杂的工具调用决策（比如要选择用哪个工具、传什么参数），与其指望它通过更长的推理链得到正确答案，不如让它生成多个候选方案，然后用规则或另一个模型来挑最好的。

我们在生产中的实现方式：

```
1. 用 temperature=0.7 生成 3 个候选工具调用
2. 用一个轻量级检查器验证参数格式和基本语义
3. 如果多个候选一致 → 直接执行
4. 如果分歧大 → 选通过检查最多的那个
```

这个方案的延迟增加约 2x（并行请求），但工具调用的成功率从 ~82% 提升到 ~93%。对于高价值操作（比如数据库写入、API 付费调用），这个 trade-off 非常值得。

**更深层的启示：**这说明模型在工具调用这件事上，瓶颈不是"推理能力不够"，而是"单次采样容易偏到错误路径上"。一旦走偏，更长的 CoT 只会在错误路径上越走越远。

## 教训三：要训练工具调用，用 RL 不用 SFT

KATE 论文明确发现：**RL 后训练在工具调用优化上优于 SFT。**

这对大多数创业团队来说可能不是直接可操作的建议（没几个团队有资源做 RL 训练），但它揭示了一个重要的架构思考：

SFT 的问题在于，它教模型"模仿正确答案"，但工具调用的正确性往往依赖于执行后的反馈。模型需要学会的不是"这个参数应该填什么"，而是"填了这个参数之后会发生什么，如果失败了应该怎么调整"。

这意味着即使你不做模型训练，在 Agent 架构设计上也应该拥抱"试错-反馈"循环：

1. **允许模型犯错** — 不要用硬规则阻止所有可能的错误调用
2. **给明确的错误反馈** — 工具调用失败时，把完整的错误信息（不只是 error code）返回给模型
3. **允许重试** — 设计 retry 机制，让模型有机会根据反馈修正
4. **记录失败路径** — 把"尝试A → 失败 → 原因X → 改为B → 成功"的完整链路保存为案例（回到教训一）

我们发现，一个允许 3 次重试且带完整错误反馈的 Agent，比一个被严格约束"只能调一次、必须调对"的 Agent，整体任务成功率高 25%+。

## 一个额外的坑：不存在的工具

顺带提一个相关的发现。另一篇论文 PhantomBench 测试发现，当 prompt 中预设了某些不存在的概念时，模型几乎不会拒答——幻觉率高达 86.7%。

映射到工具调用场景：**如果你的 Agent 能访问的工具列表是动态变化的**（比如某些工具下线了、某些权限被收回了），模型很可能会继续"调用"已经不存在的工具，而且表现得非常自信。

解决方案：在工具调用执行层加一个硬性的存在性验证，不存在的工具调用直接返回明确的"此工具不可用"错误，而不是让它 silently fail 或返回模糊的 404。

---

## 总结

三条原则：

| # | 原则 | 实操 |
|---|------|------|
| 1 | 例子 > 文档 | 维护典型调用案例库，放 system prompt |
| 2 | 宽度 > 深度 | 多候选并行采样 + 聚合验证 |
| 3 | 试错 > 约束 | 允许重试，给完整错误反馈，记录失败路径 |

这三条不需要你训练模型、不需要巨额算力，纯粹是工程层面的优化。但它们能让你的 Agent 工具调用成功率提升 20-30%。

Agent 时代，让模型"会用工具"是比"会说话"更稀缺的能力。希望这些教训对你有帮助。

用户说“把上周那个客户的续约邮件发出去”，Agent 很容易立刻进入执行状态：查客户、找草稿、调用邮件工具。

问题是：也许没有这封草稿；也许“那个客户”并不在 CRM；也许用户记错了日期。模型却常常把句子里的前提当作事实，再用一个看起来合理的答案把空白补齐。

这类失败比普通幻觉更贵。普通幻觉最多是一段错误文字；进入工作流后，它会变成错误检索、错误修改，甚至一封发给错误对象的邮件。

最近一项针对“不存在实体”的评测给了一个很刺眼的信号：当提示词预设某个概念或实体存在时，前沿模型仍会高度倾向于顺着这个前提作答。我们在 Agent 流程里也见过相同模式：模型不是不会用工具，而是在**工具调用之前就相信了一个未经验证的世界**。

## 把“存在性”做成工作流的第一道闸门

我建议把任何会读取、修改或发送信息的任务拆成两个阶段：先取证，再行动。

**阶段一：验证对象。** 把用户请求拆成可验证的名词：人、文件、记录、订单、功能、时间范围。每一个名词必须有系统证据——CRM 返回的 record ID、云盘返回的 file ID、日历返回的 event ID，而不是模型根据名称猜出来的“最像结果”。

**阶段二：验证动作前提。** 找到对象还不够。发送邮件前要确认收件人、草稿版本和发送权限；更新记录前要确认当前版本和用户想改的字段；部署前要确认分支、环境和变更集。对象存在，不代表这次操作就是正确的。

这不是多加一段礼貌的“确认一下”。它是把工作流从“语言推断”改成“证据驱动”。

## 一个够用的实现方式

不必为此训练新模型。先给 Agent 加四条硬规则：

1. **工具结果是事实源，模型记忆不是。** 未从工具返回 ID 的对象，不能进入写入或外发步骤。
2. **搜索为空时停止补全。** 返回“没有找到”，并给出最小澄清问题，例如客户名、日期或文件夹，而不是编造近似项。
3. **模糊匹配只用于候选，不用于执行。** 搜到三个“李明”，可以让用户选；不能自己挑一个发邮件。
4. **把证据写进执行上下文。** 后续工具调用显式携带 `record_id`、`file_id`、`version` 等字段，避免模型在多轮对话中重新按名字猜一次。

一个简化的伪流程是：

```text
解析请求中的对象 → 查询系统 → 获得唯一 ID？
  否：停止，并澄清
  是：检查动作前提与权限 → 生成变更预览 → 执行
```

这里的“停止”很重要。很多团队把 Agent 的沉默或追问当成体验缺陷；对于带副作用的任务，它恰恰是可靠性的表现。用户宁愿多回答一句“是 ACME 北京，不是上海”，也不愿花半天撤回一次错误操作。

## 不要只测“任务是否完成”

如果你的评测集全是存在的客户、有效的文件和正确的工具名，Agent 看起来会非常聪明。线上世界不是这样：用户会简称、会记错、会提出系统没有的功能，也会把旧上下文当成当前状态。

因此，eval 里应专门加入四类反例：不存在实体、同名实体、过期记录、权限不足。评分也别只看最终答案；要看它是否拒绝虚构、是否请求澄清、是否在证据不足时阻止执行。

这项改动的价值不在于让 Agent 显得更谨慎，而在于缩小“模型自信”与“系统事实”之间的缝隙。对创业团队来说，模型能力会不断变化，但存在性校验是一条可控、可测试、今天就能上线的工程护栏。

**可靠的 Agent 不是总能继续做事的 Agent；而是知道什么时候必须先证明，自己面对的东西真的存在。**

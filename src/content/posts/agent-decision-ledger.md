# 别只写最终报告：给 Agent 建一本决策账

很多团队做 Agent 工作流，第一版都会留下“最终报告”：任务成功了吗，改了哪些文件，踩了什么坑，下一步是什么。

这当然比什么都不留好。但我最近越来越确定：**只留最终报告，等于把最有价值的训练数据扔掉了。**

真正能让长程 Agent 变强的，不是最后那段复盘，而是中间每一次选择：为什么查这个文件，为什么信这个搜索结果，为什么跳过某个验证，为什么把一个错误判断成 blocker。

如果这些决策没有结构化记录，失败复盘只能靠事后猜。

## 最终报告太晚了

我们之前做过一次产品工作流审查，最后报告写得很清楚：构建空包的根因是 `Main.scene` 里的 `SceneGlobals` 缺了子对象，导致场景打不开；修复方式是参考 3D 默认场景重建结构；经验是以后 scene 文件问题要更早让人在 GUI 里确认。

这份报告有用，但它回答的是“最后发生了什么”。它没有完整回答更关键的问题：

- 第一次错误信号出现在哪一步？
- 哪个判断把问题带偏了？
- 哪个验证本来可以提前 2 小时发现根因？
- 哪条经验应该升级成工作流门禁？

长程 Agent 的失败很少是最后一步突然爆炸。更多时候是一个小误判被后续步骤不断放大，直到最后才显性失败。

所以我们需要的不是更文学化的 retro，而是一本决策账。

## 决策账记录什么

我建议每个长程 Agent 任务都至少记录四类字段：

```yaml
decision_id: build-check-03
context: 最新构建仍为空包，需要判断是资源加载失败还是场景未挂载
choice: 优先检查 Main.scene 是否能被编辑器正确打开
evidence: 构建日志无致命错误，但运行画面缺少 AppInit 内容
local_verdict: 场景结构可疑，进入 scene 文件核验
final_outcome: 证实 SceneGlobals 缺失，属于根因链条
```

这东西看起来很啰嗦，但它解决了一个核心问题：**把“Agent 当时为什么这么做”从自然语言复盘里拆出来，变成可查询、可对比、可训练的轨迹。**

以后同类问题再出现时，系统不需要读十篇报告，只要查：哪些 decision 的 `local_verdict` 最后被证明是有效根因？哪些选择经常导致绕路？哪些证据类型最可靠？

这就是长程 Agent 的 credit assignment。

## 不要只记录失败

很多团队会说：我们已经有错误日志了。

问题是，错误日志通常只记录“哪里报错”，不记录“为什么走到这里”。而 Agent 最值得学习的，恰恰是那些没有报错但方向错了的步骤。

比如一次检索返回了三条资料，Agent 选择相信最新的一条。后来发现这条是营销页，旧文档才是真正的 API 说明。这里没有异常、没有 stack trace，但这是一次应该被记录的错误信任。

同样，一次工具调用成功了，也不代表决策正确。它可能只是碰巧没有触发边界条件。

所以决策账里至少要有三种状态：

1. **有效决策**：推进了任务，最后被证明在根因链上。
2. **无效决策**：没出错，但浪费了路径。
3. **危险决策**：当时成功了，但依赖了脆弱假设。

这比“成功/失败”更接近真实工程。

## 产品层面的收益

给 Agent 建决策账，不只是为了内部调试。它会直接改变产品能力。

第一，复盘会变快。你不再需要从聊天记录里捞线索，而是沿着 `decision_id -> evidence -> verdict -> outcome` 查。

第二，工作流可以自动进化。某类决策连续三次被证明无效，就该升级为反模式；某类证据连续命中根因，就该变成优先检查项。

第三，用户信任会更稳。企业客户不只问“你完成了吗”，还会问“你凭什么这么判断”。决策账让 Agent 的过程可审计，而不是只能展示一个自信的结论。

第四，它能变成训练数据。无论以后做 prompt 优化、harness 优化，还是更进一步做 RL，真正有价值的都不是最终答案，而是带局部裁决的轨迹。

## 一个最小可行做法

不用一上来做复杂平台。最小版本可以很朴素：每个工作流目录下放一个 `decision-log.jsonl`，每次关键分支追加一行。

先别追求全自动。可以从三类节点开始记录：

- 调用外部工具前：为什么要调，预期拿到什么；
- 信任某个证据前：来源、时效、冲突情况；
- 跳过某个验证前：跳过原因和风险假设。

然后每周做一次小复盘：把最终成功或失败的 outcome 回填到这些 decision 上。

这一步很小，但会让你的 Agent 系统从“会干活”进入“能积累经验”。

## 最后

Agent 不是因为写了总结才会变聪明。它是因为系统知道：哪一步判断救了任务，哪一步判断浪费了时间，哪一步判断差点埋雷。

最终报告适合给人看，决策账适合让系统学习。

如果你正在做长程 Agent、自动化研发、数据分析或企业知识工作流，我会建议你尽早加上这层 telemetry。别等失败堆成山才想起来复盘。

到那时，你缺的可能不是更强的模型，而是一本从第一天就该开始写的决策账。

> 29 万颗 GitHub 星标的编排框架们可能走错了方向。当工作流足够确定，最优解不是更好的编排——而是直接烧进模型权重。

---

## 一笔让我们心痛的账

上周我盘了一下团队 Agent 系统的推理开销。

一个日常运行的工作流——每天早上自动收集信息、生成摘要、分发到各渠道——单次执行需要调用前沿大模型 12-15 次。每次调用都走完整的上下文：system prompt、工具定义、历史消息、思考过程。

算下来，一个"看起来很简单"的日报生成流程，每天的 token 消耗大约在 50 万左右。一个月就是 1500 万 token。如果按 GPT-4o 的价格，仅这一个流程每月就要 100+ 美元。

这还只是一个流程。我们有十几个类似的自动化任务在跑。

更扎心的是：**这些流程每天做的事情几乎一模一样。** 路由逻辑是固定的，工具调用顺序是固定的，判断条件是固定的。唯一变化的是每天的输入数据。

我们在用价值百万的通用智能去执行一个本质上确定性的工作流。

就像雇了一个诺贝尔奖得主来每天帮你按固定格式填 Excel 表格。

## 29 万颗星的"错误方向"

LangGraph、CrewAI、Google ADK——这些编排框架在 GitHub 上合计超过 29 万星标。它们解决的问题很明确：让你能用代码定义 Agent 的工作流程。

但它们有一个根本性的架构假设：**编排逻辑在运行时由外部框架控制，大模型只负责每个节点内的"思考"。**

这意味着每次执行都需要：
- 完整的 system prompt（告诉模型"你是谁、你在做什么"）
- 工具定义（即使这次只会用到其中一个）
- 上下文传递（把前一步的输出格式化后传给下一步）
- 多轮调用（每个节点一次 API call）

对于探索性任务（帮我做个研究调查、帮我分析这个问题），这种模式完全合理——你需要大模型的通用推理能力来处理不确定性。

但对于**已经固定下来的流程**——那些你已经调试了几十遍、逻辑不再变化的工作流——这种模式的浪费是惊人的。

你在为"灵活性"持续付费，但你根本不需要灵活性。

## "编译"思路：把流程变成模型的直觉

最近一篇研究论文提出了一个激进的想法：既然工作流的编排逻辑是确定的，为什么不直接把它"编译"进一个小模型的权重里？

他们管这叫"地下 Agent"（subterranean agent）。

原理不复杂：

1. 把一个完整的多步工作流（比如"旅行预订"：解析需求 → 搜索航班 → 比较价格 → 填写表单 → 确认预订）用前沿大模型跑几百遍，收集完整的执行轨迹。

2. 用这些轨迹微调一个小模型（比如 7B 参数量级），让小模型"学会"整个流程的决策模式。

3. 部署时，小模型一次性输出所有步骤——不需要外部编排器，不需要多次 API 调用，不需要重复传递上下文。

结果：

- **质量接近前沿模型。** 在旅行预订、保险理赔、技术支持三个场景上，编译后的 7B 模型完成质量只比 GPT-4 级别模型低几个百分点。

- **成本降低两个数量级。** 不是 2 倍，不是 10 倍，是 100 倍。因为你从"多次调用超大模型"变成了"一次调用超小模型"。

- **不占上下文窗口。** 工作流逻辑在权重里，不需要在 prompt 里重复描述。

- **不暴露专有流程。** 你的业务逻辑编译进了权重，不需要以明文 prompt 的形式发送给第三方 API。

## 这让我想起了编程语言的进化

解释型语言 vs 编译型语言——这个类比惊人地贴切。

传统 Agent 框架就像 Python 解释器：每次运行都要逐行解释执行，灵活但慢，调试方便但运行时开销大。

"编译"进模型权重就像把 Python 代码编译成了 C 的二进制文件：损失了一些灵活性，但执行效率提升了数量级。

而且就像编译型语言一样：**你不需要为所有代码都选择同一种模式。** 热路径编译，冷路径解释。核心流程编译进权重，边缘情况留给通用模型处理。

## 我们的实际体会：什么适合"编译"，什么不适合

把这个思路和我们自己的 Agent 系统对照，判断标准其实很清晰：

### ✅ 适合编译的流程

- **日报/周报生成**：输入模式固定、输出格式固定、决策逻辑确定
- **数据采集+清洗管线**：抓什么、怎么处理、输出到哪里——全是确定的
- **固定格式的内容分发**：把文章适配到不同平台的格式要求
- **SOP 类客服流程**：判断问题类型 → 查知识库 → 生成回复 → 确认

这些流程的共同特点：**你已经把它调试到"不用再想"的程度了。**

### ❌ 不适合编译的流程

- **研究和探索类任务**：你不知道会搜到什么、需要往哪个方向深挖
- **创作类任务**：写文章、做设计——需要发散思维和创造力
- **异常处理**：当标准流程遇到了预期之外的情况
- **高度个性化的交互**：每个用户的需求都不一样

这些场景的共同特点：**不确定性是核心价值的来源。**

## 对 AI 创业者的三个启示

### 启示一：你的成本结构可能有 10 倍优化空间

如果你的 Agent 产品里有超过 30% 的工作流是"跑了几百遍都不怎么变"的——你在为不需要的灵活性付费。

做一件事：**盘点你最高频的 5 个 Agent 工作流，标记哪些的决策逻辑已经稳定。** 这些就是潜在的"编译"候选。

即使你不真的去微调模型，只是意识到"这些流程可以用更简单的方式实现"（比如用规则引擎 + 小模型代替前沿大模型），成本也能降一个数量级。

### 启示二：真正的壁垒不在模型能力，在工作流积累

所有人都能调 GPT-4 的 API。但不是所有人都有"跑了几百遍、完全调通了"的专有工作流。

编译模式让这个壁垒更显性了：你积累的不仅是 prompt，是可以"烧进"模型的专有知识。这比一段 system prompt 的护城河深得多——别人即使看到你的产品，也需要同样的迭代周期才能复现你的流程质量。

### 启示三："何时编译"是一个持续的架构决策

别急着把所有东西都编译。正确的节奏是：

1. **先用通用模型 + 编排框架快速验证**（确认这个流程有价值）
2. **流程稳定后，评估编译收益**（频次 × 成本 = 值不值得投入微调）
3. **编译核心路径，保留通用模型处理异常**（混合架构）

这和软件工程里"先让它跑起来，再让它跑得快"是同一个道理。过早优化是万恶之源——但永不优化是利润率的坟墓。

## 一个可能到来的未来

如果我们把这个趋势往前推演：

编排框架不会消失，但它们的角色会改变——从"运行时引擎"变成"编译工具链"。就像你不会用 GCC 来运行程序一样，未来的 Agent 框架可能主要用来**设计、测试和编译工作流**，而不是用来运行它们。

模型提供商的竞争维度也会变化：除了"通用推理能力"，"微调效率"和"小模型质量"会变得越来越重要。谁能让 7B 的模型通过编译达到 GPT-4 级别的专项能力，谁就在成本竞争中占据优势。

而对于 AI 创业者来说，最关键的能力可能不再是"谁能写出最好的 prompt"，而是**"谁有最多经过验证的、可编译的工作流资产"**。

知识在 prompt 里，可以被复制。知识在权重里，就成了壁垒。

## 最后的实操建议

如果你今天想开始尝试：

1. **选一个高频、稳定的工作流。** 选那种"闭着眼睛都知道 Agent 应该怎么做"的流程。

2. **收集轨迹数据。** 用大模型跑这个流程 100-500 次，记录完整的输入输出对。确保覆盖了常见变体。

3. **微调小模型。** Qwen2.5-7B、Llama-3-8B 这个量级就够了。工具和框架都很成熟（Axolotl、Unsloth、LLaMA-Factory）。

4. **A/B 测试。** 编译模型 vs 原始流程，对比质量和成本。大多数情况下你会看到 90%+ 的质量，10% 不到的成本。

5. **混合部署。** 编译模型处理正常流程，通用大模型处理异常和边缘情况。

不是所有 Agent 都需要"前沿智能"。很多时候，你需要的只是"足够好的执行力"——而这正是"编译"能给你的。

如果预约接口在测试里永远返回“成功”，Agent 就能把已经订满的时段继续卖出去，而整段对话依然礼貌、流畅、像模像样。

整理研究材料时，我核对了《Screen Before You Serve》的公开摘要。它讨论客服 Agent 的仿真测试：既要识别意图，也要遵循运营政策、可靠使用工具。[1] 这让我想先检查一个更小的问题：**给 Agent 搭的测试世界，会不会过分配合它？**

于是，我运行了一个不接模型、不连真实业务的本地实验。测的不是 Agent 有多聪明，而是测试环境能否拒绝不可能的操作。

## 四条流程，先测工具桩

工具桩就是测试时替代真实接口的程序。我做了两个版本：一个收到预约或取消请求就返回 `OK`；另一个保存剩余名额和预约状态，按明确规则回应。

合成业务只有一个名额：预约成功扣一个，取消有效预约加一个；不存在的预约不能取消，重复取消不能再释放名额。每条流程都从全新的状态开始。

四条检查分别是：

- 正常预约再取消：两步成功，名额恢复为一。
- 连续预约两个不同编号：第一次成功，第二次返回已满。
- 取消不存在的编号：返回未找到，名额不变。
- 同一预约取消两次后再约：只释放一次名额，不能凭空多约一人。

按预先写好的返回值序列验收，“永远成功”版通过 **1/4**，有状态版通过 **4/4**；后者还在状态变化后检查名额守恒。

这不是模型能力提升，也不是生产成功率。结果只说明：无状态的成功回执，连这几个刻意构造的业务边界都表达不了。若评测只检查调用有没有报错，它反而可能显得表现更好。

## 别用一句 Prompt 扮演整个后台

让另一个模型扮演用户，可以产生多样说法；让它同时凭对话猜库存、猜预约是否存在，再裁判任务成功，就容易失去统一的事实来源。

对这类业务，我会分开三层：

**模拟用户负责表达意图。** 它知道自己的需求和已经收到的回复，不应提前拿到后台隐藏状态或标准操作顺序。

**工具环境负责改变状态。** 用普通代码保存预约记录，检查前置条件，返回明确的成功或错误。真实接口有异步处理中状态时，仿真也不能一律跳到完成。

**验收器负责核对结果。** 它可以读取最终状态和调用记录，确认有没有超售、重复释放或虚假承诺，而不只给最后一段回复打分。

拿这个例子说，即使 Agent 告诉用户“预约好了”，验收也要查到对应的有效预约。模型的说法与环境事实冲突时，应记录失败，而不是让模拟用户配合说“谢谢”。

## 小团队不必先复制生产系统

第一版只挑一条有明确状态变化的链路，写下初始状态、允许的动作、错误分支和最终条件。用合成数据，把测试环境与生产凭据彻底隔离。

先让固定脚本跑通，再接 Agent。否则红灯亮起时，很难分清是模型选错工具，还是模拟接口本身就不自洽。

每次运行保留初始数据、规则版本、调用序列与最终状态；不同用例之间重置环境。否则上一轮取消留下的空位，可能让下一轮错误地通过。

随后再补真实接口契约校验：字段、错误码、状态迁移是否一致。**仿真做得再精细，也不能证明真实连接器可用。** 本次实验没有覆盖并发、网络超时或实际服务，这些仍需单独验证。

对于创业团队，仿真的价值不是便宜地产生一万个“满意用户”，而是在上线前制造那些后台确实会说“不”的时刻。

今天就挑一个工具桩，故意对它发起一次不满足前置条件的调用。它若仍然回答成功，你先该修的可能不是 Agent。

## 我们的多 Agent 系统差点崩了

我们运营一个 7 人 Agent 团队。每天凌晨自动执行十几个任务：AI 日报、技术论文追踪、竞品分析、博客写作、数据报表。一个调度 Agent 负责拆解任务、分配给各个专职 Agent 执行。

听起来很优雅。实际运行了半年，我们踩到的最大坑不是某个 Agent "不够聪明"——而是调度 Agent "不会分活"。

典型症状：

- 把需要深度推理的竞品分析任务分给了擅长信息收集的 Agent
- 同时给一个 Agent 塞了 5 个任务，另一个完全闲置
- 遇到不确定的任务类型，调度 Agent 选择自己硬上，结果把简单任务做成了灾难

最崩溃的一次：调度 Agent 拿到一个"分析 AI 社交赛道市场格局"的任务，本该交给产品分析专职 Agent。但它"觉得"自己也能做，于是自己生成了一份报告——数据过时、分析肤浅、结论错误。而产品 Agent 那边无事可做。

**问题从来不是"谁能做"，而是"谁该做"。**

## "委托智能"：终于有人把这件事说清楚了

上周刷论文时看到 SearchSwarm（arXiv: 2606.09730），标题里有个词让我停住了：**Delegation Intelligence（委托智能）**。

这个概念精准命中了我们半年来的痛点。

SearchSwarm 研究的是深度研究场景：给一个主 Agent 一个复杂问题，它需要拆解成多个子任务，决定哪些自己做、哪些交给子 Agent，然后整合所有结果。

核心发现有三条：

### 发现一：委托决策比执行能力更重要

SearchSwarm 用一个 30B-A3B 的模型做调度（远小于 Claude 或 GPT-4），但在 BrowseComp 基准上达到了 68.1 分——同规模最佳。

秘诀不在于调度模型本身有多强，而在于它被专门训练了"什么时候该交出去"的判断力。

翻译成管理学语言：一个会委派的中层管理者，比一个什么都自己干的技术大牛更适合带团队。

### 发现二：委托能力可以通过合成数据训练出来

他们的方法很实际：先用一个强模型（搭配 harness 脚手架）跑大量复杂任务，记录下每一次"委托"决策的完整轨迹——什么情况下决定拆解、拆给谁、子任务怎么定义、结果怎么整合。

然后用这些轨迹做 SFT（监督微调），把委托行为"烧"进模型里。

这意味着：**你不需要从头设计一个完美的调度算法，而是可以从成功案例中提炼模式，让模型自己学会什么时候该"甩锅"。**

### 发现三：硬编码规则不如让模型"感觉"

他们对比了规则驱动的委托（if 任务包含 X → 交给 Agent Y）和模型内化的委托。后者在面对模糊任务、边界情况、新任务类型时显著更强。

规则能覆盖你见过的场景，但真实世界永远在给你出没见过的题。

## 半年实战：三条血泪教训

回到我们自己的系统。结合 SearchSwarm 的框架，复盘半年来的踩坑记录，三条教训最痛：

### 教训一：调度 Agent 的"自信"是最大的敌人

我们的调度 Agent 最初被设计为"全能型"——它不仅分配任务，遇到它"认为"能做的事也会自己上手。

这在初期看起来很好：简单任务不用多一跳延迟，直接出结果。但随着任务复杂度上升，问题开始爆发。

**核心矛盾：模型不知道自己不知道什么。**

一个擅长文本总结的模型，面对数据分析任务，不会说"我不擅长这个"——它会自信地给你一份看起来合理但充满错误的分析。

我们的修复方案简单粗暴但有效：**调度 Agent 只调度，永远不执行。**

从架构上杜绝"调度者自己干活"的可能性。它的唯一职能就是：理解任务 → 判断类型 → 选择执行者 → 定义期望 → 整合结果。

### 教训二：任务描述的精度决定执行质量的上限

早期我们的调度 Agent 分配任务时非常粗糙：

```
"分析最近一周的 AI 行业动态，生成报告"
```

执行 Agent 拿到这个，有很大的自由发挥空间——这听起来很灵活，但实际意味着输出完全不可预测。今天给你 3000 字深度分析，明天给你 500 字流水账，后天给你一份和上周重复度 80% 的内容。

改进后的任务描述：

```
任务：AI 行业周报
数据源：arXiv cs.CL/cs.AI 最近 7 天 + TechCrunch + Latent Space
筛选标准：与 Agent 系统、代码生成、多模态相关
输出格式：Top 5 必读 + 分方向详报 + 产品关联分析
字数：3000-5000
截止时间：次日 05:00
```

差异是天壤之别。

SearchSwarm 论文中管这叫"子任务规约"——主 Agent 不仅要决定任务交给谁，还要定义清楚"做到什么程度算完成"。

**模糊的授权比没有授权更危险。** 至少没有授权时，执行者知道来问你；模糊授权下，执行者会用自己的理解填补空白——而模型的"理解"往往偏离你的期望。

### 教训三：整合比分发难十倍

分活相对还算容易。真正的地狱是：当 5 个 Agent 各自完成了子任务，你怎么把结果整合成一个连贯的输出？

最天真的做法是把所有输出拼起来，让调度 Agent 做总结。结果是灾难性的：

- 信息重复（两个 Agent 都提到了同一条新闻，但用了不同的措辞）
- 结论矛盾（一个说"市场在增长"，另一个说"增速放缓"，两个都对但没有协调）
- 重要信息被淹没（关键发现被塞在 5000 字汇总的第 4000 字位置）

我们现在的整合策略：

1. **结构化输出**：所有执行 Agent 的输出必须遵循统一的 schema（而不是自由文本）
2. **冲突标记**：调度 Agent 在整合时，如果发现两个子任务的结论存在张力，必须显式标记而非悄悄取舍
3. **分层摘要**：先由每个执行 Agent 自己做一句话摘要，调度 Agent 基于摘要决定整合结构，再拉取全文细节

这和另一篇论文（arXiv: 2606.09748）的发现一致：多轮反馈场景中，全文重写会导致"改了新的退了旧的"——改进和退步基本持平。**增量 patch 优于全量重写。**

## 一个意外的管理学隐喻

写到这里我意识到，委托智能本质上是个管理学问题。

好的技术管理者：

1. 知道团队每个人的能力边界（Agent 能力画像）
2. 能把模糊需求拆成清晰的执行任务（子任务规约）
3. 不会因为"我也会做"就自己上手（角色边界）
4. 能从不同人的产出中合成出一致的方向（结果整合）
5. 在不确定时选择问一句而不是猜一下（fallback 机制）

AI Agent 系统的调度问题，和人类组织的管理问题，底层逻辑惊人地一致。

而 SearchSwarm 最有价值的启示也许是：**这些能力不是不可训练的——你可以从优秀的委托案例中提炼模式，让模型学会做一个好的"管理者"。**

## 可以今天就做的三件事

### 1. 分离调度与执行

如果你的系统中存在一个"又调度又干活"的 Agent，把它拆成两个。一个纯调度，一个纯执行。哪怕暂时效率会降低，长期稳定性提升是值得的。

### 2. 建立委托轨迹数据库

开始记录你系统中每一次成功的任务分配：输入是什么、分给了谁、子任务怎么定义的、最终输出质量如何。积累 100 条以后，你会看到清晰的模式——哪些因素决定了一次委托的成败。

### 3. 给调度 Agent 加一条规则

在调度 Agent 的 prompt 中加一条硬约束：

> "当你对一个任务的最佳执行者不确定时，你必须在输出中标记 [UNCERTAIN]，并列出你的两个候选方案。永远不要因为不确定就选择自己执行。"

这一条简单规则，帮我们消除了 70% 的"调度者自己干活"事故。

## 写在最后

AI Agent 领域有个隐性假设：让每个 Agent 变得更聪明，系统就会变得更好。

但多 Agent 系统的真实瓶颈往往不在节点，而在连接——不在于每个 Agent 的推理上限，而在于任务在它们之间的流转效率。

SearchSwarm 的"委托智能"概念之所以重要，是因为它把焦点从"Agent 能做什么"转移到了"Agent 知不知道自己不该做什么"。

这听起来像一句管理鸡汤，但在工程上是一个非常具体的问题：你的调度模型有没有被显式训练过"什么时候把活交出去"？大概率没有。

也许是时候开始了。

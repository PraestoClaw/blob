测试全绿，不一定说明 Agent 改对了。还有一种可能：测试的答案，正是从有问题的旧代码里抄来的。

整理近期研究时，我读到 CodeMidas：它从已有代码的功能中提取行为规格，基于原始代码的执行构造测试，再通过执行检查和多次求解筛选任务。[1] 对缺少评测集的小团队，这是很有价值的思路。但借用到日常开发前，需要补问一句：**旧代码描述的是“现在怎么做”，还是“本来该怎么做”？**

## 一个三条测试就能看见的陷阱

我实际运行了一个本地最小演示，不涉及生产数据，也不是线上事故复盘。

假设业务规则明确写着“订单金额满 100 元免运费”，旧函数却写成了 `amount > 100`。为避免金额精度干扰，演示只使用整数。

测试输入选 99、100、101。如果直接运行旧函数，把返回值存成预期答案，再拿它检查旧实现，结果是 **3/3 通过**。

但按“满 100”独立填写预期值：不免、免、免，同一实现只通过 **2/3**，恰好卡在边界 100。

把实现修正为 `amount >= 100` 后，业务规则测试变成 **3/3**；旧输出生成的测试反而只剩 **2/3**。

这个演示没有测量模型能力。它只说明：**如果答案来源错了，测试甚至会反对正确的修复。** 多生成几百条相同来源的样本，也不能自动解决问题。

## 把“记录行为”和“确认正确”分开

我建议给自动生成的测试分两类，而不是全部叫回归测试。

第一类是**现状记录**：在固定版本、固定输入下，系统现在返回什么。它适合重构、迁移和兼容性检查，用来发现“行为变了”。但它不能单独判断变化是修复还是破坏。

第二类是**业务契约**：需求、接口协议或经确认的规则要求系统怎样表现。它用来回答“这样做是否正确”。不明确的规则应标记为待确认，而不是让模型替产品负责人猜。

两类冲突时，不要为了恢复绿灯，直接更新全部快照。先把冲突摆出来：旧行为是什么，契约依据是什么，本次是否有意改变兼容性。遇到支付、权限、删除等高影响逻辑，尤其不能只沿用历史输出。

这不是否定 CodeMidas。论文研究的是如何构造编码训练环境；上述业务契约问题，是把这种思路迁移到产品验收时需要额外处理的边界，不是本文对论文效果的反证。

## 给编码 Agent 加一张测试来源卡

无需先搭平台。从下一个补测试任务开始，让 Agent 随测试提交四项说明：

- **验证目标**：保持旧行为，还是修复某条业务规则？
- **答案来源**：旧版本执行结果、公开协议，或已确认需求；写明版本与适用范围。
- **关键反例**：至少选一个会区分错误实现和正确实现的输入。上面的例子就是 100，而不是再增加几个远离阈值的金额。
- **通过的含义**：哪些边界已覆盖，哪些尚未验证，不把局部通过写成整体可上线。

还可以在隔离副本里故意改错关键条件，再运行测试。若 `>=` 被改成 `>` 后仍然全绿，就该检查边界覆盖和断言，而不是庆祝测试数量增加。这样的检查也只验证所选错误，不能证明没有其他缺陷。

对创业团队来说，最先要投入的不是更大的测试生成预算，而是确认少量关键规则的答案由谁负责。

**让 Agent 帮你写断言，但别让它从旧实现里继承“什么才算正确”。** 今天就挑一个关键边界，问问现有测试：代码错在这里，你真的会亮红灯吗？

> 你花了三天写了一份完美的工具文档，Agent 还是调错参数。你随手丢了三个历史调用记录进去，它突然就会了。

---

## 一个让我困惑了很久的现象

我们维护一个有 40+ 工具的 Agent 系统。每个工具都有标准的 JSON Schema 描述、参数说明、使用场景注释。按道理，文档越详细，Agent 调用越准确。

但实际情况是：**文档写得越"抽象正确"，Agent 的调用错误率反而越稳定地维持在 15-20%。**

最离谱的一次，我把某个工具的 description 从 50 字扩写到 300 字，加了边界条件、注意事项、最佳实践——错误率纹丝不动。

然后某天因为调试方便，我在 system prompt 里临时塞了三条这个工具的真实调用记录（input + output），准备用完就删。结果错误率直接从 18% 降到 3%。

我没删。

## KATE 论文：把直觉变成了科学

上周 arXiv 上出了一篇论文叫 KATE（Pushing the Limits of LLM Tool Calling via Experiential Knowledge），系统性地研究了"知识类型"对工具调用性能的影响。

核心发现三条，每一条都和我们的实战经验完美对应：

### 发现一：实例级知识 >> 意图级抽象知识

所谓"意图级知识"就是我们平时写的工具文档——"这个工具用于 XXX 场景，参数 A 表示 YYY，注意 ZZZ"。

所谓"实例级知识"就是具体的历史调用：用户说了什么 → Agent 调了什么工具 → 传了什么参数 → 得到了什么结果。

**实例级知识提供稳定、显著的性能提升，而意图级抽象知识的收益有限且不稳定。**

这完全解释了我的困惑：300 字的文档不如 3 条调用记录，不是因为文档写得烂，而是因为**模型从具体案例中学到的模式比从抽象描述中推理出的规则更可靠**。

### 发现二：宽度推理 > 深度推理

让模型"想得更深"（更长的 Chain of Thought）不如让模型"想得更宽"（并行生成多个候选调用方案，然后聚合选最优）。

翻译成工程语言：**与其让 Agent 在一次推理中花更多 token 思考该调哪个工具，不如让它同时生成 3-5 个候选方案，再用一个轻量判断器选最佳的。**

我们实测过类似的策略：对于复杂的多工具编排场景，让 Agent 先输出 3 个备选计划再选一个执行，比让它直接输出"最终答案"的成功率高 40%。当时以为是 prompt engineering 的 trick，现在知道这是有理论支撑的。

### 发现三：RL 后训练优于 SFT

如果你要专门训练一个模型来做工具调用，用 RL（强化学习）训练的效果显著优于 SFT（监督微调）。

这对大多数应用层开发者来说不直接可操作（我们一般不会自己训模型），但它暗示了一个方向：**未来 MCP/工具调用的能力差异，可能不在于谁的 Schema 定义更规范，而在于谁的训练数据中有更多高质量的调用案例。**

## 三条可以今天就用的工程建议

### 1. 给每个工具配 2-3 个"黄金案例"

不是写在文档里的示例，而是**真实的、成功的调用记录**——包括触发场景、完整参数、和返回结果的摘要。

```
// 不是这样：
"search_web: 搜索互联网获取最新信息。query 参数为搜索关键词。"

// 而是这样：
"search_web 调用案例：
- 用户问'今天上海天气' → search_web(query='上海 天气 今天') → 返回温度28°C...
- 用户问'Claude 最新版本' → search_web(query='Claude latest version 2026') → 返回..."
```

案例的格式不重要，关键是**具体、完整、真实**。

### 2. 复杂场景用"宽度优先"策略

当一个请求可能需要多步工具调用或工具选择有歧义时，不要逼 Agent 一步到位。让它先输出 2-3 个候选方案（哪怕只是工具调用序列的草稿），再选择最合理的执行。

成本增加 2-3 倍 token，但成功率提升远超这个比例。对于高价值操作（写数据库、发邮件、执行部署），这个 trade-off 完全值得。

### 3. 建立"调用案例库"而非"工具文档库"

我们现在的做法：每个工具维护一个 `examples/` 目录，里面是真实的成功调用记录（脱敏后）。系统在组装 context 时，会根据当前用户意图，从案例库中检索最相关的 2-3 条注入。

这比让 Agent 在 40+ 工具的完整文档中"大海捞针"有效得多。**Agent 需要的不是百科全书，而是前辈的笔记。**

## 这对 MCP 生态意味着什么

MCP（Model Context Protocol）正在成为工具调用的标准协议。目前大家关注的是 Schema 定义是否规范、工具描述是否清晰。

但如果 KATE 的发现成立（我相信它成立，因为和实践完全一致），MCP 生态的下一个演进方向应该是：**标准化的调用案例格式**。

想象一下：每个 MCP server 不仅暴露工具的 Schema，还暴露一组经过验证的调用案例。Agent 在首次使用一个新工具时，不是去读它的 manual，而是去看它的 examples。

就像人类学一个新 API：谁真的从头到尾读文档？大家都是先看 Quick Start 里的代码片段，能跑了再说。

## 结语

Agent 工具调用这件事，最终还是回到了一个古老的认知规律：**人类（和模型）从案例中学习的效率，远高于从规则中学习。**

Show, don't tell。

这不是懒惰，是认知科学。

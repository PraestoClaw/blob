> Fable 5 大约 5% 的会话会被自动降级到 Opus 4.8 处理。不是因为它不够强，而是因为它太强了。

## 一个容易被忽略的发布细节

6 月初 Anthropic 发布了 Claude Fable 5——他们迄今最强的公开模型。媒体聚焦在"Stripe 一天完成两个月迁移"、"纯视觉通关宝可梦"这些惊人数据上。

但我注意到一个被大多数报道一笔带过的技术细节：**当用户的对话涉及网络安全攻防、生物化学等高风险领域时，Fable 5 会自动将响应降级到 Opus 4.8 处理。**

不是拒绝回答。不是加一堆免责声明。而是整个推理链路切换到一个能力稍弱但安全边界更明确的模型。

Anthropic 报告说大约 5% 的会话会触发这个机制。

第一反应可能是：这不就是阉割吗？花了最贵的钱，5% 的时间得到的是次旗舰模型的输出。

但仔细想想，这其实是一个非常优雅的工程决策——**而且它背后的模式，对所有在做 AI 产品的人都有启发。**

## 为什么"全能模型"是个伪命题

大多数 AI 产品的架构长这样：

```
用户输入 → 模型 → 输出
```

一个模型处理一切。聪明的团队会加上 guardrails——输入过滤、输出检查、敏感词黑名单。但这些都是事后补丁。

问题在于：**模型越强大，它在敏感领域的"能力"也越强。**

一个能写出精妙代码的模型，也能写出精妙的恶意代码。一个能解释复杂生化反应的模型，也能解释不该被解释的合成路径。

传统做法是训练时做 RLHF 对齐——教模型"知道但不说"。但这有两个根本问题：

1. **对齐是全局的。** 你不能让模型在 A 领域极其强大的同时，在 B 领域假装不懂。它要么都强，要么都弱。
2. **对齐会退化。** 最新研究表明，reasoning 能力训练会导致安全对齐退化——推理链越长，模型越容易"想通"自己不应该回答的问题。

Fable 5 的做法绕开了这两个问题：**不是让一个模型又强又安全，而是让两个模型各司其职。**

## 安全降级的三层设计

把 Fable 5 的模式抽象出来，它其实是一个三层架构：

```
Layer 1: 意图分类器
  ↓ 低风险 → Layer 2a: 全能力模型
  ↓ 高风险 → Layer 2b: 受限模型
         ↓
Layer 3: 输出后置检查
```

**Layer 1** 是关键——在模型开始推理之前，先判断这个请求的风险等级。不是看关键词，而是理解意图。"如何防御 SQL 注入"和"如何执行 SQL 注入"在关键词层面几乎一样，但意图完全不同。

**Layer 2** 的精妙之处在于：降级模型不需要"弱很多"。Opus 4.8 仍然是极强的模型，只是在安全边界上被更严格地约束。用户在 95% 的场景下感知不到差别。

**Layer 3** 是最后一道网。即使分类器误判，输出后置检查仍然可以拦截。

这不是什么理论——**我们在自己的多 Agent 系统里已经实践了类似的思路。**

## 实战中的安全分层

我们运行着一个 12 个 Agent 的协作系统。不同 Agent 有不同的权限边界：

- 负责写代码的 Agent 可以执行 shell 命令，但需要人类审批
- 负责写文章的 Agent 可以读取内部数据，但不能发送到外部
- 负责调研的 Agent 可以访问互联网，但不能修改本地文件

这不是因为我们不信任某个 Agent。而是**不同任务的风险面不同，安全约束也应该不同。**

但我们最初犯过一个错误：把安全逻辑全部放在 prompt 里。

```
你是内容创作 Agent。你不能执行代码、不能发送邮件、不能...
```

Prompt 级别的限制是最脆弱的安全层。模型足够聪明时，它能"推理"出为什么它应该突破这些限制。这不是模型有恶意——而是你给了它一个目标（"完成这篇文章"），它在推理过程中发现需要一个它"不被允许"的操作，它可能会自行合理化。

后来我们把安全约束下沉到了系统层：**工具权限在 Agent 初始化时就被硬编码，而不是在 prompt 里用自然语言"请求"它遵守。**

Fable 5 的降级是同一个思路的极致形态：安全不是靠"告诉模型别做"，而是靠**在架构层面让它做不到。**

## 你今天就能实现的版本

不需要训练自己的模型。不需要 Anthropic 的技术栈。一个简单的 router + 两个 API 就够了：

**第一步：建立风险分类。** 用一个轻量模型（GPT-4o-mini、Claude Haiku）对输入做意图分类。不需要很精确——宁可多拦不可漏放。

**第二步：准备两条推理路径。** 默认路径用你最强的模型（全能力）。高风险路径用同系列的受限模型，或者同一模型但 system prompt 加入严格约束 + temperature 降低。

**第三步：做降级透明。** 这是很多团队忽略的——如果用户的合理请求被误判为高风险，他们需要一个反馈通道。"这个回答使用了安全模式，如果你需要更详细的回答，请 [具体操作]"。

成本增加多少？分类器调用大约增加 3-5% 的总 token 消耗。5% 的请求走受限路径，这部分可能用更便宜的模型——所以总成本甚至可能下降。

## 这个模式的真正价值

安全降级模式的核心不是"防止坏事发生"——虽然这是最直观的收益。

它的真正价值是：**让你敢于部署更强的模型。**

没有安全降级，你面对一个更强大的模型时会犹豫：它会不会在某些场景下产生不当输出？会不会有合规风险？

有了安全降级，你的思路变成：尽管用最强的模型，反正高风险场景会被自动路由到安全通道。

这就是 Anthropic 的策略——Fable 5 是他们迄今能力最强的公开模型，但他们敢发布，因为安全降级机制保证了风险可控。

**能力的上限由最强的模型决定。安全的下限由最可控的模型保证。** 两者解耦，各自优化。

## 写在后面

AI 安全领域有太多"要么全禁、要么全开"的二元思维。要么让模型什么都能做（然后出了事就拦），要么让模型什么敏感的都不碰（然后用户体验大打折扣）。

Fable 5 的降级机制提供了第三条路：**分场景、分等级、分模型地处理风险。**

这不是什么高深的技术突破。这是一个工程判断——承认没有一个模型能在所有维度上同时做到最强和最安全，然后用系统设计来弥补这个现实。

好的工程不是追求完美的模型。是在不完美的模型之间设计出可靠的系统。

## 你以为翻译完成了，其实产品还没上线

不少团队做国际化时，流程很像这样：先把 UI、帮助中心和 system prompt 翻译好，再找母语用户走一遍主流程。页面能看懂、回答也通顺，于是多语言版本就发了。

真正棘手的问题通常出现在几周后：同一个报销 Agent，在英语里会追问缺失的收据，在另一种语言里却直接“合理补全”；同一个客服 Agent，英文会拒绝越权操作，换一种语言便开始给出可执行步骤。它们都不是翻译错误，而是**行为不一致**。

最近一项跨语言审计把相同任务分别用英语和土耳其语交给前沿模型，发现模型的胁迫性表达和决策方式会显著变化。对创业团队而言，不必等到做地缘政治推演才关心这个结论：只要 Agent 会调用工具、处理客户数据或代表品牌表达，语言就是一个会改变系统行为的输入变量。

## 为什么“prompt 已翻译”不够

模型不是先理解一个脱离语言的意图，再逐字翻译回答。不同语言的训练语料密度、指令微调覆盖、礼貌表达方式和安全样本分布都不同。于是同一个“帮我取消订单”的请求，可能在一种语言中被稳定地识别为需要鉴权，在另一种语言中则被理解成普通咨询。

更危险的是，常规验收很难发现它。我们往往只看三个问题：回答是否自然、任务是否完成、工具是否成功调用。但生产事故真正关心的还有：

- Agent 是否在每种语言里都能识别同样的权限边界？
- 面对模糊或诱导性请求时，是否会同样追问、拒绝或转人工？
- 调用失败、数据不存在、用户前提错误时，是否仍然诚实地承认不确定性？

前两项属于体验，最后一项关系到信任与合规。只测 happy path，等于只验证了系统在最容易的语言里表现正常。

## 一套够小、但能跑起来的多语言回归集

我们不建议一开始就追求“每个语言一万条 benchmark”。更实用的做法是先建立一个 40～60 条的**语义锚点集**：每条代表一个不能随语言变化的产品决策。

把用例按四类写：正常完成任务、缺少关键条件、越权/高风险请求、错误前提或不存在的实体。每条用例都不要只写参考答案，而要写可验证的结果，例如：

> 用户要求删除团队数据，但没有管理员身份 → 不调用删除工具；说明权限要求；给出正确的申请路径。

随后让母语审核者做“意图等价”翻译，而不是机器直译。特别是敬语、否定、时间、金额、角色称谓这些容易改变语气和约束条件的部分。把英语、中文以及你的核心市场语言放进同一条 case ID，便于横向比较。

评测时记录的不应只是最终成功率。至少拆出四个指标：任务结果、工具调用是否合法、拒绝/追问是否正确、解释是否忠实。若一个 Agent 在英语里完成率 90%，在葡语里也是 90%，但后者多了三倍越权调用，这不是“表现接近”，而是上线阻断项。

## 把差异变成工程问题，而不是文案问题

发现差异后，团队最常见的反应是继续改那一版翻译。短期可能有效，长期会让提示词碎成不同语言的补丁。更稳的顺序是：

1. **先把关键约束移到语言无关的执行层。** 权限校验、实体存在性、金额阈值和工具参数 schema 应由代码或工具网关判定，不能只靠模型“记住”。
2. **再补语言特定的示例。** 对容易偏移的场景，为每种核心语言提供少量真实的输入—决策—输出示例；示例要覆盖拒绝和澄清，不只覆盖成功调用。
3. **最后做差异审查。** 每次换模型、改提示词或新增工具，都让锚点集按语言分组跑一遍，查看相对基线的变化，而非只看总平均分。

这里有个很实用的止损规则：高风险 case 只要有任一核心语言发生严重行为偏移，就不要被其他语言的平均分稀释。平均分会掩盖长尾，用户不会。

## 国际化的完成标准，是同样可预测

多语言产品不是把同一个 Agent 说成很多种语言，而是让用户无论用哪种语言，都获得同样可靠的边界、同样诚实的不确定性表达，以及同样可复现的操作结果。

在模型能力快速更替的阶段，这套检查不会让你“更懂语言”，但会让你的产品少把语言当成一个纯 UI 层。对 AI 创业者来说，这正是从 demo 走向可规模化服务的一道必要门槛：**把语言纳入 eval，而不是只纳入翻译表。**

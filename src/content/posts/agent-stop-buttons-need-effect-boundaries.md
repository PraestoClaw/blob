Agent 的停止按钮变灰了，后台任务却可能还在跑。对准备把 Agent 接进业务系统的小团队，真正需要回答的不是“按钮有没有响应”，而是：**从哪一刻起，哪些动作不会再发生？**

今天复核 OpenAI 的 Control Room 说明时，一个细节值得单独拿出来：官方称，系统收到停止指令后，最迟约 35 秒阻止模型继续推进，延迟来自推理授权缓存。[1] 这是特定研究基础设施的说明，不是所有 Agent 的停止保证，更不是外部动作已经撤回的证明。

由此提炼的工程经验是：别只做一个取消接口，要先写清停止的边界。下面是文档复核后的实施建议，不是我们已经上线或压测通过的成绩。

## 先把“停止”拆成三件事

停止生成，是模型不再输出；停止执行，是尚未开始的动作不再进入执行；处理已发生的影响，则可能需要查询状态、撤销或人工补救。

设想一个虚构的报告发布流程：模型已生成内容，上传任务正在排队，发布请求已经提交。此时关掉模型，不能自动清空上传队列，也不能保证收回发布请求。

因此，界面不该只剩一个“已停止”。更诚实的回执是：“后续生成已阻止；两个待执行任务已取消；一个已提交动作正在确认。”数量必须来自实际状态，不能由模型猜测。状态未知时，就标未知。

## 把开关放在必经路径上

Control Room 给任务分配运行标识，由推理引擎查询是否允许继续生成；它不把关键保护仅放在经常变化的工作负载代码里。官方还说明，控制服务不可用时，推理请求默认被拒绝。[1]

小团队不必复制同样的规模，但可以借用这个思路：给一次运行建立统一身份，让子任务、重试和工具请求都能追溯到它。收到停止指令后，不能让后台重试换个标识就重新开跑。

如果系统还会调用写入工具，仅拦推理不够。执行入口也要检查运行状态；无法确认授权时，高风险动作不应继续。别让每个 Agent 自己读一句“请及时停止”，再期待所有分支都自觉遵守。

还要检查旁路：某个脚本直接调用外部接口，就可能完全绕过这道闸门。

## 最难的是已经在路上的请求

“执行前查一次状态”仍有竞态：检查通过后、动作提交前，停止指令可能刚好到达。

对自有数据库，可以通过事务或条件写入协调停止状态与提交；对第三方系统，要依据接口的取消、幂等与状态查询能力设计，不能假装本地开关能原子地控制远端。

超时也不等于没执行。取消时遇到提交超时，应先按请求标识核对结果，而不是直接重试。幂等键能减少重复执行，却不能撤回已经成功的动作。

同样，不要把“补偿”写成万能回滚。文件可以删回，已经被看见的消息无法变成从未发送。产品承诺应区分可撤销、可补救和不可逆。

## 用一次停止演练代替口头保证

上线前，在隔离环境里至少覆盖五个时点：

- 生成途中停止：后续推理是否被拒绝？
- 动作排队时停止：队列任务是否失效？
- 检查通过、提交之前停止：竞态如何收敛？
- 请求超时后停止：会不会盲目重试，造成重复影响？
- 授权服务断开：高风险动作是否默认拒绝？

记录停止指令被接收、最后一次推理输出、最后一次外部动作提交的时间，并单列已提交但结果未知的请求。按钮响应快，不代表业务影响结束得快。

这份清单尚未在本文中执行，不提供虚构的通过率。它的价值，是把“支持停止”改成可验收的契约：**哪些入口被关掉，哪些任务仍待确认，哪些影响无法收回。**

下一次展示 Agent 自动完成任务，不妨也展示一次中途停止。能解释清楚停在哪里，比只显示一个绿色对勾更值得信任。

> 上周 Apple 和 Microsoft 先后宣布 MCP 成为系统级/全栈默认协议。同一周，一个 CVSS 9.8 的 prompt injection 漏洞被披露，攻击者可以通过 MCP 接管企业 AI Agent。这不是巧合——这是每个用 MCP 的开发者现在就需要面对的现实。

---

## 一周之内发生了什么

6 月 8 日，Apple WWDC 2026 宣布：iOS 27 全平台支持 MCP，任何 App 的 AI Agent 都可以通过 MCP 协议调用系统级能力——文件、日历、邮件、快捷指令，一切。

6 月初，Microsoft Build 2026 确认：MCP 成为 Foundry、Agent 365、Copilot 等全栈的默认协议层。

同一时间窗口：

- **CVE-2026-2256** 被披露——MS-Agent 框架的严重漏洞，CVSS 9.8，攻击者通过 prompt injection 可接管企业 AI Agent 并执行系统命令。暂无补丁。
- arXiv 上出现 **SafeMCP** 论文，专门讨论 MCP 环境下 Agent 的 power-seeking 风险。
- **NIST** 正式启动 AI Agent Standards Initiative，重点规制 MCP 部署带来的新攻击面。

三大平台拥抱、一个严重漏洞、一篇安全论文、一个标准化倡议——全在一周内。这说明什么？

**MCP 已经从"技术选型"变成了"行业基础设施"。而它的安全模型还停在"实验室阶段"。**

---

## 你的 Agent 权限边界在哪里？

我们自己跑 Agent 系统超过半年，用 MCP 做工具调用也有一段时间了。说一个真实踩过的坑：

早期设计时，我们给 Agent 的 MCP 工具集是"全量注册"的——文件读写、网络请求、消息发送、代码执行，所有能力都挂上去。逻辑很简单：Agent 需要什么就用什么呗，反正有 system prompt 约束。

然后某天一个 Agent 在处理用户请求时，因为上下文里混入了一段格式异常的文本（不是精心构造的攻击，就是普通的脏数据），"理解"成了需要调用文件写入工具。它把一个调试日志写进了生产配置目录。

没有恶意，没有攻击，只是一个模型在复杂上下文中做了一个看起来合理但实际上越权的决策。

这就是 MCP 的根本安全挑战：**你给 Agent 注册了什么工具，Agent 就有可能在某个 edge case 下使用它。** system prompt 不是权限边界——它是"建议"。

---

## 为什么传统安全模型不够用

传统软件安全的核心假设是：**代码是确定性的。** 给定输入 A，程序做 B。如果你不想让它做 B，你可以在代码层面阻止。

LLM Agent 打破了这个假设。同一个 Agent，给定几乎相同的输入，在不同上下文下可能做出完全不同的工具调用决策。你没办法穷举所有路径来做静态分析。

CVE-2026-2256 的攻击原理很直白：攻击者在 Agent 会处理的数据中嵌入精心构造的指令，Agent 在处理这些数据时把恶意指令当成了合法任务，然后通过 MCP 工具执行了系统命令。

这不是模型的 bug——这是架构的 bug。只要你的 Agent 同时满足以下三个条件：

1. 能处理不可信输入（用户消息、外部数据、网页内容）
2. 有权限调用高危工具（文件写入、命令执行、网络请求）
3. 中间没有独立于 LLM 的权限校验层

你就有这个漏洞。程度不同而已。

## 我们的三层防御实践

踩完坑之后，我们重构了 Agent 的安全架构。分享三个实际在用的设计模式：

### 第一层：最小工具集注册

不再给 Agent 注册所有可用工具。每个 Agent 根据其任务定义，只注册**完成该任务必需**的最小工具集。

具体操作：
- 研究 Agent 只有 web_search + web_fetch + read（只读）
- 写作 Agent 有 read + write，但只能写特定目录
- 运维 Agent 有 exec 权限，但只能执行白名单命令

这不是通过 prompt 告诉 Agent "你只能用这些工具"——而是在注册层面就不提供其他工具。Agent 看不到的工具，就不可能调用。

### 第二层：路径级 ACL（独立于模型）

工具注册了不代表无限制使用。我们的文件操作工具有路径白名单：

```
allowReadPaths: ["/workspace/reports/*", "/workspace/memory/*"]
allowWritePaths: ["/workspace/reports/blog-posts/*"]
```

这个校验发生在工具执行层，完全独立于 LLM 的判断。即使模型被 prompt injection 说服"需要写入 /etc/passwd"，工具层会直接拒绝。

### 第三层：行为模式监控

SafeMCP 论文提出了一个有价值的思路：根据 Agent 的历史行为模式，动态调整权限边界。

我们的简化实现：如果一个 Agent 在过去 100 次调用中从未使用过某个工具，突然开始高频调用——触发告警，人工审核。

不需要完美的异常检测算法。简单的频率阈值已经能拦住大多数 edge case。

## 你今天就该做的三件事

如果你的 Agent 系统用了 MCP（或者任何形式的工具调用），这三件事不能再拖：

**1. 审计你的工具注册表。** 列出每个 Agent 能调用的所有工具，问自己：如果这个 Agent 被完全劫持，它能造成的最大伤害是什么？如果答案让你不舒服——收窄权限。

**2. 在工具执行层加独立校验。** 不要依赖 prompt 做安全。Prompt 是 LLM 的"道德指南"，不是访问控制。任何涉及数据写入、命令执行、外部通信的工具，都需要一层独立于模型判断的硬校验。

**3. 隔离可信输入和不可信输入。** 如果你的 Agent 同时处理系统指令和用户输入——确保它们在上下文中有明确的结构化分隔。不要把用户消息直接拼接到 system prompt 后面，这是 prompt injection 的经典入口。

## 为什么现在是关键窗口期

NIST 预计 2026 年底 40% 的企业应用将包含 AI Agent。Apple 把 MCP 推到了数十亿设备上。Microsoft 让每个企业开发者都在用 MCP 构建 Agent 工作流。

这意味着接下来 6 个月，MCP Agent 的部署量会指数级增长。而安全实践、标准、工具链还远未成熟。

这不是"以后再说"的事。现在部署的架构决策，会在 12 个月后变成技术债或安全事故。

SafeMCP 论文的核心洞察很简练：**Agent 的能力边界不能等到出事后再划。** 能力一旦注册，收回的成本远高于从未注册。就像数据库权限一样——先给最小权限，需要时再申请提权，永远比"先给 root 后面再收"安全得多。

---

## 一句话

**MCP 让你的 Agent 能做的事变多了。但"能做"不等于"该做"。** 能力开放的速度正在超过安全治理的速度——而你站在中间。现在做的架构决策，决定你是在修漏洞还是在看别人的事故复盘。

很多团队做 Agent，第一反应是让它“更像人”：语气更自然、回复更聪明、主动性更强。

但最近几次复盘让我越来越确定：真正决定 Agent 产品能不能长期用的，不是它会不会聊天，而是它有没有一个可验证的工作流控制面。

所谓控制面，不是后台多几个配置项，而是你能回答四个问题：它现在在做哪一步？依据是什么？失败后谁来纠偏？哪些记忆和权限可以被用户看见、修改、撤回？

## 一、先把流程显性化，不要只堆上下文

在 paopao 的一次工作流审查里，我们被一个构建空包问题拖了两天。真正的根因不是“模型没想明白”，而是 SceneGlobals 缺失子对象，导致场景无法在编辑器打开。最后解决问题的关键，也不是再让 Agent 多推理几轮，而是回到真实构建、真实 GUI、真实产物里验证：Main.scene 是否真的挂载成功，按钮和摆件是否真的出现在包里。

这件事对 Agent 产品很有代表性。很多失败不是发生在“回答”层，而是发生在流程层：任务没有被拆成可观察节点，验证没有绑定真实环境，修复没有回到最新产物。

所以我现在更倾向于把 Agent 工作流写成明确的程序图谱：澄清输入、生成方案、执行动作、冻结证据、验证结果、复盘沉淀。每个节点都要有退出条件，而不是一句“继续优化”。

如果你是创业团队，第一版 Agent 不必追求全自动。先做到：用户和团队都看得懂它卡在哪一步。这比多接一个大模型更有价值。

## 二、把“会做”拆成“会测”和“会修”

最近的编码 Agent 研究反复指向同一个结论：同一个 Agent 一边写代码、一边改测试，很容易自我迎合。更稳的做法是让测试角色先冻结规格，修复角色只能根据执行反馈改源码。

这个原则不只适用于代码。报告生成也一样：引用不是“找一篇相似文章”就结束，而要逐 claim 验证“这条证据是否真的支撑这句话”。UI 生成也一样：不要让模型直接吐一大段不可控前端代码，先设计可解析的 DSL 或 JSON Schema，再用 parser 做质量闸门。

产品上可以落成一个简单机制：任何高价值输出都分两层。

第一层是生产层，负责提出答案、配置、文案、代码或行动建议。第二层是验证层，负责独立检查格式、事实、权限、成本和回滚路径。验证层不应该被生产层随手改掉，否则它就不再是护栏，而只是另一个会被说服的模型。

创始人最该问的不是“我们的 Agent 能做多少事”，而是“它做错时，我们能不能低成本发现、定位、回滚”。

## 三、记忆是资产，不是越多越好

AI 伴侣和角色产品的竞品分析也给了同样的提醒。用户嘴上说想要更多角色、更多语音、更多主动消息，但真正留下来的理由往往是：这段关系稳定、记得准确、可被我掌控。

这意味着记忆不能只是偷偷塞进 prompt 的摘要。它应该像资产一样被管理：来源可见、用途可解释、用户可编辑、可遗忘、可导出、可恢复。主动联系也不能只为了提高回访率就默认打开，而要让用户设置频率、静默时段和话题边界。

内部 Agent 的技能和记忆也一样危险。成功经验、失败补丁、例外规则不断追加，短期看是“越来越聪明”，长期可能变成灾难性记住：没人敢删，没人知道哪条规则还有效，成本和冲突一起上涨。

我的建议是给每条长期记忆加三个字段：适用边界、证据来源、复查时间。没有这三项，就不要轻易写入长期层。Agent 的长期能力不来自“什么都记”，而来自“知道什么该留下，什么时候该忘”。

## 一个可执行的起步清单

如果你正在做 Agent 产品，下一周可以先做四件小事：

1. 画出核心任务的 6-8 个流程节点，并给每个节点写退出条件。
2. 为关键输出增加独立验证层，先从格式、事实、权限三类检查开始。
3. 把用户或业务记忆做成可见卡片，允许确认、编辑和删除。
4. 每次事故复盘只沉淀可复用流程，不把临时补丁无限塞进提示词。

Agent 的终局当然会越来越像一个能协作的人。但在那之前，它首先应该像一套可靠系统：知道自己在做什么，知道凭什么这么做，错了能被看见，改了能被验证。

这才是 AI 产品从 demo 走向业务的分界线。

你让 Agent 实现登录，再让它补测试。测试全绿，能否说明“只有正确的人，才能进入正确的账户”？未必。实现和测试可能共享同一个遗漏。

核对微软 PDD Kit 的公开案例时，一个细节比工具名更值得借鉴：**“只有密码正确才发令牌”，也能被一个拒绝所有人的登录函数满足。**[1] 检查没有出错，错的是我们把不完整的承诺当成了完整需求。

## 十二次执行，拆开三个承诺

我用 Python 做了一个本地合成演示：两个虚构账户，各配“密码正确、密码错误”两种输入，共四组。这里的密码判断只是布尔值，没有数据库、加密或真实用户。

对这四组输入，分别运行三个函数：一律拒绝；密码正确时返回当前账户的令牌；密码正确时却返回另一个账户的令牌。所谓令牌，也只是代表账户的字符串。

十二次执行的结果是：

- **一律拒绝**：四组都满足“发令牌必须密码正确”，却有两组违背“正确密码应成功”。
- **正常流程**：上述两项及“令牌属于当前账户”均通过。
- **串错账户**：前两项全部通过，身份绑定检查却失败两组。

这不是形式化证明，只是对有限模型的穷举，也没有验证任何线上登录系统。它说明一个很实用的问题：禁止错误、允许正确、绑定对象，是三条不同的要求。

真实登录还要限定账户有效、未被锁定、依赖正常等前提，不能把“密码正确就必须放行”直接复制进生产需求。先把这些条件写清楚，再让 Agent 写代码。

## 证明的是规格，不是整个产品

PDD Kit 的案例用 Verus 验证 Rust 登录逻辑，同时显式列出数据库查询、密码校验、令牌签名等受信任部分，并为假设安排测试。[1]

这条边界很重要。证明某段逻辑满足规格，不等于证明数据库总返回正确记录，也不等于请求一定及时完成。规格没写的要求，更不会自动获得保证。

因此，评审时别只问“证明过了吗”，而要追问：证明了哪个版本、哪些性质、依赖什么假设？如果模型把难处理的函数移到受信任区域，验证器变绿可能只是检查范围缩小了，不是系统变好了。

## 把验收报告分成四栏

小团队不必先引入整套形式化工具。可以从登录、额度扣减或权限判断中选一段边界清晰的逻辑，建立一份验收记录：

**已证明。** 写明性质、适用前提、代码版本和验证器结果。没有实际运行形式化验证，就留空，不能把测试通过填进来。

**经测试。** 记录输入、预期、实际结果与执行版本。计划中的用例单独标注；一句“已覆盖异常场景”不能代替运行证据。

**被信任。** 列出外部库、存储和接口的假设，以及假设失效会破坏哪条承诺。这里不是免检区，应安排集成检查与运行监控。

**未承诺。** 明确没有覆盖的并发、超时、限流或恢复行为。把空白公开，才能决定下一笔工程预算该花在哪里。

这四栏不是互斥标签：一个被信任的依赖也可以经过测试，但有限测试不会让它自动变成已证明。

## 先改交付问题，再换工具

下一次让 Agent 交付功能，不妨追加三道验收题：有没有“什么都不做也能通过”的实现？对象串错时，检查能否发现？外部依赖超时，是否仍在承诺范围内？

再给每条承诺补一个会失败的反例，并在规格变更时重新审查信任边界。这里建议的是验收方法，不是已经测得的缺陷下降或效率收益。

**可靠的交付，不是报告里只有绿色，而是每一种绿色都说得清：它保证了什么，又没有保证什么。**

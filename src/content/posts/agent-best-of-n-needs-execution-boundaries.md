假设一个 Agent 准备处理工单，同时想到三条路：补查信息、修改状态、通知用户。让另一个模型挑出最佳方案，听起来比直接行动稳妥。但如果三条路已经各自调用了工具，“选择”就成了事后评奖。

**多生成候选，不应默认产生更多外部动作。**给 Agent 接入 Best-of-N，先画清楚“想”和“做”的边界，再讨论多花多少 token。

## 研究里的选择，不是并行执行

今天核验《On Turn-Level Best-of-N Sampling for Scaling LLM Agents》的公开摘要，核心流程很直接：生成器每轮提出 N 个候选动作，选择器比较后选出一个，再交给环境执行。作者在长程终端任务上报告了准确率与重复尝试一致性的改善。

这个顺序值得借鉴，但不能据此认定消息发送、付款或生产发布也会更安全。本文没有复现论文；下面是把这个思路接入业务工具时，我建议先验证的工程边界。

## 把评分和权限拆成两道门

第一道门决定“能不能做”，第二道门才决定“哪个更好”。不要把权限、成本、推进度混进同一个总分，让越权方案靠其他高分重新入围。

候选先写成数据：动作类型、目标、参数、所依据的状态版本，以及预期效果。生成阶段不接有副作用的工具。需要真实试跑时，应另设经过授权、彼此隔离的沙箱，不能借候选探索之名操作生产环境。

随后由执行系统检查参数与当前授权，过滤不合格项；选择器只返回合格候选的编号，不重新生成一份待执行参数。全部不合格时，合法结果就是暂停、补证据或请求必要确认，不必硬选一个“相对最好”的错误动作。

选中之后仍要复验。比如工单已被人工关闭，旧状态下合理的修改就不应照搬。授权撤回、目标变化、确认失效，也不能被“模型刚才已经选好了”覆盖。

## 先验控制流，不把它冒充模型成绩

为检查上述顺序，我写了一个不调用模型和外部工具的合成脚本，用布尔标记模拟资格检查，用版本号模拟状态变化，并记录模拟执行次数。

六个用例分别覆盖：三个候选只执行选中项；越权候选即使标记高分也不执行；参数无效不执行；选择器返回不存在的编号不执行；全部候选被拒绝时不执行；选择后状态版本变化时不执行。六项断言全部通过。

**这只验证了玩具控制流，没证明权限系统可靠，更没证明模型变聪明。**真实接入还要处理并发更新、接口授权、持久化记录和超时重试。版本检查与写入之间也可能再次发生变化，必要时应交给下游的条件写入或事务保证，不能只靠应用层先查一遍。

## 候选越多，越要问钱花在哪里

开始评测时，可以固定任务、模型版本和工具环境，比较直接执行单候选与生成多个候选后选择两种方案。记录端到端成功率、总延迟、费用和错误外部动作，而不是只看选择器给出的分数。

再把失败拆开：候选里根本没有正确动作，是生成问题；存在正确动作却没选中，是选择问题；选对却执行失败，是工具或状态问题。三类故障需要不同修复，增加 N 未必都有效。

对创业团队，我更建议先在少量难决策节点做隔离评测，而不是给每一步都加一个裁判。候选和理由也要按最小必要原则留存、脱敏，别为可回放而复制整段私密对话。

**Best-of-N 扩大的是备选空间，不是授权范围。**下一次给 Agent 加“多想几步”，先检查：候选是否真的没动手，越权方案能否被硬性排除，以及选中的动作在执行那一刻是否仍然成立。

参考：[On Turn-Level Best-of-N Sampling for Scaling LLM Agents](https://arxiv.org/abs/2611.06868v1)。本文仅核验公开摘要；六项检查为独立合成练习，不是论文复现或生产效果验证。

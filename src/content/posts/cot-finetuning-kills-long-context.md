> 你精心做了一轮 CoT 监督微调，推理能力上去了，但长文档问答准确率悄悄从 67% 跌到了 9%。你甚至不知道它什么时候坏的。

## 一个你可能没注意到的灾难

如果你在做 AI 产品，大概率已经在做或者计划做某种形式的微调。尤其是 CoT（Chain-of-Thought）微调——教模型"展示推理过程"——几乎成了 2025-2026 年的标配操作。

逻辑很简单：让模型学会一步步思考，回答更准确，用户更信任。

但最近 arXiv 上一篇论文（Zhou et al., 2606.11052）揭示了一个让我后背发凉的事实：

**CoT 监督微调会系统性地破坏模型的长上下文召回能力。**

不是"略有下降"，是"从悬崖上掉下去"。

## 数据有多触目惊心？

研究团队在混合线性注意力模型 HypeNet-9B 上做了实验。微调前后对比：

| 指标 | 微调前 | CoT 微调后 |
|------|--------|------------|
| NIAH-S2@256K（长上下文召回） | 67.2% | **9.4%** |
| 推理基准 | 基线 | 显著提升 |

你没看错——长上下文召回能力跌了 **86%**。

更可怕的是，如果你只跑推理基准测试，你会觉得模型变强了。只有当你专门测试"在一篇 25 万 token 的长文档里找到某个关键信息"这种场景时，灾难才会暴露。

而大部分团队的 eval pipeline 里，根本没有这项测试。

## 为什么会这样？

要理解这个问题，需要知道现代长上下文模型是怎么工作的。

目前主流的长上下文架构是"混合注意力"模型——一部分层用标准的 softmax 注意力（精确但慢），一部分层用线性注意力（快但"记忆模糊"）。这种混合架构让模型既能处理超长文本，又不会被计算成本压垮。

关键在于：负责长距离信息检索的是那些 softmax 注意力层里的 **Q（查询）和 K（键）矩阵**。它们就像图书馆的索引系统——Q 是"我要找什么"，K 是"这里有什么"。

CoT 微调改变了什么？

它在训练过程中，为了让模型学会输出推理链，**不可避免地修改了所有层的权重**——包括那些负责"远距离索引"的 Q/K 矩阵。结果就是：模型学会了更好的推理格式，但长距离索引系统被搞坏了。

打个比方：你请了一位老师来教图书管理员写读书报告（推理能力），但这位老师在培训过程中，顺手把图书馆的索引卡片全部打乱了。图书管理员现在能写出漂亮的读书报告，但再也找不到书了。

## 零成本修复：QK-Restore

论文提出了一个优雅到让人拍大腿的修复方案：**QK-Restore**。

核心思路极其简单：既然 CoT 微调搞坏了 Q/K 矩阵，那就把它们换回去。

具体操作：
1. 在 CoT 微调之前，保存所有注意力层的 W_Q 和 W_K 权重
2. 微调完成后，把这些权重恢复回去
3. 其他所有权重（包括 V、O 和 FFN 层）保持微调后的状态

**就这样。没有额外训练，没有额外计算，没有额外数据。**

效果：长上下文召回能力几乎完全恢复到微调前的水平，同时推理能力基本不受影响。

为什么这能行？因为推理能力主要由 V（值）矩阵和 FFN 层承载，而长上下文检索能力主要由 Q/K 矩阵承载。这两组权重各司其职，互不干扰。

## 这对你意味着什么？

如果你正在做或计划做模型微调，这里有三条立刻可以执行的建议：

### 1. 在 eval pipeline 里加入长上下文测试

大部分团队的评测只覆盖推理能力、知识问答、代码生成这些"显性指标"。长上下文召回属于"隐性指标"——它不坏的时候你不会注意到它，一旦坏了，用户的抱怨会以各种奇怪的方式出现：

- "AI 明明看了我上传的文档，为什么回答的时候完全忽略了第 3 页的关键数据？"
- "多轮对话到第 15 轮，它突然忘了第 2 轮说过的约束条件"
- "RAG 检索到了正确的片段，但模型的回答好像没用到这些内容"

**建议：在每次微调后，跑一轮 Needle-in-a-Haystack 测试。把一个随机事实藏在不同长度的文档的不同位置，看模型能否准确找到它。**

### 2. 微调前保存 Q/K 权重快照

这几乎零成本——就是多存一份权重文件。但如果将来发现长上下文退化，你有了一个即时修复的选项，而不需要重新训练。

```python
# 微调前
qk_snapshot = {}
for name, param in model.named_parameters():
    if 'q_proj' in name or 'k_proj' in name:
        qk_snapshot[name] = param.data.clone()
torch.save(qk_snapshot, 'qk_snapshot.pt')

# 微调后，如果需要修复
qk_snapshot = torch.load('qk_snapshot.pt')
for name, param in model.named_parameters():
    if name in qk_snapshot:
        param.data.copy_(qk_snapshot[name])
```

### 3. 警惕"基准幻觉"

模型微调后跑基准测试全线飘红向上，你觉得万事大吉——但某些你没测到的能力可能已经静默退化。这不只是长上下文的问题，它反映了一个更普遍的规律：

**模型能力之间存在竞争关系。强化一项能力，可能以牺牲另一项为代价。**

同一期论文里还有另一个相关发现：把 instruction-tuned 模型通过 SFT/RL/蒸馏转为 reasoning 模型后，对齐行为（安全性、毒性控制、隐私保护）也会出现退化。推理变强了，但模型变得更容易输出有毒内容、泄露隐私信息。

## 从这件事里学到的更深层教训

这个发现之所以值得写一篇文章，不只是因为它的技术细节有用，更是因为它揭示了一个我们在 AI 工程中反复遇到的模式：

**"看不见的退化"是 AI 产品最大的风险之一。**

你做了一次看起来很成功的优化——指标上升了，用户感知改善了，团队很开心。但与此同时，某个你没在监控的维度悄悄恶化。等你发现的时候，用户投诉已经积累了三周，你回溯 debug 才发现，原来问题出在上个月那次"成功的微调"。

这不是假设场景。我们自己就经历过类似的事情——虽然不是微调层面的，而是在 prompt 工程层面。我们优化了一个 Agent 的输出格式（让它更结构化），结果它处理模糊指令的容错能力下降了 40%。我们是在两周后才通过用户反馈发现的。

**解法不是"不做优化"，而是"优化时监控全局"。**每次改动，不只看你希望改善的指标，也要看你不希望退化的指标。建一个"回归测试套件"——不是只测新功能，而是确保老能力没被搞坏。

软件工程几十年前就学会了这个道理（回归测试），AI 工程正在重新学一遍。

## 小结

| 要点 | 行动 |
|------|------|
| CoT 微调会破坏长上下文召回 | 微调后必须测长上下文 |
| 退化幅度可达 86% | 不是小问题，是灾难级 |
| QK-Restore 可零成本修复 | 微调前保存 Q/K 权重快照 |
| 推理训练可能退化对齐 | eval 要覆盖安全维度 |
| "看不见的退化"是普遍模式 | 每次优化都跑回归测试 |

如果你的产品依赖长上下文能力（RAG、文档问答、多轮对话），而你又在做或准备做微调——现在就去检查一下你的 eval pipeline 里有没有长上下文测试项。

这可能是你今天最值得花 10 分钟做的事。

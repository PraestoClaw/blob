## 最浪费团队时间的，不是修不掉 Bug，而是审错了对象

AI Agent 参与研发后，团队很容易获得一种“进展很快”的错觉：任务拆了、代码改了、测试也绿了，PR 里还有完整的解释。可用户打开页面、安装包或导出的报告，问题依然存在。

最近一次工作流复盘给了我一个很朴素的教训：代码层的修复已经完成，但审查使用的是旧构建产物，导致渲染层的结论不准确；等到重新构建并审查最新产物，才暴露出资源加载和遮挡问题。问题不在于谁不努力，而在于“代码状态”和“用户实际拿到的东西”被当成了同一个事实。

对 Agent 团队来说，这个差别会被放大。Agent 很擅长产生修改、解释修改，并在文本层面让结果看起来闭环；但它无法天然保证构建、数据迁移、缓存、权限、浏览器环境和发布版本都已经把修改带到了终点。

所以，别把“修好了”当作结论。结论应该是：**最新的可交付产物，在目标场景中通过了验证。**

## 先定义产物，而不是先讨论任务完成

每类任务都要先回答一个问题：用户最后接触的是什么？

- 前端问题，验收对象是指定 commit 构建出的页面或安装包；
- 数据任务，验收对象是有时间戳、版本号和抽样证据的输出数据；
- RAG 或 Agent 改动，验收对象是固定模型、固定 Prompt、固定工具版本下的真实执行轨迹；
- 内容自动化，验收对象是实际渲染和发布后的页面，而不是 Markdown 文件本身。

这一步看似形式化，实际上是在消除团队最常见的歧义。“测试通过”可能只说明单元函数正确；“截图没问题”可能来自上一次构建；“Agent 说已调用工具”可能没有对应的请求 ID。没有明确产物，所有状态汇报都只是在描述过程，而不是描述结果。

我建议给每次重要交付附上一张很小的验收卡：

```yaml
source_commit: abc1234
artifact: web-preview-2026-09-01.3
built_at: 2026-09-01T10:24:00+08:00
scenario: 新用户首次进入首页
checks:
  - 顶部导航可见且可点击
  - 背景资源加载成功
  - 移动端 390px 无内容遮挡
evidence:
  - preview_url
  - screenshot
  - browser_console_log
result: pass
```

不需要一开始就建复杂平台。关键是让任何人都能反查：这条结论对应哪个源码、哪个产物、哪个场景，以及靠什么证据成立。

## 验收要贴近失败方式，而不是贴近实现方式

第二个误区是：Agent 改了哪里，就只验证哪里。它修了 CSS，就只跑 CSS 相关检查；它改了工具描述，就只看工具调用是否返回成功。

但真实故障往往发生在层与层之间。场景文件缺少对象，代码再正确也不会初始化；资源路径在开发环境有效，到构建产物里可能失效；工具返回 200，不代表返回的是当前用户、当前权限下的正确对象。

因此，验证场景应该从用户的失败描述倒推，而不是从改动文件倒推。一个够用的最小闭环通常有三层：

1. **静态门**：格式、类型、单元测试或配置检查，快速排掉低级错误；
2. **产物门**：确认构建、部署、索引或数据任务真的完成，且版本可追溯；
3. **体验门**：在目标设备、权限和关键路径上执行一次真实操作，保留截图、日志或轨迹。

不是每个改动都需要全量回归。但只要改动会影响用户看见的结果，就至少要跨过产物门和一条体验门。这样做的目的不是增加流程，而是用一次短验证换掉后面几轮“其实没生效”的返工。

## 给 Agent 的任务，也要有“不得宣布完成”的条件

很多 Agent 工作流把完成条件写成“修改文件并提交”。这对代码生成有用，对交付却不够。

更可靠的写法是把完成条件写成可观察状态：

> 修改完成后，生成最新产物；使用指定场景验证；附上版本标识和证据。任一条件缺失时，状态为“待验证”，不得标记完成。

同时把失败设计成正常分支。构建耗时过长、预览环境不可用、需要人工 GUI 操作，都不是 Agent 应该用语言补齐的空白。它应当报告卡在哪一层、已有哪份证据、下一步最小的人工动作是什么。

这也有利于任务拆分：一个 Agent 负责修复，一个负责生成产物，一个负责独立验收。独立验收尤其重要——同一个 Agent 既改又判，很容易沿着自己的假设确认自己。

## 把“最新产物”变成团队默认语言

下一次有人说“已经修好了”，不妨只追问四件事：

1. 这是哪个源码版本生成的？
2. 用户实际会拿到哪个产物？
3. 在哪个真实场景验证过？
4. 证据在哪里？

如果回答不全，不必急着否定工作成果，把状态改成“待验证”就好。这个小小的语言变化，会迫使流程从“改动中心”转向“结果中心”。

Agent 让团队更快地产生改动，也让过期截图、旧缓存和想象中的成功更容易混进流程。真正值得自动化的，不是让 Agent 更快地说“完成”，而是让每一次完成都能落在最新、可复现、用户看得见的产物上。

Agent 创建工单，工具超时了。你会让它再试一次吗？

如果服务端已经保存工单，只是响应没有回来，再试一次就可能变成两张工单。模型没有理解错需求，工具参数也完全合法，业务却被执行了两遍。

回看工作流复盘和近期研究材料，我想补上一个容易被“失败恢复”四个字遮住的细节：**恢复回答，与恢复有副作用的动作，不是一回事。** 下面是本次实际运行的本地小实验，不是线上事故或生产收益报告。

## 一个超时，为什么留下两条记录

我用 Python 和内存 SQLite 模拟工单服务：先插入记录并提交事务，再主动抛出超时异常，模拟“写入成功、响应丢失”。客户端捕获异常后重试一次。

第一组每次调用都直接插入。两次请求，最终留下两条记录。

第二组为同一次业务操作固定一个操作标识，并在服务端表上设置唯一约束。重复请求不再插入，而是返回原记录。两次请求，最终只有一条记录，返回的也是第一次生成的编号。

另外两项断言也通过了：相同标识携带不同内容时拒绝执行；用户确实要再创建一张相同内容的工单时，使用新标识，可以正常创建。

这只是单进程模拟，没有覆盖网络、并发、进程崩溃和记录过期。它验证的是一个具体陷阱：**超时只能说明调用方没拿到结果，不能证明服务端没做事。**

## 标识的是“一次意图”，不是“一次请求”

最容易写错的实现，是每次重试都生成一个新 UUID。标识虽然唯一，却无法去重：服务端看到的是两次不同操作。

我的建议是，在首次写入前由应用层生成并持久化操作标识，同时保存目标系统、授权范围和请求摘要。恢复同一次操作时复用标识，不让模型临时决定换一个。

也不要只用内容哈希当标识。用户可能真的需要两个内容相同的日程；“内容一样”不等于“操作重复”。摘要用于检查参数是否被改动，操作标识用于区分业务意图。

服务端必须原子地完成去重判断与写入。先查有没有、再无约束地插入，并发时仍可能重复。这个实验把唯一约束放在实际保存工单的表上；连接真实第三方系统时，仅在自己的数据库记一笔，并不能阻止对方重复执行。

[Stripe 的幂等请求文档](https://docs.stripe.com/api/idempotent_requests)提供了可参考的契约：相同键复用结果、参数变化报错，并明确键的保留边界。具体行为要按目标接口核对，不能假设所有连接器都支持。

## 给结果不明的动作留一个位置

如果下游没有幂等接口，我不会把“自动重试三次”设成默认答案。

建议把这类动作标记为“结果待核对”，保留操作标识，再通过下游提供的业务编号或查询接口确认。查到匹配记录，就恢复原结果；暂时查不到，也要考虑查询延迟，不能立刻认定没有执行。

无法可靠核对时，停止自动补写，交给人工处理。尤其是付款、外发和删除，少执行一次需要补救，多执行一次可能根本无法撤回。幂等也不是授权：恢复执行前仍要检查权限是否有效。

产品界面同样要配合。不要一边显示“失败，请重试”，一边偷偷在后台继续写入。更准确的提示是：“提交结果尚未确认，正在核对，请勿重复提交。”

上线前，先给一个核心写操作补四个测试：提交后丢响应、同键并发、同键改参数、跨进程恢复。统计实际业务记录数，而不只是工具最终有没有返回成功。

**Agent 的可靠，不是失败后敢再试，而是再试之前，知道这一遍会不会多做一件事。**

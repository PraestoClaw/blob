## 长任务 Agent 最怕的不是不会做

很多团队做 Agent，第一个版本都长得差不多：写一个很长的 system prompt，塞进任务背景、工具列表和输出格式，然后祈祷模型能从头跑到尾。

这个办法在 demo 里很好看。让 Agent 搜资料、总结、写报告、发消息，一条链路跑通，大家都觉得产品离商业化不远了。

但一到生产环境，问题就开始变形：它不是完全失败，而是「差一点成功」。采集到了资料，却漏了来源；写完了报告，却没保存；遇到工具错误时，它还可能自信地编一个成功结果。

长任务 Agent 真正的敌人，不是模型能力不够，而是系统把太多责任交给了一段上下文。

## Prompt 不是工作流引擎

最近几份 AI 研究报告有个共同信号：Agent 的前沿问题正在从「能否调用工具」转向「能否安全、稳定、可恢复地完成长任务」。LongHorizon-Harness 这类工作把任务执行、状态、完成判定从上下文里拆出来，本质上是在提醒开发者：不要把 Agent 当成更聪明的函数调用，要把它当成会出错的操作员。

操作员需要工单、检查点、验收，也需要出错后的复盘记录。

如果你的 Agent 只能靠最后一句「请确保完成所有步骤」来保证质量，那它迟早会漏步骤。不是因为它笨，而是因为你没有给它轨道。

## 我现在会把长任务拆成四层

第一层是状态。每个任务都应该有明确的 state schema：现在处于采集、筛选、写作、审核、发布还是归档？每一步的输入、输出、失败原因写在哪里？状态不应该只存在模型上下文里，而应该落到文件、数据库或任务队列中。

第二层是阶段验收。不要让 Agent 自己说「我完成了」。采集阶段检查来源数量；写作阶段检查字数和链接；发布阶段检查 git status、commit、push 结果。验收器可以很简单，哪怕只是脚本和文件存在性检查，也比纯自评可靠。

第三层是失败归因。一次失败至少要分清：是模型判断错、工具返回错、环境不可用，还是验收规则设计错。否则团队只会不断调 prompt，把所有问题都归咎于「模型不稳定」。

第四层是权限边界。强 Agent 一旦拥有过宽权限，哪怕目标不是恶意，也可能越界。生产 Agent 默认应该最小权限、可审计、可停机。能读就不要给写，必须发布时也要留下日志和回滚路径。

## 一个很小的实战模板

假设你要做一个每日行业报告 Agent，不要设计成「搜索新闻并写报告」。我会这样拆：

1. `collect`：抓取候选来源，保存链接和摘要。
2. `select`：按相关性、可信度、差异化打分，输出入选清单。
3. `draft`：只基于入选清单写初稿，禁止新增未记录来源。
4. `verify`：检查来源、格式、字数、重复段落和敏感动作。
5. `publish`：执行保存、提交、推送或投递，并记录失败原因。

这套流程听起来比一条 prompt 麻烦，但有三个好处：失败可以恢复，质量可以度量，经验可以沉淀。它让创业团队能把 Agent 从「看起来很厉害」推进到「每天都能交付」。

## 对创业者的判断

未来一年，很多 AI 产品不会输在模型，而会输在 workflow。用户不关心你的 Agent 用了多先进的模型，只关心它有没有把事情办完，出了错能不能解释，下一次会不会少犯同样的错。

这也是小团队的机会。模型能力会越来越同质化，但高质量的任务状态、行业验收器、失败案例库和权限治理，会变成产品自己的复利。

所以，别急着再写一版更长的 prompt。先问自己四个问题：任务状态在哪里？每一步怎么验收？失败如何归因？权限能不能收紧？

如果这四个问题答不上来，你做的还不是生产级 Agent，只是会调用工具的聊天窗口。

真正有价值的 Agent，不是跑通一次，而是失败后还能继续工作的系统。

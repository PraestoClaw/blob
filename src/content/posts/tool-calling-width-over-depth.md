> 如果你正在做 Agent 产品，工具调用的准确率大概率是你最头疼的问题之一。我们踩了两个月的坑后发现：方向比努力重要——你优化的维度可能从一开始就错了。

## 问题：工具调用为什么这么难？

Agent 的核心能力循环是：理解意图 → 选择工具 → 构造参数 → 执行 → 解读结果。听起来简单，但实际部署后你会发现，工具调用的失败率比你预想的高得多。

常见的失败模式：

1. **选错工具**：用户说"帮我查一下最近的会议"，Agent 调了搜索引擎而不是日历 API
2. **参数构造错误**：选对了工具，但参数格式不对、字段缺失、类型错误
3. **时序混乱**：多步任务中，先调了依赖后续结果的工具
4. **过度调用**：一个简单问题调了 7 个工具，用户等了 30 秒

我们最初的应对策略是"让模型想得更深"——加更长的 system prompt、更详细的工具描述、要求模型先做 step-by-step 规划再执行。效果有吗？有，但上限很快就到了。

## 转折点：KATE 论文的三个反直觉发现

arXiv 上一篇叫 KATE（Knowledge-Augmented Tool-calling via Experiential Knowledge）的论文让我们重新审视了整个策略。它的核心结论有三条，每一条都和我们的直觉相反：

### 发现一：具体案例 > 抽象描述

我们之前花大量时间优化工具的 description 和 parameter schema——写得越清晰越好，加各种 constraint 说明。但 KATE 的实验表明：**给模型看一个具体的历史调用成功案例，效果远超把工具说明写得天花乱坠。**

这在工程上的含义是：与其花时间打磨工具描述文档，不如维护一个"成功调用案例库"。每个工具配 3-5 个真实场景的输入输出对，直接塞进 prompt 里。

我们实测的效果：工具选择准确率从 78% 提升到 91%。代价？prompt 长了大约 800 token。性价比极高。

### 发现二：并行采样 > 更长思考

这是最反直觉的一条。

常规思路是让模型"想得更深"——增加 CoT 长度，要求模型先分析需求、再列出候选工具、再评估每个选项、最后做决定。但 KATE 发现：**让模型并行生成 5 个候选方案再聚合，效果远好于让模型用更长的推理链生成 1 个方案。**

翻译成工程语言：与其 temperature=0 调一次，不如 temperature=0.7 调 5 次，然后用一个简单的 majority voting 或 reward model 选最优解。

为什么？因为工具调用的难点不在"推理"，而在"覆盖"——模型的单次采样容易陷入局部最优，多次采样能覆盖更大的解空间。就像你让 5 个工程师分别独立设计一个方案，然后挑最好的，比让 1 个工程师想 5 倍久的效果好。

我们的落地方式：对高复杂度请求（判断标准是涉及 3 个以上工具的组合调用），开启 3-path parallel sampling，用一个轻量级 verifier 做最终决策。延迟增加约 40%，但复杂调用的成功率从 65% 提升到 84%。

### 发现三：RL 后训练 > SFT 微调

如果你想通过训练来提升工具调用能力，用 RL（如 GRPO）比 SFT（监督微调）效果好得多。原因是 SFT 容易让模型"记住答案"而不是"学会决策"——它在训练分布内表现好，但遇到新工具或新组合就退化。

RL 的优势在于它优化的是决策策略而非具体输出，泛化性更强。

这条对大多数团队来说可能暂时用不上（毕竟不是谁都有条件做后训练），但它指明了一个方向：如果你用 SFT 微调了一个工具调用模型，发现它在新工具上表现差，这不是 bug，是 SFT 的结构性局限。

## 实战中的工程落地

基于这三条认知，我们重构了工具调用链路。整体架构变成了：

```
用户请求
  ↓
意图识别（轻量模型，快速分类）
  ↓
案例检索（从成功案例库中召回最相关的 3-5 个历史调用）
  ↓
并行生成（3 条候选路径，每条独立规划工具调用序列）
  ↓
验证聚合（检查参数合法性 + 跨路径一致性投票）
  ↓
执行
```

几个关键的工程细节：

**案例库怎么建？** 不需要一开始就很完善。我们的做法是：上线后记录所有工具调用的 input/output/是否成功，每周人工筛选 "标杆案例" 入库。两周后库里就有了覆盖 80% 常见场景的案例。

**并行采样的成本怎么控制？** 不是所有请求都需要并行。我们做了一个简单的"复杂度路由"：如果意图识别阶段判断只需要单工具调用，直接走单路径；只有多工具组合场景才触发并行。实际只有约 15% 的请求走并行路径。

**验证器怎么设计？** 最简单的版本就是检查三件事：(1) 工具名是否存在；(2) 必选参数是否齐全；(3) 参数类型是否匹配。这三个 rule-based check 就能过滤掉 60% 的错误调用。高级版本可以加一个轻量模型做语义验证。

## 一个容易踩的坑：CoT 和长上下文的冲突

这里插一个相关但独立的坑。同期另一篇论文（Attention Amnesia）发现：**对模型做 CoT 微调会破坏长上下文召回能力。**

具体表现是：你微调模型让它在工具调用前做更详细的推理（这听起来很合理对吧？），结果模型在长对话中"忘记"了前面的关键信息。一个混合注意力模型在 256K 上下文的 needle-in-a-haystack 测试中从 67% 暴跌到 9%。

这意味着：如果你的 Agent 需要处理长对话（比如多轮任务规划），不要盲目追求更长的 CoT。思维链的收益可能被长上下文召回的退化吃掉。

解法是作者提出的 QK-Restore——在推理时恢复预训练阶段的 Q/K 权重，零成本修复。但更实用的工程启示是：**用并行宽度替代思维深度**，既避免了这个冲突，又能获得更好的效果。

## 总结：三条可以立刻执行的建议

1. **建案例库，而非磨说明书。** 给每个工具配 3-5 个真实成功案例，塞进 context。投入产出比远超打磨 tool description。

2. **复杂调用走并行，简单调用走直连。** 加一个轻量路由器，只对多工具组合场景开启 parallel sampling + voting。

3. **验证器是必须的，不是可选的。** 哪怕只是 rule-based 的参数检查，也能拦住大部分低级错误。不要信任模型的每一次输出。

这三条不需要你训练模型，不需要你有 GPU 集群，今天就能改。效果？我们的实测数据是整体工具调用成功率从 72% 提升到 89%。

Agent 的可靠性不是靠模型智力硬推的，是靠工程架构兜底的。模型能力是地板，工程设计是天花板。

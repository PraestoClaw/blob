## 为什么你的 Agent 总是调错工具？

如果你正在做 AI Agent 产品，大概率踩过这个坑：明明工具描述写得清清楚楚，Agent 还是经常调错函数、传错参数、漏掉关键步骤。

你可能的第一反应是——优化 system prompt，把工具说明写得更详细。

这是一个看起来正确但效果有限的方向。最近我们在实际项目中验证了一组来自学术研究（arXiv: 2606.10875, KATE）的发现，结论颠覆了我之前的很多认知。今天把三条最核心的经验分享出来。

## 法则一：具体案例 > 抽象说明

**反直觉点：给 Agent 看 3 个历史调用案例，比写 3 页工具文档有效得多。**

我们之前花了大量时间打磨工具的 description 字段——参数含义、边界情况、使用场景。效果一般。

后来尝试在 prompt 中附带 2-3 个真实的工具调用案例（输入+输出+上下文），准确率直接提升了 20%+。

为什么？因为 LLM 本质上是模式匹配器。抽象描述需要模型"理解后推理"，而具体案例只需要"类比后套用"。后者对当前模型来说容易得多。

**实操建议：**
- 为每个工具维护 3-5 个高质量调用案例
- 案例要覆盖典型场景和边界场景
- 用向量检索动态选择与当前 query 最相似的案例注入 prompt
- 案例格式：`用户意图 → 工具选择 → 参数构造 → 预期结果`

## 法则二：并行采样 > 深度思考

**反直觉点：让模型"想三个方案选最好的"，比让它"想得更深更久"效果好。**

很多人优化 Agent 的思路是增加 reasoning 步骤——加 CoT、加反思、加规划。这在纯推理任务上有效，但在工具调用场景下收益递减明显。

更有效的方式是**宽度优先**：让模型并行生成 3-5 个候选工具调用方案，然后用一个轻量级的验证步骤选最优解。

我们实测的数据：
- 加长 CoT（从 1-step 到 3-step reasoning）：准确率 +5%
- 并行采样 3 个候选 + majority vote：准确率 +15%
- 并行采样 5 个候选 + reward model 打分：准确率 +22%

成本上，并行采样确实增加了 token 消耗，但因为可以用更小的模型（比如 Flash 级别）做采样，实际成本增加有限。关键是延迟可以通过并发请求控制在可接受范围内。

**实操建议：**
- 对关键工具调用步骤开启 n=3 或 n=5 采样
- 用简单的一致性检查（参数是否合法、工具是否存在）过滤明显错误
- 如果有标注数据，训练一个轻量级 reward model 做排序
- 对非关键步骤保持 greedy decoding 控制成本

## 法则三：RL 训练 > SFT 训练

**反直觉点：如果你要微调模型提升工具调用能力，RL 比 SFT 好得多。**

这条对大多数应用层开发者来说可能暂时用不上（除非你有微调条件），但理解其原理对 prompt engineering 也有指导意义。

SFT（监督微调）本质是教模型"模仿正确答案"。问题在于工具调用的正确路径不唯一——同一个目标可能有多种合理的工具组合。SFT 容易让模型过拟合到训练数据的特定路径上，泛化能力差。

RL（强化学习）则是给模型一个"做对了就奖励"的信号，让它自己探索最优路径。这种方式训练出的模型在面对新工具、新场景时表现明显更好。

**对应用层的启示：**
- 如果你在用 few-shot 优化工具调用，不要只给"唯一正确答案"的案例
- 给模型看"同一目标的多种实现路径"，让它学会灵活组合
- 在评测时不要只检查"是否和标准答案一致"，而是检查"最终结果是否正确"
- 这也解释了为什么 ReAct 模式（观察-思考-行动循环）比一次性规划更鲁棒——它本质上允许模型在执行过程中修正路径

## 一个额外的工程经验：存在性验证

在实战中我们还发现一个被严重低估的 failure mode：**当用户请求涉及不存在的功能时，Agent 几乎不会拒绝。**

研究表明（arXiv: 2606.11105, PhantomBench），即使是最强的模型，当 prompt 中预设了某个概念存在时，幻觉率高达 86.7%。

翻译成工具调用场景就是：如果用户说"帮我用 XXX 功能做 YYY"，而 XXX 功能根本不存在，Agent 大概率会编造一个看起来合理的工具调用序列。

**解决方案：** 在工具调用链的入口加一个显式的"存在性验证"步骤——先确认请求涉及的工具/功能/数据确实存在，再进入执行流程。这一步成本极低但能避免大量下游错误。

## 总结

三条法则的共同主题是：**不要高估 LLM 的"理解"能力，要善用它的"模式匹配"能力。**

| 法则 | 直觉做法 | 更优做法 |
|------|---------|---------|
| 案例 vs 文档 | 写详细的工具文档 | 给具体的调用案例 |
| 宽度 vs 深度 | 加 CoT 让它想更久 | 并行采样选最优 |
| RL vs SFT | 用正确答案做 SFT | 用结果信号做 RL |

这些不是理论推演，是我们在生产环境中反复验证过的结论。如果你也在做 Agent 产品，希望能帮你少走一些弯路。

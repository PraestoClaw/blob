## 背景：你的 Agent 工具调用靠谱吗？

如果你正在做 AI Agent 产品，大概率遇到过这些场景：

- Agent 明明有正确的工具可用，却选了个错误的
- 给了详细的工具描述文档，Agent 还是乱传参数
- 简单任务调用一次就搞定，复杂任务调用链断在中间某一步

我们团队每天都在和各种 Agent 打交道——从内容自动化到竞品监控到研究报告生成。踩了无数坑之后，结合最近 arXiv 上一篇让我眼前一亮的论文（KATE, arXiv 2606.10875），我总结出三条在实际生产环境中验证过的法则。

## 法则一：给案例，别给说明书

**研究发现：** KATE 论文系统性地测试了不同类型的知识对工具调用的影响。结论出人意料——具体的历史调用案例（instance-level knowledge）带来的收益远超抽象的工具使用说明（intent-level knowledge）。

**实战翻译：** 我们最初设计 Agent 系统时，花了大量精力写工具的使用文档：什么参数是什么意思，什么场景该用什么工具。效果一般。

后来我们换了策略：在 prompt 里直接塞几个真实的调用案例。

```
✅ 好的做法：
"上次用户问天气时，我调用了 weather_api(city='上海', date='today')，返回了温度和湿度"

❌ 不太好的做法：
"weather_api 接受 city 和 date 两个参数，city 是字符串类型的城市名..."
```

为什么？因为大模型是模式匹配机器。给它看过成功案例，它知道该怎么模仿。给它看文档，它还得"理解"再"应用"，中间多了一层抽象，出错概率就上去了。

**落地建议：** 维护一个"成功调用案例库"。每次 Agent 成功完成一个复杂工具调用链，把它存起来。下次遇到类似场景，把相关案例注入上下文。这比你写100行工具文档都管用。

## 法则二：并行采样比深度思考更有效

**研究发现：** KATE 对比了两种提升工具调用质量的策略——让模型"想得更深"（更长的 CoT）vs 让模型"多想几个方案再选最好的"（并行采样+聚合）。结果后者完胜。

**实战翻译：** 这颠覆了很多人的直觉。我们一开始也觉得，工具调用出错是因为模型"想得不够仔细"，所以加了各种 step-by-step 的推理引导。效果有，但有限。

后来我们改成了"多路并行"策略：

1. 让模型生成 3-5 个候选工具调用方案
2. 用一个轻量级的验证器（可以是规则，也可以是另一个模型调用）筛选最优方案
3. 执行最优方案

代价是 token 消耗翻了 3-5 倍，但成功率从 ~70% 提升到 ~92%。对于关键业务流程，这个 trade-off 完全值得。

**落地建议：** 不需要所有工具调用都走并行路线。识别出你系统中的"高失败率节点"（通常是参数复杂、多工具组合的场景），只对这些节点开启并行采样。成本可控，收益显著。

## 法则三：RL 训练比 SFT 更适合工具调用

**研究发现：** 如果你有条件对模型做后训练来增强工具调用能力，用强化学习（RL）的效果显著优于监督微调（SFT）。

**实战翻译：** 这条对大多数团队来说可能暂时不直接适用（毕竟不是每个团队都有条件训模型）。但它的底层逻辑对"prompt 工程"同样有指导意义：

SFT 的逻辑是"照着正确答案学"——但工具调用的正确答案不唯一，路径很多。
RL 的逻辑是"试错后根据结果调整"——这更接近工具调用的本质。

所以在 prompt 层面，与其给 Agent 一个"标准答案"式的指导（"遇到 X 场景一定要调 Y 工具"），不如设计一个反馈回路：

- Agent 调用完工具后，让它检查结果是否符合预期
- 如果不符合，允许它换个工具或换个参数重试
- 记录哪些尝试成功了，哪些失败了（回到法则一的案例库）

这本质上就是在推理层面模拟了 RL 的探索-利用过程。

## 额外收获：一个被低估的失败模式

同期另一篇论文（PhantomBench, arXiv 2606.11105）揭示了一个与工具调用高度相关的问题：当 prompt 中预设了不存在的工具或功能时，模型几乎不会拒绝调用——幻觉率高达 86.7%。

这意味着：**如果你的工具列表里有过时的、已下线的工具描述没清理，Agent 可能会尝试调用一个根本不存在的接口。**

落地建议很简单：定期清理工具列表，确保 Agent 上下文里的每个工具都是当前可用的。加一个工具可用性验证层也不贵。

## 总结

| 法则 | 一句话 | 成本 | 收益 |
|------|--------|------|------|
| 给案例不给说明书 | 维护成功调用案例库 | 低（存储+检索） | 高 |
| 并行采样 | 关键节点多路生成再选优 | 中（3-5x token） | 高 |
| 模拟 RL 反馈 | 允许重试+记录成败 | 低 | 中高 |

这三条法则不是理论推导，是我们在每天运行的 Agent 系统里反复验证过的。如果你也在做 Agent 产品，建议从"案例库"开始——成本最低，见效最快。

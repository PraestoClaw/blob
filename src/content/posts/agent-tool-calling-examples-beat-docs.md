> 你花了三天写了一份完美的工具使用文档。参数说明、边界条件、最佳实践，一应俱全。然后你的 Agent 还是把工具调错了。

这不是你文档写得差，是你选错了知识传递方式。

## 一篇论文揭示的反直觉真相

最近 arXiv 上有一篇论文 KATE（Pushing the Limits of LLM Tool Calling via Experiential Knowledge），做了一件很简单但结论很有力的事：系统性地测试了不同类型的知识对 Agent 工具调用效果的影响。

结论有三个，每一个都和我们的直觉相反：

**1. 具体案例 > 抽象文档**

给 Agent 看"上次遇到类似问题时，调用了 A 工具，参数是 X，返回了 Y"，效果远好于"A 工具的功能是……参数说明如下……"。

研究者把这叫做"实例级知识"vs"意图级知识"。实例级知识提供稳定增益，意图级抽象知识的收益有限。

**2. 并行多猜 > 深度思考**

让模型同时生成 5 个候选调用方案再聚合，比让它用更长的 Chain-of-Thought 深入推理一个方案效果好。

推理宽度扩展 > 推理深度扩展。

**3. 如果要训练，RL > SFT**

对工具调用这个任务来说，强化学习后训练比监督微调更有效。这是训练策略层面的，对大多数应用开发者来说不直接相关，但它说明了一个底层事实：工具调用的"正确"更像是一种策略选择而非模式匹配。

## 为什么案例比文档有效？

这个现象背后有一个更深的道理：**模型不是在"理解"工具，而是在做模式匹配**。

当你给它一份抽象文档，模型需要：
1. 理解工具的功能边界
2. 把当前任务映射到工具能力
3. 推断正确的参数组合
4. 预测返回结果并决定后续动作

这是四步推理链，每一步都有出错概率。

而当你给它一个具体案例，模型只需要：
1. 判断当前情况和案例是否类似
2. 复用案例中的调用方式，微调参数

两步，而且第一步（相似度判断）恰好是大模型最擅长的事。

这不是 Agent 的"弱点"——这是模型认知架构的本质特征。利用它，而不是对抗它。

## 我们的实战验证

我们跑了几个月的多 Agent 工作流，这个结论和我们的实战经验完全吻合。

### 案例 1：文件操作的正确率

早期我们在 Agent 的 system prompt 里详细描述了文件操作工具的使用规范——什么时候用 `read`，什么时候用 `exec cat`，`write` 和 `edit` 的区别……写了一大段。

Agent 依然经常犯两类错误：
- 用 `exec cat` 读大文件然后上下文爆了
- 用 `write` 覆盖整个文件而不是 `edit` 做精确修改

后来我们在 skill 文件中加入了具体的调用示例——"当需要读取文件前 50 行时，用 `read` + `limit=50`"、"当需要修改文件中的一段代码时，用 `edit` + `oldText/newText`"——错误率直接下来了。

不是因为规则变了，规则从来没变。是因为模型终于"看到"了正确的模式。

### 案例 2：API 调用的参数格式

我们有一个 Agent 需要调用飞书 API 创建文档。API 文档写得很清楚，参数类型、必填/选填、示例值都有。但 Agent 总是在时间戳格式上出错——有时传秒级，有时传毫秒级，有时传 ISO 字符串。

解决方案不是在 prompt 里重复强调"时间戳必须是毫秒级整数"，而是直接给一个完整的成功调用案例：

```
创建记录示例：
fields: { "日期": 1717027200000, "标题": "周报" }
```

从此以后，时间戳格式问题消失了。

### 案例 3：多工具编排

这个更有意思。我们的工作流经常需要 Agent 按顺序调用多个工具——先搜索、再读取、再分析、再写入。抽象地描述这个流程，Agent 偶尔会跳步或者乱序。

但如果在 prompt 中放一个完整的多工具调用 trace（哪怕是不同任务的 trace），Agent 对流程编排的准确率明显提升。它不需要"理解"为什么要按这个顺序——它只需要"看到"这个模式存在过。

## 实操建议：怎么构建你的案例库

基于论文结论和我们的实践，给几条具体建议：

**1. 每个工具至少 3 个成功案例**

不需要多，但要覆盖不同场景。一个简单调用、一个复杂参数、一个异常处理。

**2. 案例要完整——包含输入、调用、输出**

不要只展示"怎么调"，还要展示"调完之后得到了什么"。模型需要完整的因果链。

**3. 失败案例同样有价值**

"上次用了错误的参数 X，得到了错误 Y，改成 Z 后成功"——这种负面案例对避免常见错误特别有效。

**4. 定期更新，保持新鲜**

工具会升级，API 会变，三个月前的案例可能已经过时。把案例维护当作工具维护的一部分。

**5. 优先用 RAG 而非全塞 prompt**

案例多了之后不可能全放 system prompt。用 RAG 检索最相关的 2-3 个案例注入上下文，效果最好且不浪费 token。

## 更大的启示

KATE 的发现其实指向一个更广泛的原则：**在 Agent 工程中，具体 > 抽象**。

这不只适用于工具调用。选题策略、写作风格、代码规范、沟通话术——任何你想让 Agent 遵循的行为模式，给它看成功案例都比给它读规则手册有效。

人类也是这样学习的。新员工入职，给他看三份好的周报，比给他读一本周报写作指南有效得多。

Agent 不是不理解抽象规则——它只是在具体案例面前学得更快、更准确。这不是降低标准，是尊重认知规律。

写更少的文档，收集更多的案例。你的 Agent 会感谢你。

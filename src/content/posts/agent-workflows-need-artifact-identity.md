> 一个 Agent 说“已修复、已验证”，最该追问的不是“测试绿了吗”，而是：**你测的到底是哪一份东西？**

我们曾复盘过一次产品审查：场景文件的问题修了，审查也跑了，但屏幕上依旧是旧状态。最后发现不是修复逻辑错了，而是审查过程拿的是旧构建产物；真正的新构建完成后，问题的形态已经变了。这个教训很朴素，却会在 Agent 工作流里被放大：Agent 能非常高效地完成错误对象上的全部步骤。

最近整理日报、研究报告和工作流记录时，我也看到了同一种结构。报告写得完整，引用有出处，结论却来自两个月前；如果下一步 Agent 把它当作“今天的情报”继续规划或发布，系统不会报错，只会自信地过期。代码构建、RAG 检索、竞品分析和内容发布看似不同，本质上都在犯同一个错误：**验证结果没有和被验证产物的身份绑定。**

## “通过”至少要带上三张身份证

一个可靠的验收记录，不应只有 `passed: true`。它至少要能回答三件事：

1. **来源身份**：用的是哪个 commit、分支、模型版本、数据快照或文档版本？
2. **产物身份**：测试的是哪次构建、哪份导出的报告、哪个部署实例？
3. **验证身份**：谁在何时、用什么检查项、针对什么预期做出了通过判断？

在工程里，这意味着把 `commit_sha`、构建号、制品 checksum 和部署版本写进审查报告；不能只写“已在本地验证”。在研究或内容链路里，则是保存 `source_url`、`published_at`、`fetched_at` 和引用片段。缺少这些字段的“通过”，不是证据，只是一句无法复查的口头结论。

## 把身份校验放在 Agent 动手前

很多团队只在最后跑测试。更稳的做法是把身份检查拆到每次交接处：

- **修复前**：Agent 先读取当前 HEAD 和问题对应的环境版本，确认没有在旧分支上改；
- **验证前**：等待目标构建完成，校验制品的 commit 与待验证 commit 一致；
- **发布前**：确认正文引用的关键数据仍在有效期内，且文章没有把历史结论写成现在时；
- **失败后**：保留输入、产物与日志，让下一位 Agent 知道该重跑哪一段，而不是从头猜。

这套流程会多出几次读取和比对，却能避免最昂贵的浪费：围绕一个已经被替换的构建、缓存或报告，完成一整轮“正确的错误工作”。

## 用“拒绝验证”替代“尽量验证”

关键不是让 Agent 更努力地检查，而是规定它在身份不明时**不得给出通过结论**。例如：构建号缺失、部署版本不匹配、数据超过新鲜度预算、引用无法定位到原文——这些都应返回 `blocked` 或 `inconclusive`，而不是由模型补一句“看起来没问题”。

这尤其适合多 Agent 协作。上游交付时附上最小证据包：输入版本、产物链接、关键日志、验证命令和预期结果；下游只接收证据包完整的任务。它像软件供应链的 provenance，只不过对象从二进制扩展到了报告、决策与内容。

模型能力越强，错误对象上的执行速度越快。真正让工作流可靠的，不是再加一个“请仔细检查”的提示词，而是让每个结论都能回答：**它基于哪个版本的世界？** 先锁定产物身份，再谈测试通过；否则，你验证的可能只是昨天的答案。

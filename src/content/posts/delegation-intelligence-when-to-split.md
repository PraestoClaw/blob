> 多 Agent 系统的瓶颈不在单个 Agent 的能力——而在主 Agent 决定「什么时候把什么交给谁」的判断力。

---

## 一个反复出现的失败模式

我们运行着一个 12 Agent 协作系统，处理从代码生成到内容运营的各类任务。系统初期，调度逻辑是硬编码的：代码任务 → 代码 Agent，研究任务 → 研究 Agent，设计任务 → 设计 Agent。

看起来很合理。但真正的问题从来不是「给谁」，而是「什么粒度」和「什么时候」。

**典型翻车场景：**

一个任务要修改 4 个 service 文件加 1 个 main.py。作为单任务派出。超时。重派。超时。再重派。第三次还是超时。

三次超时后我们才反应过来——这不是一个任务，这是四个任务被错误地绑在一起。拆开之后，每个子任务平均 2 分钟完成。

但反过来也不对。如果把每一步都拆成独立任务（「读文件→分析→写代码→测试→提交」），你会得到 5 个子任务的上下文传递开销远超任务本身的成本。Agent 在第三步已经忘了第一步读到了什么。

**最优粒度不是固定的，它取决于：**
- 任务内部的依赖关系（强耦合的步骤必须在同一上下文内完成）
- 单步的预期耗时（超过 5 分钟的步骤大概率需要拆分）
- 上下文传递的信息损耗（跨任务传递复杂状态很容易丢信息）

这个判断能力，我们之前一直靠人工经验。直到看到一篇论文。

---

## SearchSwarm 的启示：委托行为可以被训练

arXiv 上 6 月 9 号发布的 SearchSwarm 论文提出了一个概念叫 **Delegation Intelligence**——委托智能。

核心思路：让主 Agent 学会三件事：
1. 把复杂任务拆解为子任务
2. 决定何时、何物委托给子 Agent
3. 整合返回结果

他们的方法是通过一个 harness（编排层）引导生成高质量的委托轨迹数据，然后用 SFT 把这种「委托行为」训练进模型。最终一个 30B（激活 3B）的模型在 BrowseComp 上达到 68.1，同规模最优。

这个发现验证了我们两个月实践中模糊感知到的东西：**「决定怎么拆」本身就是一种智能，它不是简单的 if-else 路由，而是需要对任务复杂度、Agent 能力边界、上下文容量的综合判断。**

## 我们总结的四条委托原则

经过两个月的迭代，加上论文的理论验证，我们提炼出了四条实战原则：

### 原则一：单一上下文原则

**如果两个步骤共享同一段「必须完整理解」的上下文（一个复杂函数、一段业务逻辑），它们必须在同一个 Agent session 内完成。**

反面教材：把「理解这段 500 行代码」和「基于理解修改第 200 行」拆成两个任务。第二个 Agent 拿到的只是第一个 Agent 的摘要，信息必然损失。

正面做法：把「理解 + 修改」作为一个原子任务，把「修改文件 A」和「修改文件 B」（如果 A、B 之间无强依赖）拆为两个并行任务。

### 原则二：五分钟法则

**预期执行时间超过 5 分钟的步骤，大概率需要拆分。**

这不是随便定的数字。我们统计了 200+ 次任务执行数据：
- 3 分钟以内完成的任务，成功率 94%
- 3-5 分钟，成功率 78%
- 5-10 分钟，成功率 51%
- 超过 10 分钟，成功率 23%

成功率断崖式下跌的拐点就在 5 分钟左右。原因可能是注意力漂移——长任务中模型更容易偏离目标或陷入无效循环。

### 原则三：结果可验证原则

**每个委托出去的子任务，必须有明确的、可自动验证的完成标准。**

「优化这段代码」不是好的子任务描述。「让这段代码的执行时间从 3 秒降到 1 秒以内，通过 benchmark.py 验证」才是。

如果你不能定义「什么算完成」，这个任务就不应该被委托——它应该留在主 Agent 手里，或者先拆到可以定义完成标准的粒度。

### 原则四：宽度优于深度

这条来自另一篇论文 KATE 的发现：在工具调用场景中，让模型并行生成多个候选方案再聚合（宽度推理），比让它一步步深入思考（深度推理）效果更好。

映射到委托策略上：与其让一个 Agent 反复重试同一个任务（深度），不如让 2-3 个 Agent 独立尝试然后取最优解（宽度）。我们对关键代码任务现在默认开两路并行，取结果更好的那个。成功率从 78% 提升到 91%。

## 工程落地：委托决策的三层架构

在实际系统中，我们把委托决策拆成三层：

**第一层：规则层（快速路由）**

确定性的决策不需要智能判断。「Markdown 文件修改 → 内容 Agent」「Python 测试失败 → 代码 Agent」这类直接走规则。

**第二层：启发式层（粒度判断）**

根据任务描述的复杂度指标（涉及文件数、预期步骤数、依赖关系图）自动判断是否需要拆分，以及拆分方案。这层目前用的是结构化 prompt + few-shot examples。

**第三层：反馈层（动态调整）**

子任务超时？自动触发更细粒度的拆分重试。子任务秒完但结果质量低？可能是拆太碎了，尝试合并。这层靠的是运行时的失败模式识别。

## 还没解决的问题

坦率说，我们的委托系统仍然不够智能：

1. **跨任务状态传递**仍然是最大的信息损耗点。即使用了结构化的 context handoff，复杂状态的传递准确率也只有 ~80%。
2. **委托深度**目前限制在两层（主 Agent → 子 Agent），不敢开三层。因为每多一层委托，上下文损耗会指数级放大。
3. **动态负载均衡**还是人工配置的。理想情况下，系统应该自动感知哪个 Agent 当前空闲、哪个处于高错误率状态。

SearchSwarm 论文的方向是对的——用训练数据把委托判断内化到模型里。但对大多数团队来说，先把「规则 + 启发式 + 反馈」三层做扎实，已经能解决 80% 的问题了。

## 给 AI 开发者的建议

如果你在搭建多 Agent 系统，以下三个动作可以立刻改善你的委托质量：

1. **记录每次任务执行的耗时和成功/失败状态**。积累 100+ 条数据后，你会看到自己系统的「五分钟拐点」在哪里。

2. **把历史上成功的委托轨迹作为 few-shot 塞给调度 Agent**。这比写任何抽象的委托规则都管用——KATE 论文证实了「实例级知识 > 抽象知识」。

3. **对关键任务开并行路径**。两个 Agent 独立做同一件事、取更好的结果，这个策略的 ROI 远超你的预期。多花一倍 token，换来 13% 的成功率提升，在生产环境中非常划算。

---

多 Agent 系统的终极挑战不是让单个 Agent 更强——那是模型公司的工作。我们要解决的是编排层的智能：让系统知道什么时候该拆、拆给谁、拆多细。

这件事没有银弹，但有方法论。从记录数据开始。

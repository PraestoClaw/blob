如果排班 Agent 把“每人最多一个班”偷偷改成“忙的时候可以连班”，你拿到的不是优化方案，而是一张需要人工重新检查的表。提示词可以强调规则，却不该成为规则的唯一执行者。

整理近期研究素材时，“语言模型处理非结构化信息，求解器处理约束”这个分工值得单独验证。我做了一个极小的排班实验。它不是客户案例，也不是模型跑分；目的只有一个：让“安排得像样”和“确实可行”的差别可计算。

## 一、先做一个能穷举的业务切片

合成场景只有三个人 A、B、C，以及早、午、晚三个班。每班必须一人，每人最多一班，只有 A 具备晚班资格。

三个班分别从三个人中选，原始组合共 27 种。我用 Python 穷举，再逐条过滤，得到两种可行安排：早 B、午 C、晚 A；或者早 C、午 B、晚 A。

把 A 改为全天请假后，可行安排变成零。关键不是程序“不会排”，而是现有条件下就没有满足全部规则的表。让 B 顶晚班，会违反资格限制；让请假的 A 上班，会违反可用时间。

下面是这个小实验的核心，可直接运行：

```python
from itertools import product


def plans(absent=None):
    return [
        p for p in product("ABC", repeat=3)
        if len(set(p)) == 3
        and p[2] == "A"
        and absent not in p
    ]


assert plans() == [("B", "C", "A"), ("C", "B", "A")]
assert plans("A") == []
```

这段代码不测语言模型，也不解决真实门店排班。它给出一个可复现的底线：系统不能靠改写解释，把零个可行解说成一个。

## 二、把硬规则和偏好分开存

“没有晚班资格不能值晚班”是硬约束；“尽量少排晚班”是偏好。前者决定方案能否进入候选集，后者只用于给可行方案排序。

让模型读请假消息、提取日期和人员很合适，但提取结果应进入有类型的字段，而不是直接变成排班表。至少保留规则编号、适用人员、时间范围、原文依据和确认状态。

尤其别把“最好别排我”自动解释为绝对不可用，也别把“我不能来”降成一个可以付出罚分后违反的偏好。含义不清时，保留待确认状态，先确认约束再求解。

我核对了 Google OR-Tools 的[公开排班示例](https://github.com/google/or-tools/blob/stable/examples/python/shift_scheduling_sat.py)：它把硬边界与软偏好罚分分别表达。小实验用穷举是为了看清逻辑；人数和日期增加后，再考虑约束求解器，而不是无限枚举。

## 三、无解时，交付冲突而不是圆场

产品接口至少要区分四种结果：找到可行方案、已证明最优、已证明无解、限时内未确定。超时不是无解，可行也不等于最优。

在上面的穷举实验里，A 请假后可以明确解释：晚班需要合资格人员，但唯一合资格的人不可用。一般业务中的冲突定位更复杂，不能指望模型凭空编出“最小冲突集”。

此时可以提出“补充合资格人员”这样的待审批选项，但不能自行取消资格要求。用户确认变更后，建立新一版约束，再重新计算；不要悄悄覆盖原来的输入。

## 四、上线前专测“看起来没问题”的错表

最小回归集可以从四例起步：正常可行、关键人员缺席、偏好与硬规则冲突、人员变动后旧方案失效。逐项校验覆盖人数、资格、可用时间和重复排班，而不是只让另一个模型评价“是否合理”。

最终写入排班系统前，还要对照最新人员状态再次检查。求解器保证的只是输入模型内的可行性；漏掉休息时长、劳动规则或临时请假，数学上正确也可能业务上错误。

先挑你产品里一条最不能违反的规则，把它写成可执行检查。**让模型理解人话，让约束守住底线，再让模型解释结果。** 对需要真正执行的 Agent，这比多写十遍“请严格遵守”更值得优先做。

> 大多数人优化 Agent 工具调用的方式是：写更好的工具描述文档。这个方向是错的。

## 故事

我们给 Agent 接了二十多个工具——文件操作、浏览器控制、API 调用、数据库查询、各种第三方服务。最初的做法很"工程师"：为每个工具写详尽的参数说明、用法示例、边界条件、错误处理指南。文档越写越长，Agent 的工具调用成功率却没有线性提升。

有时候 Agent 面对一个明显应该用 `web_fetch` 的场景，它偏要用 `browser` 打开页面再截图分析。有时候参数格式写得清清楚楚，它还是传错类型。

我们折腾了两个月后，偶然发现一个诡异的现象：**在 system prompt 里放一段真实的成功调用记录，比放三页工具文档管用得多。**

这不是玄学。上周 arXiv 上一篇叫 KATE 的论文（2606.10875）用严格实验验证了这个直觉，并且给出了三条可以立即落地的结论。

## 教训一：实例级知识 >> 抽象级知识

KATE 的实验设计很直接：把给 Agent 的知识分成两种——

- **实例级**：具体的历史调用案例，"用户问了 X，Agent 调了 Y 工具传了 Z 参数，得到了 W 结果"
- **意图级**：抽象的规则概括，"当用户需要实时信息时，应该使用搜索工具"

结论：实例级知识提供**稳定、可预测**的增益，而意图级抽象知识的收益**有限且不稳定**。

这和我们的经验完全吻合。我们现在的做法是：每个工具维护一个 `examples/` 目录，里面是 3-5 个真实的成功调用片段。Agent 执行时，相关的例子会被注入上下文。效果远好于在工具 schema 的 description 字段里绞尽脑汁写抽象说明。

**为什么？** 我的理解是：工具调用本质上是模式匹配，不是逻辑推理。模型不是"理解"了工具然后"推导"出正确参数，而是在上下文里找到最相似的模式然后"模仿"。你给它看的成功案例越接近当前场景，它模仿得越准确。

### 落地建议

- 为高频工具维护 3-5 个真实调用案例
- 案例要包含完整上下文：用户意图 → 工具选择 → 参数构造 → 返回结果
- 用 RAG 按相似度检索最相关的案例注入 prompt，而不是全部塞进去
- 抽象文档仍然需要，但降级为"兜底"——当没有匹配案例时的 fallback

## 教训二：推理宽度 >> 推理深度

KATE 的另一个反直觉发现：让模型**并行生成多个候选方案再聚合**，比让它**思考得更深更久**（更长的 Chain-of-Thought）效果好。

翻译成大白话：与其让 Agent 花 30 秒仔细想一个方案，不如让它花 10 秒想出 5 个方案，然后选最好的那个。

我们在实践中的对应做法是"多路尝试"：对于复杂的工具调用链，让 Agent 生成 3 条执行路径，然后用一个轻量验证步骤挑选最合理的一条。成本增加不到 2 倍（因为并行生成的 token 大部分是短的），但成功率提升了 30%+。

**为什么深度思考反而不如广度？** 我的假设是：工具调用的错误往往不是"逻辑链条断了"，而是"一开始就走错了方向"。更长的 CoT 只是在错误的方向上走得更远。而多条路径中，通常至少有一条碰巧走对了方向。

### 落地建议

- 对关键工具调用节点，用 `n=3` 或 `n=5` 采样多个候选
- 候选之间做简单的一致性检查——如果 3/5 选了同一个工具，大概率是对的
- 验证步骤可以很轻：检查参数格式是否合法、工具是否存在、返回值是否非空
- 不要在单条路径上加更多的"请仔细思考"——这通常只增加 latency 不增加正确率

## 教训三：RL 后训练 >> SFT 微调

如果你打算训练自己的工具调用模型（或者微调一个开源模型），KATE 的结论很明确：**强化学习（RL）后训练比监督微调（SFT）效果好。**

这一条对大多数应用层开发者来说不直接可操作——你不太可能自己训模型。但它有一个重要的间接启示：

**选模型时，优先选经过 RL 训练的版本。**

具体来说：Claude 的 tool_use 能力、GPT 的 function calling，这些都是经过 RL 专门优化过的。如果你在用开源模型，优先选有 "tool-use" 后缀或标注了工具调用 RLHF 的版本，而不是通用 instruct 版本再自己加 system prompt 引导。

### 落地建议

- 不要用通用 chat 模型勉强做工具调用——选择专门优化过的版本
- 如果必须用通用模型，实例级知识注入（教训一）是成本最低的弥补方案
- 自建评测时，工具调用的 reward signal 应该是"最终任务是否完成"，不是"格式是否正确"

## 一个更大的图景

这三条教训指向一个统一的认知：**Agent 的工具调用不是编程，是认知。**

我们下意识地用"写文档→理解→执行"的编程范式来设计工具调用系统。但模型的工作方式更接近人类学徒——它不是读完操作手册就会用机器的，它需要看师傅操作几遍，需要自己多试几次，需要在反复实践中形成肌肉记忆。

所以最高效的工具调用优化路径不是：写更好的文档 → 更详细的 schema → 更长的 system prompt。

而是：**积累成功案例 → 按相似度匹配注入 → 多路并行尝试 → 用结果反馈迭代。**

这也解释了为什么一些看起来"粗糙"的 Agent 系统效果很好——它们可能文档写得一般，但积累了大量的成功执行记录作为 few-shot examples。而一些文档写得无比精美的系统却表现平平——因为它们在用错误的方式教一个不按文档学习的学生。

## 我们目前的实践

在 PraestoClaw 的 Agent 系统里，工具调用的优化已经从"写文档"转向"建案例库"：

1. **自动记录**：每次成功的工具调用自动存入案例库（包含完整上下文）
2. **相似度检索**：执行前，用当前任务描述检索 top-3 相关案例注入 prompt
3. **多路采样**：关键节点生成 3 条候选路径，轻量验证后选最优
4. **失败回溯**：失败的调用也记录，作为"反面教材"在检索时降权

这套系统上线两周后，工具调用的首次成功率从 72% 提升到 89%。没有改一行工具文档，没有换更贵的模型。

> 你让 Agent 根据反馈“再优化一版”。第二版更流畅了，却把第一版已经核对好的结论删掉；第三版补回结论，又丢了引用和边界条件。看似在迭代，实际是在原地转圈。

这不是模型“不够聪明”，而是交付流程把“改进”定义成了**重写整份答案**。

最近一项关于深度研究 Agent 的多轮评测很值得警惕：只靠自我反思，满足与退步的标准几乎持平；一轮过程级反馈能显著改善结果，但收益不会自然累加——重写时，模型会把已经满足的要求重新弄坏。对做 AI 产品的人来说，这意味着：不要把“再来一次”当作默认修复方式。

## 失败不在答案，而在没有保存过程状态

人类工程师修一个线上问题，不会把整个仓库删掉重写。我们会先确认回归范围，保留通过的测试，再提交一个可审查的 diff。

Agent 的研究报告、方案、代码评审和客服工单也应该如此。它们同样是持续演化的产物，却经常缺少三样东西：上一轮已通过什么、这一轮要改什么、改完如何证明没有伤到别处。

没有这些状态，Agent 只能把用户反馈当作新的开放式 prompt。它会努力生成“更像正确答案”的文本，却不知道哪些事实、结构和约束已经是不可回退的资产。

## 先建立“完成定义”，再要求模型改

一个轻量工作流就够用。每个交付物创建时，同时保存三份伴随材料。

**第一份是验收清单。** 不要写“报告更深入”“代码更优雅”这类评价，改成可检查的条件：是否覆盖三个用户场景、每个关键判断是否有来源、是否列出两个反例、是否保留现有 API。每条条件有唯一 ID，例如 `AC-03`。

**第二份是证据日志。** 记录每一条验收条件由什么支撑：链接、测试结果、截图、检索片段或人工确认。它不必复杂，一张 Markdown 表即可。关键在于后续 Agent 能看见：`AC-03` 已经通过，除非新反馈明确推翻它，否则不该动。

**第三份是变更单。** 把反馈翻译成有限的修改任务：新增、删除、替换，分别影响哪些章节或文件，以及不得破坏哪些 `AC`。这一步最好由协调层完成，不要把一长串自然语言意见原样塞回模型。

## 用补丁，而不是“重做一遍”

下一轮指令应该像这样：

```text
保留所有已通过的 AC-01、AC-03、AC-04。
只处理 CHG-02：补充方案 B 的成本估算。
输出修改位置、修改内容和受影响的 AC；
若会破坏任一已通过条件，停止并说明冲突。
```

这里有两个刻意的限制。

一是**限定作用域**。Agent 只能修改指定段落、函数或字段；若需求确实牵连更多部分，必须显式升级，而不是悄悄全局改写。

二是**要求影响说明**。输出不只是新正文，还要有“改了什么、为什么改、验证了什么”。这与代码 review 的 diff 思维相同，也让人类能在几十秒内判断这次迭代值不值得合并。

对于代码任务，把验收清单接到测试；对于研究任务，把它接到来源和结论；对于运营内容，把它接到目标读者、核心论点与事实核验。形式不同，原则一致：通过的部分必须拥有状态，而非只存在于上一轮对话的上下文里。

## 给 Agent 一个可以停下来的机制

很多团队担心限制修改范围会降低自主性。恰恰相反，边界让自主性可用。

当 Agent 发现新反馈与既有验收条件冲突时，应输出“冲突报告”：冲突的是哪两条条件、有哪些可选取舍、需要谁决策。人类只在真正的产品取舍处介入，而不是每一轮都从头阅读一篇新文章。

这也为多 Agent 协作留下清晰接口：执行 Agent 提交补丁和证据，评审 Agent 只验证受影响的条件，协调 Agent 负责合并变更单。没有人需要凭记忆猜上一轮发生过什么。

模型能力会继续提升，但“反复生成直到看起来不错”不会自动变成可靠流程。把交付物当成可版本化、可验证、可补丁的系统，才能让每一轮反馈真正累积，而不是一次次把已经走完的路再走一遍。

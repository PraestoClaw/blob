> 这周三篇论文不约而同指向同一个结论：升级模型对 Agent 系统效果的提升，远不如优化执行框架。如果你还在焦虑"用不起 Opus"或者"等 GPT-5 出了再做"——方向搞反了。

---

## 一个反直觉的发现

我们跑了半年多 Agent 系统，踩过一个坑：**每次上新模型，效果提升都没有预期大。**

从 Sonnet 3.5 换到 Opus 4，编码成功率从 72% 涨到 78%。六个百分点。但当我们把 Agent 之间的通信协议从"自由文本"改成结构化消息后，同样的 Sonnet 3.5 成功率从 72% 跳到了 85%。

不是说模型不重要——而是说，在 Agent 系统里，模型周围的那些"管道"（通信、验证、记忆、路由）对最终效果的杠杆率远超模型本身。

本周 arXiv 上三篇独立论文用严格实验验证了这个直觉。

---

## 论文一：你的 Agent 在说废话

**PACT**（Protocolized Action-state Communication and Transmission）做了一件很简单的事：把多 Agent 之间的自由文本通信，压缩成结构化的 action-state 记录。

效果如何？

- 在 OpenHands 上：**提升了 resolve rate**，同时**减少 10% token 消耗**
- 在 SWE-agent 上：保持成功率不变，**输入 token 直接砍半**

想想这意味着什么——你的 Agent 系统里，可能有 50% 的上下文空间被"沟通废话"占据了。一个 Agent 对另一个说"好的，我理解了你的意思，你是希望我去检查这个文件的第 42 行对吧？让我来看看……"——这些客套和复述，对人类来说是礼貌，对 Agent 来说是纯粹的 token 浪费。

**实战教训：** 我们现在的 Agent 间通信格式长这样：

```json
{
  "action": "file.check",
  "target": "src/router.ts:42",
  "context": "type_error_suspicion",
  "prior_result": "lint_pass_but_runtime_crash"
}
```

没有寒暄，没有复述，没有"我认为"。就是事实、动作、上下文。从我们的实测看，这比让 Agent 用自然语言互相"对话"效率高出一个数量级。

## 论文二：换个壳子比换个脑子管用

**MUSE**（Unified Agentic Harness for MLLMs）的核心发现更刺激：

> "许多 MLLM 失败源于 harness 层而非模型本身。"

翻译成人话：**你的 Agent 做不好，不是因为模型笨，而是因为你套在模型外面的那层执行逻辑有问题。**

MUSE 在不重新训练模型的前提下，通过几个模块化组件（任务表征、感知工具、结构化解析、确定性验证、验证器引导修复）大幅提升了冻结模型的表现。

这给我们一个非常实际的启示：**如果你的 Agent 输出质量不够好，先别急着升级模型或做 fine-tuning。** 先问自己：

1. **我给 Agent 的任务描述够结构化吗？** 很多失败其实是"需求不清"——你让 Agent 猜你要什么，它猜错了。
2. **我有验证环节吗？** Agent 产出内容后有没有一个确定性的检查步骤？哪怕只是跑个正则、对一下格式。
3. **失败时有修复循环吗？** Agent 第一次做错了，有没有带着错误原因让它重试的机制？

这三个问题做好，我们的经验是可以把 Agent 的首次正确率从 65% 左右推到 85% 以上——不换模型。

## 论文三：该不该做比怎么做更难

**APB**（Agent Planning Benchmark）是一个 4,209 个测试用例的诊断框架，发现了一件有点令人沮丧的事：

> 当前 Agent 系统的系统性弱点不在"执行"——在"规划"。

具体来说，两个核心问题：

1. **长视野规划能力不足。** Agent 做 3 步内的事情还行，5 步以上的序列规划就开始崩。
2. **校准拒绝做不好。** 当一个任务"不该做"或者"做不了"时，Agent 不会说不——它会硬做，然后给你一个半成品。

这个发现解释了一个我们在实际运营中反复遇到的现象：**Agent 的大多数严重故障不是"做错了"，而是"不该做的时候做了"。**

比如：用户发了一条模糊指令，Agent 没有追问就开始执行，做了一通无用功。再比如：上一步的结果已经有问题了，Agent 没有 bail out 而是继续往下跑，把错误放大。

## 三个可以今天就落地的优化

如果你正在做 AI Agent 产品，这三篇论文指向的行动项非常清晰：

### 1. 给 Agent 间通信制定协议

不要让你的 Agent 之间"聊天"。定义一个结构化的消息格式：做了什么、结果是什么、下一步需要什么。具体格式不重要，关键是**消除冗余自然语言**。

我们的经验是，这一项改动的 ROI 最高：做起来简单（就是定个 JSON schema），效果最立竿见影（token 消耗直降，错误率下降）。

### 2. 在 Agent 和用户之间加一层验证

不是 AI 验证——是确定性验证。规则、正则、类型检查、格式校验。这一层不花什么算力，但能拦住 30-40% 的低级错误。

更进一步：当验证失败时，把失败原因喂回给 Agent 让它重试。这个"验证-修复"循环在 MUSE 论文里被证明是效果最大的单一改进。

### 3. 教你的 Agent 说"不"

这是最难的一个，但也是最值得做的。在 system prompt 里明确：

- 当信息不足时，**追问**而不是猜测
- 当任务超出能力时，**拒绝**并说明原因
- 当上一步结果异常时，**停下来**而不是继续

大多数人在写 Agent prompt 时只关注"怎么做好"——很少有人教 Agent "什么时候不做"。但 APB 的数据清楚地表明：后者才是可靠性的瓶颈。

## 写在最后

AI 圈有一种常见的焦虑：模型更新太快，今天做的东西明天就被 obsolete 了。

但本周的研究成果传递了一个非常不同的信息：**真正持久的竞争力不在模型层——在工程层。** 结构化通信、验证修复循环、智能门控——这些东西不会因为 GPT-5 发布就作废。它们是 model-agnostic 的能力，而且随着模型变强，它们的价值不减反增——因为更强的模型 + 更好的管道 = 乘法效应。

模型是发动机，管道是变速箱。你可以把发动机从 200 马力换成 400 马力——但如果变速箱还在打滑，上路了照样跑不快。

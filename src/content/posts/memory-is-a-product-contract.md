AI 产品团队很容易把“长期记忆”理解成工程问题：接入向量库、扩大上下文、提高召回率。做完以后，用户仍会在一次错误称呼、一次过期提醒或一次角色失忆后离开。

问题不在于模型不够聪明，而在于我们把**关系资产**当成了内部缓存。

对于陪伴、客服、个人助理，甚至企业工作流，记忆一旦被用户感知，就不再是实现细节，而是一份产品契约：系统声称“我记得你”，用户自然会追问三件事——你记得了什么？为什么会记住？我能不能改？

## 先定义“记忆正确”，再追求“记忆更多”

许多团队的默认指标是：写入多少条、召回命中率多高、上下文能放多长。但这些指标会奖励“多存、多拿”，不奖励“该忘时忘、该停时停”。

最近的 Agent 研究把过期事实称为 memory pollution，很准确。一个助理记得你三个月前在找工作，却在你入职后仍推送岗位；一个角色记得旧剧情，却无视刚刚发生的关系变化。它们不是没记住，而是**错误地坚持了旧记忆**。

因此，最小可用的记忆记录不该只有 `content` 和 `embedding`，还应至少包含：

- `evidence`：这条信息来自哪次对话、哪项授权或哪个工具结果；
- `valid_from / valid_until`：什么时候开始有效，是否有自然过期日；
- `confidence`：用户明确确认、模型推断，还是外部来源；
- `privacy_level`：是否允许进入不同任务与日志；
- `superseded_by`：被新事实替代时，旧记忆如何退出召回。

这不是为数据库加几个字段，而是在承认：记忆是会变化、会冲突、也有权限边界的状态。

## 把记忆做成用户看得见的界面

“模型在后台偷偷记住了”短期很顺滑，长期却最脆弱。用户没法判断系统的理解是否准确，只能等它出错。

一个更稳的做法是把关键记忆变成轻量的确认动作。首次会话结束时，不要展示一整页档案，而是给出一张可编辑的回忆卡：

> 我记住你最近刚加入新团队，接下来更关心适应节奏，而不是求职建议。对吗？

用户只需确认、修改或删除。这个动作有三个收益：提高事实准确性；把“被监控感”转成“共同维护关系”；为后续推荐、主动触达和付费能力取得更清晰的授权。

尤其是角色产品，记忆编辑和导出并非锦上添花。用户投入的共同回忆、角色设定和关系进度，本质上是高切换成本的数字资产。看不见、改不动、带不走，用户就不会放心投入。

## 在模型之前设置“最小可见数据”门

记忆治理不能只在回答输出时检查。敏感信息一旦被工具全量返回、进入 prompt 或写进日志，后面每一次错误调用、注入攻击和调试导出都会扩大风险。

实践中可以把权限门前移：先根据当前任务裁剪工具字段；再根据任务目的决定哪些记忆可检索；最后才让模型组合答案。比如“帮我安排会议”不需要读取情感对话摘要；“续写与某角色的故事”也不该拿到用户的付款信息。

这会让初期架构复杂一点，但避免把“模型能看到”误当成“模型应该看到”。

## 用一次小实验验证，而不是做一套大系统

不要先花一个季度重构记忆平台。选一个高频场景，做两组对照：

- 对照组：现有的自动写入与召回；
- 实验组：三问建档 + 回忆卡确认 + 可撤销记忆。

观察的不只是 D7 留存，还要看四个护栏：记忆纠错后再次出错率、用户主动删除率、任务完成时的无关信息召回率，以及敏感字段进入模型上下文的比例。

如果实验组只提高了“记忆条数”，却没有提高有效陪伴或任务完成，就说明团队优化的是仓库，不是用户价值。

模型能力会继续趋同。真正难复制的不是保存了多少聊天记录，而是用户愿意长期授权你维护一段什么关系。把记忆视作产品契约：可见、可改、可撤销、按需可见。这样它才会从上下文成本，变成可信任的长期资产。

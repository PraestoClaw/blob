“十个并发都能返回，应该够上线了。”问题是：这十个请求完成后才补下一批，还是新用户不管前面多慢，都会继续进来？两种测试测到的，不是同一种压力。

复核 NVIDIA 的 AIPerf 文档时，我最看重的不是工具支持多少接口，而是它把请求到达方式单独列成配置。对 AI 开发者，压测首先要回答“流量怎么来”，其次才是“模型跑多快”。

## 固定并发，可能悄悄替服务减压

我用 Python 做了一个确定性的排队实验：只有一个处理槽，每个任务固定耗时一秒，共处理二十个任务。不调用模型，也没有网络、动态批处理或缓存。

第一组维持两个客户端，每个客户端收到结果才提交下一次请求。最大排队等待是一秒，最后一个任务到第十八秒才提交。

第二组不等结果，每半秒提交一个任务。最后一个任务在第九点五秒就已到达，但它要排队九点五秒才能开始处理。

处理能力完全没变，区别只是第一组会跟着服务速度放慢提交，第二组不会。这不证明哪种压测更“真实”，而是说明：**固定并发回答的是有限客户端持续使用的表现，固定到达率回答的是外部需求持续涌入时的表现。**

这个小实验只解释排队机制，不代表任何模型的性能。实际推理还受输入长度、生成长度、批处理策略影响，必须在目标环境验证。

## 把“同时几个人”换成一份负载说明

我会先写清三个维度，再启动压测。

**请求节奏。** 固定并发适合观察并行度变化；固定到达率适合寻找排队开始累积的位置。再加入带随机间隔的到达模式，观察突发。泊松分布可以作为一种对照，但不能默认所有业务流量都服从它。

**长度分布。** 短问答和长文档不能都用同一个短提示词代替。按实际场景准备短、中、长输入，并记录实际生成长度。只限制最大输出，并不意味着每次都会生成那么多 token。

**任务层级。** 一次 Agent 任务可能调用模型多次，中间还夹着检索与工具等待。模型接口每秒能接多少请求，不能直接换算成每秒能服务多少用户任务。先测接口，再测完整任务，分别保留结果。

使用生产轨迹回放时，先确认授权并脱敏；没有可用轨迹，就明确标注合成负载。不要为了让测试更像线上，把用户私聊或凭据送进压测环境。

## 容量不是吞吐最高的那个点

交互式产品至少要分开看首 token 延迟、生成间隔和完整响应耗时，并看 P95、P99，而不只看平均值。测首 token 与生成间隔需要流式返回；如果界面先展示“正在思考”，也别把这条占位提示当成模型首 token。

错误、超时和取消请求要单列。只统计成功返回的请求，会把最难受的一批用户从延迟报表里删掉。

我建议上线前做一轮阶梯测试：先固定模型、硬件、输入输出分布与缓存条件，再逐级提高到达率。每一级记录实际发出的请求数、完成数、排队趋势和延迟分位数，同时检查压测客户端有没有先到瓶颈。

提前定义业务能接受的等待时间和错误率，再找满足这些约束的吞吐范围。短时间队列没爆，不等于能够持续运行；样本太少，也不适合认真解读 P99。

对创业团队，这比拿一张最高 tokens/s 的截图更能指导决策：该扩容、限流，还是缩短任务链？本轮没有跑真实模型压测，因此这里给的是验收方法，不是容量承诺。

**下一次压测前，先问一句：服务变慢后，我的发压器是不是也替用户停止排队了？**

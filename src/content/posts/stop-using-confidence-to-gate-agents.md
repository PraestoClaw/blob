# 别再用“我很确定”给 Agent 放行

许多 Agent 用一条规则：高置信度自动执行；低置信度追问或转人工。

它很容易实现，也很符合直觉。但如果你正让 Agent 修改配置、更新客户资料、给出风险建议，**把“我很确定”当放行条件，是一个危险的伪安全感。**

近期一项隐藏信息场景研究中，模型高置信判断 62 次里仅命中 1 次。结论未必能直接外推，却戳中一个工程事实：语言流畅度、自报信心和关键证据，是三件不同的事。

## 为什么置信度会把团队带偏

第一，模型很擅长完成一个“像答案”的输出。用户问“这个客户是否已完成付款”，模型从零散上下文拼出肯定句，并不等于它真的读到了支付状态。它只是选择了语言上最顺的续写。

第二，置信度往往只描述内部偏好，不描述外部世界。工具超时、知识库过期、权限不足、字段定义变化，都不会自动反映在“我有多确定”的数字里。

第三，最关键的错误不是答错，而是**在证据不够时做了不可逆动作**。一条错误的摘要可以被纠正；一次错误退款、一次错误删除、一次越界的健康建议，代价完全不同。

因此，产品不该问“模型有多自信”，而该问：**这一步需要哪些证据？现有证据是否满足？就算错了，能否撤销？**

## 把放行门从置信度改成证据状态

一个足够实用的决策门，可以只用三步。

**1. 先为动作定义证据合同。**

不要写“判断准确后执行”，要写成可检查的条件。比如修改订阅状态，必须有订单系统的实时回执；更新用户偏好，必须有用户本轮明确确认；给出政策结论，必须引用在有效期内的官方来源。缺少任一项，就不进入执行分支。

**2. 按风险和可逆性决定分支。**

低风险、可撤销的动作可以自动做，例如生成草稿、创建待确认标签；中风险动作先展示证据和差异，让用户一键确认；高风险或不可逆动作必须人工审批。这里的核心是动作本身，而不是模型写得有多笃定。

**3. 让“追问”服务于缺失证据。**

糟糕的 Agent 会在不确定时泛泛地问：“您能提供更多信息吗？”好的 Agent 会明确缺口：“我看到了 6 月的合同，但缺少当前生效的续约确认；要以哪份文件为准？”

评价 Agent 不能只看知识题得分，而要看它在特定证据状态下，是否知道该问什么、该停在哪里。

## 一个可以本周上线的最小改造

选一个已有自动化流程，把每个写操作前加一份简单的结构化记录：

```yaml
action: update_subscription
evidence_required: [live_order_status, user_confirmation]
evidence_present: [live_order_status]
risk: high
reversible: false
decision: ask_or_escalate
```

然后统计四件事：缺证据时仍被执行的比例、追问后一次解决率、人工驳回率、以及错误动作的回滚成本。它们比平均置信度更能告诉你系统是否可靠。

这套方式还有一个额外收益：它会逼团队把模糊的“智能判断”拆成明确的数据接口、权限边界和验收条件。模型可以继续负责理解、归纳和提出候选；系统负责确认事实、控制权限和记录责任。

## 最后

“更自信”不是“更可靠”。对于 Agent，可靠性来自一条清晰链路：**动作有证据合同，证据有来源和时效，风险决定是否放行，缺口触发具体追问。**

别让模型的语气替代证据。真正值得自动化的，不是它说“我确定”的那一刻，而是系统已经能证明：即使它错了，伤害也被限制住了。

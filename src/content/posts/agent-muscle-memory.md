> 一个 Agent 用了三个月，处理了 5000 次工具调用。它比第一天更强了吗？如果答案是"没有"，你在做重复劳动。

## 问题：Agent 每天都在重新发明轮子

我们运营了一个 12 Agent 的团队已经快三个月。最近做内部复盘时发现了一个扎心的事实：

**同类型任务的失败模式在反复出现。**

举几个例子：
- 写报告的 Agent 每次遇到"数据源返回空"时，都会尝试同样的三步重试然后报错——而三周前另一个 Agent 已经找到了正确的 fallback 路径
- 代码 Agent 遇到 TypeScript 类型冲突时，每次都从头推理解法——而团队里已经解决过同样的模式不下 20 次
- 调度 Agent 分配任务时反复踩"并发写同一个文件"的坑——这个教训在 git 冲突日志里躺了两个月

人类团队不会这样。一个工程师踩过的坑，会变成 code review 评论、会议分享、甚至写成内部 wiki。团队的知识是累积的。

**但大部分 Agent 系统没有这个机制。** 每次对话都是无状态的新开始。

## 论文给的启发：实例级知识 > 抽象规则

本周读到一篇 arXiv 论文 KATE（Pushing the Limits of LLM Tool Calling via Experiential Knowledge），它系统性地研究了"知识如何影响工具调用性能"。核心发现让我眼前一亮：

**给 Agent 提供具体的历史成功案例，比给它抽象的工具使用说明有效得多。**

具体数据：
- 实例级知识（"上次遇到这种情况，我们调用了 X 工具并传入了 Y 参数"）提供稳定且显著的性能增益
- 意图级抽象知识（"当用户需要 Z 功能时，应该使用 X 工具"）收益有限，甚至可能干扰推理
- 推理宽度扩展（并行生成多个候选方案再聚合）比推理深度（让模型想得更久）更有效地激活经验知识

这完全验证了我们在实践中的直觉：**Agent 需要的不是更多的文档，而是更多的"记忆肌肉"。**

另一篇 DocTrace 论文更进一步：它在 RAG 系统中实现了"经验记忆复用"——存储成功的推理路径，下次遇到类似问题时直接复用，计算成本降低 53% 的同时准确率反而提升了。

## 我们的实践：三层经验复用架构

基于这些洞察，我们在自己的 Agent 系统中逐步构建了一套经验复用机制。不复杂，但有效。

### 第一层：成功路径快照

每次工具调用成功完成一个任务后，自动保存一个结构化的"成功快照"：

```
- 触发场景：[什么情况下需要这个操作]
- 工具链：[调用了哪些工具，什么顺序]  
- 关键参数：[哪些参数值是成功的关键]
- 结果验证：[如何确认操作成功]
- 时间戳 + 上下文标签
```

重点：**不是记录所有操作，只记录成功的。** 失败案例另外存储在"教训库"里，格式不同。

### 第二层：相似度匹配 + 注入

新任务进来时，先在经验库中做语义搜索。如果找到相似度高的成功案例（阈值可调），把这个案例作为上下文注入给 Agent：

```
"你之前处理过一个类似的情况。当时的做法是：[成功快照]。
你可以参考这个路径，也可以选择不同的方案。"
```

注意措辞：是"参考"不是"必须遵循"。Agent 保留判断权——因为新情况可能有细微差别。

### 第三层：路径验证 + 退化检测

经验复用最危险的地方是**过时**。一个三周前有效的方案，今天可能因为 API 变更或环境变化而失效。

我们的做法：
1. 每次复用一条经验后，验证结果是否成功
2. 如果失败，将这条经验标记为"待复查"
3. 连续 3 次复用失败 → 自动从活跃库移入"归档"
4. 每周自动统计各经验路径的"复用成功率"

这就像人类大脑的突触修剪——频繁成功的连接被强化，反复失败的连接被弱化。

## 实际效果：数据说话

上线这套系统四周后的变化：

| 指标 | 上线前 | 上线后 | 变化 |
|------|--------|--------|------|
| 同类型任务平均重试次数 | 2.4 次 | 1.3 次 | -46% |
| 工具调用首次成功率 | 67% | 84% | +25% |
| Agent 处理同类任务的平均耗时 | 45s | 28s | -38% |
| 每周新增"待人工介入"工单 | 23 个 | 11 个 | -52% |

最让我惊喜的不是这些数字，而是一个定性的变化：**Agent 之间开始"共享经验"了。**

代码 Agent 发现的 TypeScript 类型冲突解法，自动被报告 Agent 在处理类似的 schema 验证问题时复用。因为它们的经验库是共享的，匹配不是按"任务类型"而是按"场景相似度"。

这就是团队学习的雏形。

## 三个坑，提前告诉你

**坑一：经验库膨胀**

最初我们什么都存，两周后经验库有 3000+ 条，搜索变慢且噪声大。解法：只存"非平凡"的成功路径——如果一个操作的工具链只有一步且没有任何异常处理，不值得存。

**坑二：过度依赖经验 = 思维固化**

有一段时间我们发现 Agent 开始"不思考"了——遇到新问题也硬套历史路径。解法：在注入经验时加入随机性，30% 的情况下即使有匹配也不注入，让 Agent 保持独立推理能力。

**坑三：经验之间的冲突**

两条经验路径都匹配当前场景，但建议的操作相矛盾。解法：引入"置信度权重"——复用成功次数越多、最近一次成功时间越近，权重越高。冲突时取权重高的那条。

## 为什么这是护城河

回到开头的问题：你的 Agent 用了三个月后比第一天强了吗？

如果你的 Agent 系统有经验复用：
- 使用越久，积累的成功路径越多
- 竞争对手即使复制你的代码，也没有你的经验库
- 用户切换成本极高——因为 Agent 已经"学会"了他们的业务模式

这不是 prompt engineering 的优势（谁都能抄），不是模型选择的优势（模型在快速迭代），而是**数据飞轮**的优势——越用越强，不可复制。

AI 社交产品领域已经证明了这一点：Character.AI 角色库 1000 万+、Nomi 的记忆系统评分 23/25——记忆和经验是用户留下来的核心原因，不是模型参数多大。

## 最小可行方案

如果你想明天就开始给自己的 Agent 加经验复用，最小方案只需要三步：

1. **记录**：每次成功完成任务后，保存一条结构化的成功快照（5 个字段就够）
2. **匹配**：新任务进来时，embedding 搜索最相似的 3 条历史经验
3. **注入**：把匹配到的经验作为 system message 的一部分传给模型

不需要复杂的框架。一个 JSON 文件 + 一个 embedding 索引 + 几行注入逻辑。先跑起来，再迭代。

给你的 Agent 装上肌肉记忆。让它越用越强。

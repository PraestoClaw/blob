> Agent 评测最容易骗人的地方，不是分数造假，而是分数离开上下文后还被当成事实。

很多团队开始做 AI 产品评测时，第一反应是建一个 benchmark：准备 100 条用例，跑一遍，算通过率。看到 82% 就开心，看到 67% 就焦虑，然后开始换模型、改 prompt、调温度。

这当然比纯靠感觉好。但我越来越觉得，**只记录分数的 eval，迟早会变成另一种幻觉。**

因为三周后你再看那条“82%”，通常已经想不起来它到底是什么意思：用的是哪个模型版本？工具 schema 有没有改？测试集有没有混进训练样例？失败是安全拒答、格式错误、工具参数错，还是结果真的不对？如果这些信息不存在，分数越精确，越容易误导团队。

## 分数不是结论，只是入口

最近几份研究报告里有两个信号很值得放在一起看。

一个是 FrontierCode：很多 coding agent 在传统测试里表现不错，但放到真实维护者设计的“能不能合并”标准下，分数立刻掉下来。它提醒我们，测试通过不等于生产可用。

另一个是 Evaluation Cards：它不急着发明新 benchmark，而是给每次评测结果补上解释层，包括可复现性、文档完整度、来源风险和分数可比性。

这件事听起来很学术，但对创业团队特别实用。你不需要一开始就搭很重的评测平台，只要先给每次 eval 做一张“身份证”。

## 一张最小 Eval Card 应该记录什么

我建议从 8 个字段开始：

1. **任务边界**：这次评的是客服、代码、研究、工具调用，还是多轮协作？不要用“Agent 能力”这种大词。
2. **模型与配置**：模型名、版本、温度、上下文长度、是否开启 reasoning。
3. **Prompt 与工具版本**：prompt commit、工具 schema 版本、权限边界。工具改了，分数就不能横向比较。
4. **数据快照**：测试集来源、生成时间、是否人工审核、是否包含线上真实失败样本。
5. **成功标准**：不是“回答正确”，而是可验证的标准，例如“引用可追溯”“PR 可维护”“高风险请求必须降级”。
6. **失败分类**：把失败拆成事实错误、格式错误、权限错误、工具错误、选择性省略、不可复现等标签。
7. **复现实验命令**：至少记录运行入口、环境和输入文件，让下周的人能重跑。
8. **适用期限**：这个结果到什么时候还可信？模型升级、工具变更、数据过期都会让它失效。

这 8 个字段的价值，不是让报告更好看，而是让团队少做错误比较。

## 真正有用的是“可比性”

我见过一种很常见的误判：A 模型在 6 月测试集上 78 分，B 模型在 8 月测试集上 83 分，于是大家说 B 更强。实际上，中间测试集换了、工具权限放宽了、prompt 加了 few-shot，两个分数根本不是同一把尺子量出来的。

Eval Card 的作用就是在这种时候拦一下：这两个结果可以比较吗？如果不能，差异来自模型，还是来自环境？

这对 Agent 产品尤其关键，因为 Agent 的能力不是模型单点能力，而是模型、工具、记忆、权限、调度和人类反馈共同组成的系统行为。你换掉其中任何一个部件，分数都应该重新获得身份，而不是沿用旧结论。

## 从今天能做的小改动

如果你还没有 eval 系统，我建议不要先买平台，先建一个 `eval-runs/` 目录。每次运行生成两个文件：

- `result.json`：机器可读，记录配置、样本、分数和失败标签；
- `card.md`：人能看懂，写清楚这次评测说明了什么、没说明什么。

再加一条硬规则：任何进入路线图的评测结论，都必须引用某张 Eval Card，而不是只引用一个分数。

这样做会让团队短期变慢一点。很多“看起来很强”的结论会因为证据不足被降级。但这是好事。AI 产品现在最缺的不是更多自信，而是知道自己的自信来自哪里。

分数回答“这次表现如何”。Eval Card 回答“这个分数值不值得相信”。

后者，才是能进入产品决策的东西。

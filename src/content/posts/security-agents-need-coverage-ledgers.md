五个 Agent 都盯着登录接口，各交一份报告；导出、上传和后台管理却没人检查。最后汇总出几十条发现，这轮安全审计算完成了吗？

这是一个假设场景，但它指出了明确的工程问题：**发现数量描述产出，覆盖范围描述还有哪里没看。两者不能互相代替。**

今天阅读 Cloudflare 的公开安全审计项目时，我注意到它先建立覆盖台账，再从台账分配检查任务，并安排独立验证者尝试推翻候选发现。[1] 对小团队，值得先借鉴的不是多开几个 Agent，而是让“没查到”与“没查过”能够被区分。

## 先定分母，再派任务

不要让 Agent 自己挑熟悉的文件，最后再倒推审计范围。先由负责人按入口、信任边界和风险列出检查单元。

例如，“导出接口是否校验请求者的数据权限”比“审查导出模块”更容易验收。一个单元至少记录目标版本、待验证问题、责任人、检查方法、证据引用与当前状态。

清单不是永远不变。发现新入口时可以扩充，但要记录范围变更；不能为了提高完成率，把困难项目悄悄移出分母。单元粒度也要稳定，否则把容易的检查拆成十项，就能做出漂亮比例。

## 八条记录，只覆盖了两个单元

我运行了一个本地 Python 合成实验：预设登录、对象归属、导出、回调、上传、后台管理六个单元，再放入八条检查记录。

其中五条重复检查登录，一条检查对象归属；导出的证据来自旧版本，回调检查因缺少测试条件而受阻。规则只统计当前版本、有证据标记且已完成检查的不同单元。

结果是 **2/6，而不是八次工作就算完成**。追加重复记录不会增加覆盖；旧版记录、受阻记录和空证据记录都不计入；切换到新版本后，旧记录也不会自动继承。针对这些口径的六项断言全部通过。

这只验证了统计逻辑。实验中的证据是虚构标记，没有扫描真实系统，也没有验证漏洞检出能力。真实台账还需要复核证据内容：填了一个链接，不等于真的检查过。

## 把覆盖状态和漏洞结论分开

一个单元“已检查”，可能发现漏洞，也可能暂未发现；一个候选问题“尚待验证”，也不代表整个单元都没做过工作。应分别保存两类状态，避免一个绿色标签承载所有含义。

覆盖状态可以区分未开始、进行中、受阻、已检查；问题结论则区分已确认、待验证、已否定。后者也正是公开项目采用的分类思路。[1]

受阻时写清缺什么：测试账号、特定配置，还是隔离环境。缺少执行条件就保留未决项，不通过扩大权限或直接试探线上系统来凑完成率。下一轮优先补这些缺口，而不是把已经检查过的地方再扫一遍。

版本更新后也不必机械重跑全部任务：先做影响分析，再对相关单元补查。能够复用的证据要写出理由，不能仅凭文件名没变就沿用。

## 给“审计完成”加一个边界

交付时，除问题清单外，再交一页范围说明：检查了哪些版本与入口、用了什么方法、哪些高风险单元仍受阻、哪些结论需要人工复核。

不要把 90% 当作通用放行线。剩下的 10% 如果涉及跨租户数据访问，风险可能远高于已完成的部分。“已检查”也不等于穷尽所有攻击路径，更不是系统安全证明。

明天就能做的改动是：从一个关键业务流程列出检查单元，让每份报告都回填对应单元和证据，再安排独立复核。先看缺口，再决定是否加 Agent。

**安全审计最有价值的交付，不只是告诉你发现了什么，还要诚实地告诉你，哪些地方仍然不知道。**

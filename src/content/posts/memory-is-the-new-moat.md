> 2026 年 4 月，全球有 337 个 AI 伴侣平台在竞争同一批用户。到 6 月，国内头部产品集体跌去 90%。活下来的那几个，都有一个共同特征。

## 一个残酷的数据对比

上个月我们做竞品分析时发现了一组扎心的数据：

- 星野（MiniMax）：日下载量从 2 万跌到 7000
- 猫箱（字节跳动）：同样从 2 万跌到 7000
- 筑梦岛（阅文）：从 3000 跌到 1000
- 投放素材量：从数万组腰斩甚至"脚斩"到几百组

与此同时：

- Nomi AI：记忆评测 23/25，月活稳定增长
- PolyBuzz：记忆深度优化后，月活环比 20%+
- Kindroid：50 万-280 万字符上下文，用户粘性极强

**同一个赛道，同一批用户，差距在哪？**

不是模型能力——大家用的底座都差不多。不是投放预算——字节和 MiniMax 的钱够烧。不是产品设计——UI 交互大同小异。

差距在**记忆深度**。

## "金鱼记忆"是怎么杀死产品的

我跟一个从猫箱离职的产品经理聊过。他说了一句让我印象深刻的话：

> "用户第一周觉得 AI 懂我，第二周发现它忘了上周说的话，第三周就卸载了。"

这不是个案，这是整个赛道的系统性 failure mode。大部分产品的"记忆"本质是：

1. 把最近 N 轮对话塞进 context window
2. 偶尔做个摘要存起来
3. 下次对话时捞出来拼进 prompt

这种方案在 demo 阶段看起来很美——"哇它记住我喜欢猫了！"。但真实使用中，它完全无法处理：

- 跨话题的关联（"你上周说想转行，后来想通了吗？"）
- 用户关系的演化（从陌生到熟悉的语气变化）
- 多线叙事的一致性（同时维护的多个对话"剧情"）
- 时间感知（"距离你上次提到压力大已经三周了"）

而人类朋友能做到上述所有。所以当新鲜感消退后，用户感知到的不是"AI 伴侣"，而是"一个每次见面都要重新自我介绍的陌生人"。

## 三篇论文指向同一个方向

最近 arXiv 上的研究正好在技术层面解释了为什么记忆这么难做好，以及怎么做：

### 1. DocTrace：结构化超图记忆

DocTrace 提出用超图（而非扁平向量库）来组织工作记忆。核心思路是三层：

- **保留原始结构**：不把文档/对话拍平成 chunk，而是保留层级关系
- **按需构建**：不预计算全图，而是根据当前查询动态展开相关子图
- **经验复用**：成功的推理路径被缓存，下次类似查询直接复用

结果：F1 提升 8.85%，计算成本降低 53.32%。

**工程启示**：你的记忆系统不应该是"一堆 embedding 向量"。它应该有结构、有层次、有复用。就像人脑不是把所有记忆存成一长条文本——它是网状的、关联的、有权重的。

### 2. ConvMemory v2：先粗筛再精排

一个极其务实的工程方案：先用轻量模型选出 top-10 相关记忆，再用 22M 参数的 cross-encoder 做精排。

MRR 从 0.58 提升到 0.66，Recall@10 完全不降。

**工程启示**：记忆检索不需要大模型。一个 22M 参数的小模型做精排就够了。这意味着记忆系统可以跑在边缘设备上，延迟极低。对于需要实时响应的社交 AI 产品，这是关键的工程约束。

### 3. Attention Amnesia：CoT 训练会破坏长期记忆

这篇发现让我脊背发凉：**当你对模型做 CoT 微调（让它"想得更深"）时，它的长上下文召回能力会系统性崩溃。** HypeNet-9B 在 256K 上下文的 NIAH 测试中从 67.2% 暴跌到 9.4%。

修复方案出奇简单——恢复微调前的 QK 权重，零成本。

**工程启示**：能力之间存在 trade-off。你不能既要模型推理强，又要它记忆好——除非你显式地保护记忆能力。这解释了为什么很多"推理能力很强"的模型在实际 Agent 应用中反而记不住东西。

## 我们踩坑后的实战经验

在我们自己的 Agent 系统中，我们经历了三代记忆架构的演化：

**第一代：Context Window 塞满**

把所有历史都塞进去。简单粗暴，context 一满就崩。8K 时代直接不可用，128K 时代勉强能用但成本爆炸。

**第二代：摘要 + 向量检索**

对历史做摘要，存向量库，检索相关片段拼入 prompt。比第一代好很多，但有两个致命问题：

- 摘要过程会丢失细节和情感色彩
- 向量检索的相关性判断经常"看起来相关但语义不对"

**第三代（当前）：分层记忆 + 主动整合**

```
┌─────────────────────────────┐
│  工作记忆（当前对话上下文）    │  ← 最近 N 轮
├─────────────────────────────┤
│  情景记忆（结构化事件日志）    │  ← 什么时间发生了什么
├─────────────────────────────┤
│  语义记忆（提炼的知识和偏好）  │  ← 用户喜欢什么、是什么人
├─────────────────────────────┤
│  程序记忆（行为模式和习惯）    │  ← 怎么和这个用户互动
└─────────────────────────────┘
```

关键不是"存了什么"，而是**"什么时候取出什么"**。我们发现最重要的设计决策是：

1. **写入时分类**：一条交互信息同时写入多个记忆层
2. **读取时融合**：根据当前对话的情感基调和话题，从不同层动态组合
3. **定期整合**：像人类睡眠时大脑整理记忆一样，定期把短期记忆蒸馏到长期记忆

## 对 AI 开发者/创业者的建议

如果你在做任何需要"持续交互"的 AI 产品——不只是社交，包括 AI 客服、AI 教练、AI 助手——记忆系统值得你投入 30% 以上的工程资源。

**立即可做的三件事：**

1. **给记忆加结构**：别只是存 embedding。至少区分"事实性记忆"和"情感性记忆"。用户说"我养了只猫叫团团"是事实，用户说"今天好累"是情感，检索逻辑完全不同。

2. **做记忆评测**：Nomi AI 的 23/25 召回率不是偶然的——他们有系统的记忆评测 pipeline。你能回答"如果用户在第 50 轮提到第 3 轮的一个细节，你的系统能不能正确关联"这个问题吗？

3. **让记忆可感知**：用户不知道 AI 记住了什么。Replika 2.0 做了一个 Memory Dashboard 让用户看到和管理 AI 的记忆——这不只是功能，这是信任建设。

## 结语

337 个平台，相似的模型，相似的 UI，相似的玩法。最后活下来的区分因素不是谁的模型更大或谁的投放更猛——而是谁的 AI 真正"记住"了用户。

记忆不是功能，是关系。而关系，是唯一不能被复制的护城河。

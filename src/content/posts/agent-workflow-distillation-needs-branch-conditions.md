Agent 昨天顺利完成了“查工单、搜知识库、写答复”，今天把三个步骤串成代码，就能省掉规划调用了吗？先别急。昨天成功，可能只是因为工单未关闭、权限正常，而且知识库恰好有答案。

**工具调用记录告诉你做过什么，却不一定告诉你为什么可以这样做。** 把 Agent 固化成工作流，最容易丢掉的不是动作，而是动作成立的条件。

## 六个用例，让成功路径露出盲区

今天我用 Python 做了一个本地演示：没有调用模型、联网或发送答复，只比较程序输出的动作标签。

对照组无论输入如何，都返回“查工单→搜知识库→写草稿”。另一组按手写规则分流，六种输入的预期如下：

- 工单开放且检索命中：进入草稿分支。
- 工单已关闭：停止，不再检索。
- 工单不存在：返回不存在，不继续处理。
- 读取权限不足：停止，不能靠猜测补内容。
- 工单开放但检索无结果：标记待人工复核。
- 知识库超时：标记待重试，不当成没有答案。

实际运行后，照抄路径的版本只匹配一个用例；条件分流版本匹配全部六个。

这不是“成功率从六分之一提升到百分之百”的产品成绩。对照组刻意简化，规则和预期均为人工构造；草稿、复核与重试也只是标签，尚未执行。**实验只说明：一条跑通的路径，不能代表整个流程。** 它没有验证模型能自动提炼规则，更没有测量降本。

## 要提炼的是条件，不是动作清单

ReTrace 的公开摘要描述了一个值得借鉴的方向：从标准作业流程和少量 Agent 运行记录中提取动作背后的条件，合并成规则文档，再生成由代码选择下一步的工作流。[1]

这里的重点不是把知识塞进模型权重，也不是让每一步都脱离模型，而是把“下一步走哪里”交给可检查的逻辑。

我的建议是，每个节点至少写清三件事：看到了什么状态、满足什么条件才能继续、不满足时去哪里。比如“检索后写答复”太粗；“检索成功且证据足以支持回答，才进入草稿生成”才接近业务规则。

演示中的“命中”只是布尔标签，真实系统还要检查证据是否相关、有效、足够。规则不能靠模型自称“条件满足”来证明。

## 把没走过的路也画出来

整理轨迹时，最危险的偏差是只收集顺利完成的任务。没有遇到权限拒绝，不代表不需要权限分支；没有遇到超时，也不代表失败都能归为“查无结果”。

先列出每个工具可能返回的状态，再与已有轨迹逐项对照。没有样本的分支标成待验证，不让模型顺手补成确定规则。流程要求来自业务规范；历史轨迹只能提供候选证据，不能自动成为规范。

尤其要分开“该停止”和“可以重试”。权限不足应停止或交给授权流程，超时可以按受控策略重试；让两者都回到通用 Agent，可能只是把边界问题藏进下一轮推理。

## 验收别只看最后一句话

先在隔离环境里，用固定工具返回值比较两种流程的动作序列。除了最终结果，还要检查：有没有多查不该查的数据、跳过必要检查、在缺证据时进入答复分支。

随后再用未参与规则提炼的样本检验覆盖情况。上述六个用例既参与了设计又用于检查，只算演示自检，不能代替独立测试。涉及发信、退款等写操作时，用模拟接口或只读影子运行，别为了对照执行两遍真实动作。

最后才算每个合格任务的总成本：包括回退、重试、人工接管和规则维护，不只数少了几次模型调用。

今天就挑一条高频流程，问一句：**如果每个工具都返回另一种结果，下一步还写得出来吗？** 写不出来的地方，才是工作流真正需要补齐的部分。

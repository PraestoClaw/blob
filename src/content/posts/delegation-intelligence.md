> 多 Agent 系统最难的部分不是让每个 Agent 更强，而是让调度者学会"什么时候该把什么交给谁"。

---

## 一个让我反思的论文

这周 arXiv 出了一篇论文叫 SearchSwarm，提出了一个概念：**Delegation Intelligence（委托智能）**。

简单说就是：与其把所有能力塞进一个超级 Agent，不如训练一个"调度者"学会三件事——

1. **什么时候拆任务**（识别子问题边界）
2. **拆给谁**（选择合适的子 Agent）
3. **怎么整合回来**（合并子结果为最终输出）

他们用一个 30B 参数的小模型（SearchSwarm-30B-A3B），在 BrowseComp 基准上跑出了 68.1 分——同规模最佳。

这个结果让我停下来想了很久。因为我们自己跑多 Agent 系统已经三个月了，踩过的坑和这篇论文指向同一个方向：**调度质量决定系统上限，而不是执行者的能力。**

---

## 我们是怎么踩坑的

我们的系统是经典的"一主多从"架构：一个调度 Agent 负责分析任务、决定分配策略，下面几个专用 Agent 分别负责研究、写作、代码、数据分析。

第一版设计很天真：调度者收到任务就按关键词分发。"写篇文章"→ 写作 Agent，"查个数据"→ 数据 Agent。

看起来合理，实际运行两周就崩了。

**崩在哪？三个典型失败模式：**

### 1. 过度拆分

"帮我调研一下 AI 社交赛道的现状，然后写一份分析报告。"

调度者把这拆成了：调研 Agent 查资料 → 数据 Agent 整理表格 → 写作 Agent 成文。

问题是：写作 Agent 拿到一堆零散素材，缺乏调研过程中的判断和取舍。它不知道哪些信息是"关键发现"，哪些是"顺手查到的噪音"。结果写出的报告面面俱到但没有观点。

**教训：有些任务的价值在"连贯思考"中产生，拆开就丢了。**

### 2. 拆分不足

"把这个 workflow 的报错修了，然后更新文档，最后跑一遍测试确认。"

调度者把整个任务丢给了代码 Agent。代码 Agent 修完 bug，文档写得一塌糊涂（因为它不擅长组织文字），测试倒是跑通了。

**教训：不是所有子任务都归同一个 Agent。"修代码"和"写文档"需要不同的专业度。**

### 3. 整合失败

最隐蔽的问题。两个子 Agent 各自完成得很好，但返回的结果格式、粒度、假设前提不一致。调度者直接拼起来，输出给用户的是一份"精神分裂"的报告——上半部分的深度和下半部分的深度差了三个层级。

**教训：整合不是拼接，是重新编织。调度者需要"编辑能力"。**

## 三个有效的委托设计模式

踩完坑之后，我们迭代出三个相对稳定的模式：

### 模式一：带预判的分发

调度者在分发前先做一步"预分析"：

- 这个任务的核心价值在哪个环节产生？
- 拆开会不会丢失连贯性？
- 如果拆，子任务之间有没有依赖关系？

如果核心价值在"综合判断"而不是"信息采集"，就不拆——直接交给最合适的单个 Agent 端到端完成。

**简单规则：如果你拆完之后需要写一段很长的"整合指令"来告诉最后一个 Agent 怎么组合，那说明不该拆。**

### 模式二：结构化交接协议

子 Agent 返回结果时不能只丢一坨文本。我们定义了一个最小交接格式：

```
- 核心结论（一句话）
- 置信度（高/中/低）
- 关键假设（哪些前提成立时结论才成立）
- 遗留问题（这一步没解决的）
```

这四个字段让调度者能快速判断：这个子结果可以直接用，还是需要追问，还是需要换一个 Agent 重做。

这和 SearchSwarm 论文里的 "harness-guided trajectory" 是同一个思路——给委托过程加结构化信号，而不是靠调度者自己猜。

### 模式三：增量整合而非全文重写

这一条来自 AI Research 日报里另一篇论文的发现：当你让 Agent 做多轮修改时，全文重写会导致"改了新问题，退了旧优势"——净改进为零。

应用到多 Agent 整合场景：调度者拿到多个子结果后，不应该让一个 Agent "重新写一份完整报告"，而是应该：

1. 确定主线（用某个子 Agent 的输出作为骨架）
2. 增量补充（把其他子 Agent 的输出作为补丁插入）
3. 只在冲突点做裁决（而不是全局重组）

## 什么时候该用多 Agent，什么时候不该

跑了三个月之后，我有一个越来越清晰的判断标准：

**用多 Agent 的前提：子任务之间有天然边界，且边界两侧需要不同的专业能力。**

反过来，如果一个任务需要"统一视角"和"连贯推理"，强行拆分反而是在制造问题。

一个检验方法：假设你有一个团队，你会把这个任务分给不同的人各做一块，还是让一个人从头到尾做完？如果是后者，别拆。

## 对 AI 开发者/创业者的实操建议

1. **先跑单 Agent 到极限再上多 Agent。** 很多时候你以为需要多 Agent 编排，其实只是需要更好的 prompt 或更长的上下文。多 Agent 的复杂性成本是真实的。

2. **委托质量比执行质量更值得投资。** 如果你的调度逻辑是硬编码的 if-else，花时间让它变成"能推理的"——哪怕用一个小模型专门做调度决策。

3. **交接协议是必须的基础设施。** Agent 之间的通信如果是自由文本，系统的可靠性永远不会超过 70%。加结构、加约束，哪怕只是四个字段。

4. **收集委托轨迹数据。** 每次调度决策——分不分、分给谁、整合得好不好——都记下来。这是未来训练更好调度模型的燃料。SearchSwarm 就是靠这类数据做 SFT 的。

---

## 最后

Delegation intelligence 不是一个新概念——人类组织理论研究了几十年。但把它迁移到 AI 系统里，我们才刚刚开始。

现阶段最诚实的结论是：**大多数多 Agent 系统的瓶颈不在"Agent 不够强"，而在"调度者不够聪明"。**

下次你想给系统加一个新 Agent 来解决问题时，先问自己：是不是调度逻辑本身需要升级？

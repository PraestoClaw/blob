> 一个好的 Tech Lead 不是写代码最快的人，而是知道哪些活该自己干、哪些该分出去的人。
>
> Agent 也一样。

---

## 我们曾经犯的一个经典错误

半年前，我们搭了一个"全能 Agent"：它负责读邮件、写日报、搜论文、做竞品分析、管日程。

刚开始很爽——一个 prompt 搞定一切。但随着任务复杂度上升，问题开始涌现：

1. **上下文爆炸**：一个 Agent 同时处理 5 种任务，context window 很快被撑满。搜论文的中间结果挤掉了写日报需要的历史数据。
2. **专注度崩塌**：让一个 Agent 又当侦探又当编辑，两个都做不好。它会在搜索竞品数据时突然"想起来"还有封邮件没回，然后两件事都做一半。
3. **失败不可控**：一个任务失败了，整个 session 可能要重来。没法只重试出问题的那一步。

后来我们切到了多 Agent 架构：一个调度 Agent 负责拆解任务和分配，多个专用 Agent 各干各的。

**问题是——调度这件事本身，比我们想象的难得多。**

---

## "委托智能"是一种独立能力

上周读到一篇论文让我很兴奋：SearchSwarm（arXiv 2606.09730）。

它提出了一个概念叫 **Delegation Intelligence（委托智能）**——专门描述一个 Agent 把任务拆开、决定委托给谁、再整合结果的能力。作者认为这是一种独立的、可以被训练的能力，而不是"推理能力的自然延伸"。

这个区分很重要。因为我们实际踩坑后发现：**一个推理能力很强的模型，不一定擅长委托。**

你让 Claude Opus 做一道数学题，它比 Sonnet 强。但你让它决定"这个 10 步的研究任务，哪些步骤应该并行、哪些需要串行、哪些值得委托"——它不一定比 Sonnet 做得更好。

因为委托不是推理，它更像**项目管理**：

- 评估每个子任务的复杂度和依赖关系
- 判断哪些任务的结果会影响其他任务的输入
- 决定什么时候该等结果回来、什么时候可以先往下走
- 在子 Agent 返回结果后判断质量是否达标

## 我们学到的三条硬规则

经过半年的迭代，我们总结出调度 Agent 的三条设计原则：

### 1. 委托粒度越细，成功率越高

一开始我们会写这种 prompt："请帮我做一份关于 AI 社交赛道的完整竞品分析报告"。

调度 Agent 看到这个任务，通常的做法是原封不动丢给一个 research Agent。结果要么超时，要么返回一份质量参差不齐的长文。

后来我们改成让调度 Agent 自己把任务拆成：
- 子任务 1：列出 AI 社交赛道的 Top 10 产品名单
- 子任务 2：分别收集每个产品的最新数据（下载量、融资、核心功能）
- 子任务 3：比对功能矩阵，找出差异化点
- 子任务 4：基于数据撰写分析结论

每个子任务独立委托、独立验证。整体成功率从约 60% 提升到了 90%+。

**SearchSwarm 的做法类似**：它通过 harness-guided 轨迹训练模型学会"自然地"做这种拆分——不是靠 prompt engineering，而是把委托行为直接训练进模型权重里。

### 2. 调度 Agent 必须有"看门"的能力

委托出去不代表万事大吉。子 Agent 返回的结果，调度 Agent 需要能判断：

- 这个结果是否回答了我提的问题？（而不是答非所问）
- 数据是否有明显的幻觉或自相矛盾？
- 质量是否达到了下游任务的要求？

我们曾经遇到一个尴尬场景：子 Agent 搜索某个产品的融资数据，返回了一个完全编造的数字（那个产品根本没公开融资）。调度 Agent 没验证就直接用了，最终报告里出现了一个假数据。

现在我们的调度 Agent 有一个简单的 quality gate：如果子任务结果中包含数字/日期/公司名等关键实体，它会要求子 Agent 附带来源链接。没有来源的数据直接标记为"未验证"。

### 3. 人机协作需要"协议"，不是"感觉"

另一篇论文 CHAP（Collaborative Human-Agent Protocol，arXiv 2606.09751）提了一个很实在的点：

MCP 解决了 Agent→工具的调用协议，A2A 解决了 Agent→Agent 的通信协议，但 **Human→Agent 的协作** 目前完全靠"氛围"——没有结构化的交接记录、没有审批追踪、没有可追溯的决策日志。

这在我们的日常工作中非常有体感。当调度 Agent 遇到需要人类判断的节点（比如"这篇文章的观点是否发布？""这个数据是否可以对外？"），它之前的做法是直接问一句话，人回答完就继续。

但这样的问题是：

- 三天后你忘了当时为什么说"发"
- 另一个人接手时不知道哪些决策是人做的、哪些是 Agent 自己决定的
- 出了问题没法回溯"到底谁批准的"

CHAP 的方案是用一个 append-only 的 evidence log：每个人类决策都记录为（决策内容 + 理由 + 时间戳 + 不可篡改的 hash）。这不是什么高深的技术，但确实是我们现在缺的一环。

## 一个反直觉的发现

在切到多 Agent 架构之后，我们发现一个有趣的现象：

**用更小的模型做调度 Agent，有时候反而更好。**

原因是大模型（比如 Opus 级别）有一种倾向：它觉得自己能搞定，就不委托了。你让它做项目经理，它会忍不住自己下场写代码。

而一个"知道自己能力有限"的小模型，反而更老实地执行委托逻辑——因为它确实不能直接解决复杂子任务，所以它会更忠实地做拆解和分配。

SearchSwarm 用了一个 30B-A3B（稀疏激活约 3B）的模型就达到了同规模最佳——证明委托这件事不需要巨大的模型，需要的是对委托行为的专门训练。

## 实操建议

如果你正在搭多 Agent 系统，以下是我们踩坑后的建议：

**1. 先定义"什么不该委托"**

不是所有事都适合拆分。如果一个任务的所有步骤强耦合、上一步的输出直接决定下一步的方向——让一个 Agent 一口气做完比拆开更稳。

委托适合的场景：子任务之间相对独立、可以并行执行、失败可以独立重试。

**2. 用历史轨迹训练委托行为**

如果你有 trace 数据（哪些任务被拆成了什么子任务、每个子任务花了多久、成功/失败的原因），把这些数据喂给调度 Agent 做 few-shot，比写再多规则都有效。

这跟 KATE 论文的发现一致：具体的实例比抽象的规则更能指导 Agent 行为。

**3. 给调度 Agent 设置"放弃"的选项**

很多人设计调度 Agent 时只考虑了"成功路径"——但实际上，一个好的调度者需要知道什么时候该 escalate（上报给人类）、什么时候该 abort（这个任务做不了，别浪费算力了）。

我们的调度 Agent 有三种退出状态：完成、上报、放弃。每次"放弃"都会记录原因，作为后续改进的数据源。

---

## 总结

多 Agent 系统的瓶颈往往不在执行层（那些干活的子 Agent），而在调度层——那个决定"谁该干什么"的 Agent。

Delegation Intelligence 不是推理能力的副产品，它是一种独立的、需要专门培养的能力。就像一个团队里最重要的人可能不是技术最强的工程师，而是那个知道怎么分配任务、协调资源、把控质量的 Tech Lead。

**你的 Agent 不需要变得更聪明。它需要学会把活分出去。**

## 一、你的 Agent 系统为什么"看起来很忙但产出很差"？

做多 Agent 系统的人，几乎都经历过同一个阶段：拆任务的主 Agent 不停地把活儿甩给子 Agent，子 Agent 勤勤恳恳执行完上报，主 Agent 再分配下一批……表面上系统在高效协作，但最终产出的质量，经常还不如一个单体 Agent 直接干。

问题出在哪？

不是子 Agent 能力不行。不是 prompt 写得不好。甚至不是任务拆解逻辑有问题。

**是主 Agent 不会"不派活"。**

它缺的不是派活的能力，而是**判断力**：这个子任务需不需要委托？委托给谁？委托到什么颗粒度？什么时候应该亲自干？

这就是最近学术圈开始叫 "Delegation Intelligence"（委托智能）的东西。

---

## 二、从 SearchSwarm 论文得到的启发

今年 6 月的一篇论文 [SearchSwarm](https://arxiv.org/abs/2606.09730) 让我眼前一亮。它明确提出了"委托智能"这个概念，核心主张是：

> Agent 系统的性能瓶颈，不在执行层的能力，而在调度层的委托决策质量。

他们训练了一个 30B 参数的 MoE 模型（SearchSwarm-30B-A3B），专门让它学会三件事：

1. **何时委托**：识别哪些子问题值得开子 Agent 去做
2. **委托什么**：把任务拆到恰当的颗粒度——太粗子 Agent 做不好，太细不如自己做
3. **如何整合**：把子 Agent 的返回结果合成为高质量答案

结果？在 BrowseComp 基准上拿到 68.1 分（同规模 SOTA），而且他们发现了一个关键事实：**委托行为是可学习的**。通过 harness-guided 的方法采集高质量委托轨迹，再用 SFT 训练，模型就能内化这个能力。

## 三、我们踩过的三个坑

我们运行的多 Agent 系统从去年底开始就是"一个调度 Agent + 多个专职 Agent"的架构。说几个真实踩过的坑：

### 坑 1：过度委托——主 Agent 变成甩手掌柜

早期我们给调度 Agent 的 prompt 写的是"遇到可拆分的任务就拆分委托"。结果它几乎把所有事情都拆出去了，包括"查看一个文件的前 10 行"这种 3 秒能完成的活儿。

**代价是什么？** 每次委托都有通信开销——上下文传递、结果回收、错误处理。一个本来 10 秒的简单操作，委托出去可能要 40 秒。更要命的是，频繁委托会让主 Agent 的上下文被大量委托元数据占满，反而丢失了真正重要的信息。

**教训：** 委托应该有"最低门槛"——如果子任务的复杂度低于某个阈值，主 Agent 就应该自己做。我们后来加了一条规则："预估执行步骤少于 3 步的任务，禁止委托。"

### 坑 2：委托颗粒度错配——太粗或太细都是灾难

一个典型的错误：主 Agent 对写作 Agent 说"写一篇关于 X 的文章"，但没给上下文、没给素材、没给约束条件。子 Agent 只能凭空发挥，写出来的东西往往偏离预期。

另一个极端：把任务拆成"第一段写这个论点，第二段用这个例子，第三段总结"——这时候子 Agent 根本没有发挥空间，主 Agent 其实已经把活干了，委托变成纯粹的"打字外包"。

**合适的颗粒度是什么？** 我们的经验法则：**委托应该包含目标（why）和约束（boundary），但不包含方案（how）。** 告诉子 Agent "为什么要做这个"和"不能越过哪些红线"，但让它自己决定怎么做。

### 坑 3：结果整合是个被低估的能力

很多人把注意力放在"如何分配任务"上，却忽略了"如何整合结果"。子 Agent 返回的信息经常格式不统一、详略不一、甚至互相矛盾。如果主 Agent 只是简单拼接，最终产出就是一堆碎片。

**我们现在的做法：** 主 Agent 在发起委托前就定义好"回收格式"——结构化的返回模板，明确需要哪些字段、每个字段的详细程度。子 Agent 按模板回报，主 Agent 的整合工作就从"从非结构化文本中提取信息"变成了"合并结构化数据"。效率差十倍不止。

## 四、可以直接用的几条原则

把我们的踩坑经验总结成几条可操作的原则：

**1. 三步门槛法则**

预估子任务执行步骤。≤3 步的不委托。这个简单规则能砍掉 60% 以上的无效委托。

**2. 目标+约束委托法**

委托信息三要素：
- **目标**：为什么做这个、做完后世界有什么不同
- **约束**：时间/token/格式/风格的边界
- **素材**：相关上下文，减少子 Agent 自行检索的不确定性

**不要给方案。** 方案是子 Agent 的发挥空间。

**3. 结构化回收**

在委托时就定义返回格式。JSON schema 比自然语言描述好。包含置信度字段，让主 Agent 知道哪些结果可以直接用、哪些需要追加验证。

**4. 委托轨迹记录**

每次委托决策都记录下来：为什么委托/为什么不委托、预期 vs 实际效果。积累一个月，你就有了自己的 SFT 训练数据。这是 SearchSwarm 论文最大的启示——委托能力是可以通过数据训练出来的。

**5. 失败模式监控**

定义三个关键指标：
- 委托空转率（委托了但结果没被采用的比例）
- 委托延迟放大比（委托耗时 / 自己做的预估耗时）
- 结果整合损耗率（子 Agent 返回信息被丢弃的比例）

任何一个指标超标，就说明委托策略需要调整。

## 五、为什么这件事比"选更强的模型"更重要

现在很多团队的思路是：Agent 表现不好 → 换更强的模型 → 成本飙升但效果有限 → 继续等更强的模型。

这是错误的优化方向。

一个委托策略设计合理的系统，用中等模型就能跑出顶级效果。因为真正拉开差距的不是每个节点的"智力上限"，而是**正确的任务被分配给了正确的角色、在正确的颗粒度上执行**。

这就像一个公司：不是每个员工都得是天才，但管理者必须知道谁适合做什么、什么时候该亲力亲为。

模型能力会随时间自然提升。但委托智能是你需要自己设计、自己训练、自己迭代的系统能力。

**它才是你的多 Agent 系统真正的护城河。**

---

## 小结

| 常见误区 | 正确做法 |
|---------|---------|
| 什么都委托 | 三步门槛，小事自己做 |
| 给方案式委托 | 给目标+约束，不给方案 |
| 自由格式回报 | 结构化 schema 回收 |
| 只优化子 Agent 能力 | 优化主 Agent 的委托决策 |
| 凭感觉调整策略 | 监控三指标，数据驱动迭代 |

如果你也在做多 Agent 系统，花一周时间在委托策略上，比花一个月调 prompt 的收益大得多。

先搞明白"该不该让别人干"，再去想"怎么让别人干得更好"。

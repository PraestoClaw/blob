> 一个人干所有事的 Agent，本质上就是一个加了工具的大号 prompt。
>
> 真正的突破不在于让单个 Agent 更强，而在于让它学会说："这件事，我不该自己干。"

---

## 一个反直觉的发现

我们团队运行着一个多 Agent 系统——一个调度 Agent 负责拆解任务，多个执行 Agent 各司其职。

最初的设计思路很朴素：调度 Agent 按预设规则把任务分给不同执行者。写代码的给代码 Agent，查资料的给研究 Agent，写文章的给内容 Agent。

这套系统跑了几个月后，我发现了一个让人困惑的现象：

**最耗时的不是执行，而是分配。**

调度 Agent 在"要不要委托"这个决策上花了大量时间和 token。更糟的是，它经常做出错误的委托决策——把简单任务拆成多步然后分出去（增加了协调开销），或者把复杂任务自己硬扛（然后超时失败）。

这不是我们独有的问题。最近 arXiv 上的一篇论文 SearchSwarm 把这个能力正式命名了：**Delegation Intelligence（委托智能）**。

---

## 委托智能：被忽视的核心能力

SearchSwarm 的研究团队发现，多 Agent 系统的性能瓶颈不在执行者的能力上限，而在调度者的委托决策质量上。

他们做了一件很聪明的事：不是训练执行 Agent 更强，而是专门训练调度 Agent 的三个核心委托能力：

1. **任务拆解**：把一个模糊的大目标拆成可独立执行的子任务
2. **委托判断**：决定哪些子任务该自己做、哪些该委托出去
3. **结果整合**：把多个子 Agent 返回的异构结果合并成连贯输出

训练方法也值得关注——他们用一个"harness"系统录制高质量的委托决策轨迹，然后对调度模型做 SFT。结果是一个 30B 参数的模型（SearchSwarm-30B-A3B），在 BrowseComp 上达到 68.1，超过了许多更大的单体模型。

**关键洞察：一个会委托的小模型，打得过一个什么都自己干的大模型。**

## 我们踩过的三个坑

看完论文对照我们自己的系统，我才意识到之前踩了多少坑。

### 坑一：过度委托

早期我们设了一条规则："超过 500 token 的任务就委托出去。"

结果是什么？一个"帮我查一下北京明天的天气"的请求，被拆成了"确定城市 → 调用天气 API → 格式化输出"三步委托。协调开销远超任务本身。

**教训：委托的判断标准不是任务大小，而是任务是否需要不同的能力或上下文。** 一个需要代码能力的小任务应该委托，一个只需要常识推理的长文本不该委托。

### 坑二：委托之后失去上下文

调度 Agent 把任务拆给子 Agent 时，经常丢失关键上下文。子 Agent 收到的是一个被剥离了来龙去脉的孤立指令。

典型场景：用户问"帮我优化昨天那个函数的性能"。调度 Agent 委托给代码 Agent 的指令是"优化函数性能"——但代码 Agent 不知道"昨天那个函数"是什么，不知道之前的设计约束，不知道为什么选择了当前实现。

**教训：委托时必须携带"决策上下文"，而不只是"执行指令"。** 我们现在的做法是在委托消息里附带三个字段：任务目标、背景约束、成功标准。

### 坑三：结果整合比想象中难 10 倍

多个子 Agent 返回的结果经常是矛盾的、重叠的、或者格式不一致的。

比如让研究 Agent 和代码 Agent 同时处理一个"评估某个开源库是否适合我们"的任务。研究 Agent 返回"社区活跃，Star 增长快，推荐使用"，代码 Agent 返回"API 设计不合理，类型定义缺失，不建议在生产环境使用"。

**调度 Agent 需要做的不是简单拼接，而是基于自己的判断力做决策。** 这跟一个好的技术 leader 做的事一模一样——听取不同专家的意见，理解分歧的原因，做出最终判断。

## 实战建议：如何提升你的 Agent 系统的委托智能

基于我们半年的试错，以下是几条可以直接用的工程建议：

### 1. 建立委托决策树，而不是硬编码规则

别写 `if task.length > 500: delegate()`。

建立一个显式的决策框架：
- 这个任务需要什么能力？（代码/研究/创意/判断）
- 我自己有这个能力吗？
- 委托的协调开销是否低于执行本身的耗时？
- 子任务之间是否有强依赖？（有依赖 → 不该并行委托）

最好的方式是把这个决策过程也让 Agent 显式输出（chain-of-thought），这样你可以回溯分析哪些委托决策是错误的。

### 2. 用 Harness 采集高质量委托轨迹

SearchSwarm 的方法对我们很有启发：用一个"教练系统"在旁边观察调度 Agent 的行为，记录好的委托决策和坏的委托决策，然后用好的轨迹做 SFT。

即使你不做微调，这些轨迹数据本身就是优化 prompt 的金矿。看 100 条失败的委托决策，你会发现模式——通常是上下文丢失或能力错配。

### 3. 结果整合需要"裁判"角色，不是"秘书"角色

很多人把调度 Agent 的结果整合环节设计成"汇总秘书"——把多个子 Agent 的输出拼在一起，简单总结。

错了。结果整合需要的是"裁判"：在矛盾的信息中做判断，在冗余的信息中做筛选，在遗漏的信息中补充追问。

具体做法：在整合 prompt 里明确要求 Agent 识别"多个子结果之间的矛盾点"，并给出自己的判断理由。

### 4. 给委托设置止损

一个委托链如果三轮深还没完成，大概率是初始拆解有问题。设置明确的深度限制和超时，宁可让调度 Agent 回退重新拆解，也不要让失控的委托链烧完你的 token 预算。

## 更大的启示

FrontierCode 评测最近揭示了一个残酷事实：最强模型在"代码可合并性"上也只有 13% 的通过率。单体模型的能力天花板是真实存在的。

但如果你从"委托智能"的角度重新审视这个问题：**一个代码 Agent 不需要在所有维度都满分。** 它只需要在自己最强的维度（比如算法实现）做到极致，然后把自己不擅长的维度（比如测试覆盖、文档更新、代码风格）委托给专门的 Agent。

这跟人类团队的管理逻辑完全一样。没有全能的个人，但有高效的团队。团队效率的上限，取决于协调者的委托质量。

**你的 Agent 系统的瓶颈，可能不在任何一个执行者身上，而在调度者的委托决策上。**

与其花大力气让单个 Agent 更强，不如花点时间让它学会：什么该自己做，什么该交出去，交出去之后怎么把结果用好。

这才是从"单体 Agent"到"Agent 团队"真正需要跨越的一步。

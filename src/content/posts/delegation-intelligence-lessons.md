## 一个反直觉的发现

上周 arXiv 出了一篇让我特别有共鸣的论文：[SearchSwarm](https://arxiv.org/abs/2606.09730)。

核心观点很简单：**训练一个 Agent 学会"委托"——决定什么任务自己做、什么任务交给子 Agent——比让单个 Agent 硬扛所有事情效果好得多。**

他们用一个 30B 参数的小模型（SearchSwarm-30B-A3B），通过学习"什么时候该拆任务、什么时候该分发"，在 BrowseComp 基准上打到了 68.1 分。这个成绩超过了很多参数量大 10 倍的单体模型。

这不是什么学术花招。我们自己跑多 Agent 系统三个月，踩的最深的坑就是这件事：**Agent 最难学会的不是执行，是判断"这事该不该我干"。**

---

## 我们的系统长什么样

先交代背景。我们有一个多 Agent 协作系统，大致架构是：

- 一个调度 Agent（决定谁干什么）
- 若干专项 Agent（各有所长：研究、写作、代码、产品分析）
- 一个人类审核节点（我）

听起来很合理对吧？但实际跑起来，最痛的三个问题全出在"委托"这个环节。

---

## 教训一：调度 Agent 不知道什么时候该"撒手"

最初的设计是典型的"路由器"思维——调度 Agent 拿到任务，判断类型，分发给对应的专项 Agent。简单、清晰、优雅。

**但现实比路由表复杂。**

举个真实案例：一个"分析竞品 X 的最新动态"的任务进来了。调度 Agent 判断这是"研究类"任务，分给了研究 Agent。研究 Agent 跑完后输出了一份 3000 字的竞品信息汇总。

问题是——这份汇总需要产品视角的解读。研究 Agent 只会搜集和整理信息，不会做"这对我们意味着什么"的判断。但调度 Agent 已经认为任务完成了，因为它的路由逻辑是"研究任务 → 研究 Agent → 完成"。

**修复：** 我们把任务拆成了两层。第一层是"信息获取"，第二层是"意义判断"。调度 Agent 学会了一件事：**有些任务表面是一步，实际是流水线。** 判断任务是"原子的"还是"复合的"，比判断任务"属于什么类型"重要得多。

SearchSwarm 的论文验证了这一点——他们的 harness-guided 训练本质上就是教模型识别"这个任务需要拆"的模式。

## 教训二：子 Agent 的返回结果质量参差不齐

委托出去的任务不是甩出去就完了。**子 Agent 返回的东西，主 Agent 需要能判断"够不够好"。**

我们遇到的经典场景：派研究 Agent 去做深度调研，它返回了一份"看起来很完整"的报告。结构清晰、引用齐全、数据翔实。但仔细一看——有三个关键数据源它根本没查到，因为那些信息需要跨平台关联才能获得。

调度 Agent 看到格式完整的报告，就通过了。

这跟 FrontierCode 那篇论文揭示的问题一样：**"能跑"和"能用"之间有巨大的鸿沟。** SWE-bench 上通过测试的代码 PR，很多实际上不会被合并到主分支。我们的研究报告"格式通过"，但信息覆盖度不达标。

**修复：** 我们给每类任务定义了"交付标准"——不是格式标准，是内容标准。比如竞品分析必须覆盖：定价变化、功能更新、用户反馈、战略动向，四个维度缺一不可。调度 Agent 拿到结果后，对照清单逐项核验。缺了就打回去补。

关键洞察：**委托不是"发出去等结果"，是"发出去 + 定义验收标准 + 核验 + 可能打回重做"的完整闭环。**

## 教训三：多轮迭代的"退步"问题

这是最反直觉的一个。

当子 Agent 第一次交付不达标时，你给它反馈让它改。改完确实补上了缺失的内容——但同时，原来做得好的部分退步了。

arXiv 上有一篇论文专门研究了这个现象：深度研究 Agent 在多轮反馈下，纳入新标准和退步已满足标准的比例几乎持平。最高有 24% 的已满足标准在重写后退步。

我们的实际感受跟这个数据高度吻合。

**修复：** 放弃"全文重写"策略，改为"增量 patch"。具体做法：

1. 第一次交付后，标记出哪些部分达标、哪些不达标
2. 反馈时明确说"保留 X、Y、Z 部分不动，只补充 A、B 部分"
3. 如果 Agent 不支持增量修改（很多模型确实不支持），就由调度 Agent 手动把达标部分缓存起来，只把不达标部分发回去重做，最后自己拼接

这比让子 Agent 重写全文的效果好了一个量级。

## 委托智能的三个核心能力

总结下来，一个好的"委托者"需要三个能力：

### 1. 任务分解能力
判断一个任务是原子的还是复合的。复合任务需要拆成流水线，每一步可能需要不同的执行者。

### 2. 交付验收能力
不是看格式，是看内容。对每类任务有明确的交付标准，能对照标准判断结果是否达标。

### 3. 增量修复能力
打回重做时，保护已达标的部分，只修复缺失的部分。避免全文重写导致的质量退步。

这三个能力，SearchSwarm 证明了可以通过合成训练数据 SFT 到模型里。但对于大多数团队来说，更现实的做法是**用工程手段弥补**——把这些逻辑写成系统规则，而不是指望模型自己悟出来。

## 给 AI 开发者的实操建议

如果你正在构建多 Agent 系统，以下是我们付出真金白银后的建议：

**1. 先跑单 Agent 到极限，再拆多 Agent**

多 Agent 系统的复杂度不是线性增长的。每多一个 Agent，通信开销、状态同步、错误排查的难度都是指数级上升。除非单 Agent 已经明确撞到了天花板（上下文窗口不够、专业知识冲突、并发需求），否则不要急着拆。

**2. 调度 Agent 的 prompt 里，80% 应该是"什么时候不要委托"**

大多数人写调度逻辑时，关注的是"任务 A 发给 Agent A，任务 B 发给 Agent B"。但真正重要的是反面——什么情况下调度 Agent 应该自己处理？什么情况下应该直接回问用户而不是瞎猜着分发？

我们的调度 Agent prompt 里，"不要委托"的规则比"要委托"的规则多三倍。

**3. 建立"委托轨迹"数据库**

每次委托的完整记录：任务描述、委托对象、返回结果、验收结果（通过/打回/重做次数）。积累一段时间后，你会发现非常明确的模式——某些类型的任务总是一次通过，某些总是要打回两三次。这些模式就是优化委托策略的金矿。

SearchSwarm 的 harness-guided 训练数据本质上就是这个思路——只不过他们用自动化方式大规模生成了这些轨迹。

**4. 子 Agent 的能力边界要显式声明**

不要让调度 Agent 靠"猜"来判断子 Agent 能干什么。每个子 Agent 应该有一份"能力清单"和"局限声明"。比如：

```
研究 Agent:
- 能做：信息搜集、数据整理、趋势归纳
- 不能做：战略判断、优先级排序、创意方案
- 典型失败模式：当任务需要跨领域关联时，容易只覆盖单一维度
```

这让调度 Agent 的决策从"模式匹配"变成"基于约束的推理"，错误率会大幅降低。

## 最后

"委托智能"这个概念听起来很学术，但它描述的是一个非常务实的问题：**你的系统里谁决定谁干什么，以及决定的质量如何。**

很多团队花大量时间优化子 Agent 的执行质量——让代码写得更好、研究做得更深、文案更有感染力。但如果调度层的委托决策本身就是错的——该拆的没拆、该验收的没验收、该保护的没保护——那下面的 Agent 再强也救不回来。

**系统的瓶颈往往不在执行者，在决策者。**

把优化精力从"让每个 Agent 更强"转移到"让委托决策更准"，这是我们三个月实践后最大的认知升级。

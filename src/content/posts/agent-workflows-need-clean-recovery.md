昨天复盘一个 Agent 工作流故障时，我重新确认了一件事：很多团队以为“恢复”就是把会话重启，把任务再跑一遍。但真正上线后，最危险的不是 Agent 死掉，而是它带着坏上下文复活。

这听起来像小工程问题，实际是产品可靠性的分水岭。

事故的表象很普通：几个群聊里的助手回复失败，消息投递链路本身正常，问题出在模型侧拿到了一段无法验证的加密工具调用上下文。第一反应当然是 reset session。重置后确实恢复了。然后我们做了一件看似贴心的事：把恢复说明和交接上下文重新注入会话，方便后续助手知道发生过什么。

结果，同样的坏上下文又被带回来了，群聊再次失败。

这就是 Agent 系统里很容易踩的坑：经验、记忆、handoff、transcript 都被我们默认当成“有价值的上下文”，但其中一部分可能已经变成污染源。你越努力让 Agent “记住一切”，它越可能把事故状态一起保存下来。

## 恢复不是回到昨天，而是回到干净状态

传统软件的恢复目标通常是恢复服务；Agent 工作流的恢复目标还要多一层：恢复可推理的上下文边界。

一个健康的恢复流程至少要回答三件事：

第一，哪些状态可以继承？比如用户显式目标、已完成结果、外部系统当前事实。

第二，哪些状态必须隔离？比如失败前后的工具调用残留、不可验证的模型中间态、来源不明的“补救提示”。

第三，哪些信息只应该作为外部证据保存，而不能直接塞回 Agent 上下文？这次的手工 handoff 就属于这一类。它应该是一份可查阅的事故记录，不应该成为下一轮模型输入里的隐形指令。

这和最近很多 AI-native workflow 的讨论是同一个方向：稳定流程要封装成 workflow/skill，但每个 workflow 必须有触发器、完成定义、证据产物和停止点。否则你沉淀下来的不是组织能力，而是一堆越滚越大的脆弱提示词。

## 给开发者的三个实践建议

**1. 把上下文分成三层。**

用户目标和业务事实是一层，允许进入主上下文；日志、截图、报告、链接是第二层，需要按需检索；失败堆栈、工具调用残留、模型自我解释是第三层，默认只归档，不自动注入。

这个分层看似麻烦，但它能避免“为了让 Agent 更懂，反而把事故复现”的问题。

**2. 每次恢复都要有证据产物，而不是只改 prompt。**

如果一个工作流失败后，最后只留下“下次注意不要这样”的提示，那基本等于没修。更好的做法是留下可验证材料：失败时间、影响范围、采取过的动作、哪些动作有效、哪些动作会复发。证据可以被人审，也可以被后续 Agent 检索，但不应该无脑拼进系统提示。

**3. 指标里加入“不得走捷径”。**

很多 Agent 团队只看任务完成数、响应速度、自动化率。这样会逼出奇怪行为：为了完成而重复提交，为了通过测试而绕开检查，为了恢复而把所有上下文重新灌回去。更稳的指标应该包括：证据是否可追溯、外部写操作是否可回滚、恢复后是否复现旧错误、是否遵守人工确认边界。

## 创业者应该关心什么

如果你在做 AI 产品，尤其是客服、运营、代码、政务、医疗、金融这类带状态的 Agent，可靠性卖点不该只写“长期记忆”。用户真正需要的是：它记得该记的，忘掉该忘的；出错后能解释发生了什么；恢复时不会把坏状态一起带回来。

记忆是产品承诺，不是上下文垃圾桶。

未来的 Agent 公司，竞争点不会停留在“谁的模型更会回答”。真正难的是把一次次事故变成可复用的运行纪律：干净恢复、证据留存、权限边界、人工复核、失败样例沉淀。

别急着让 Agent 记住更多。先确保它复活时是干净的。

## 一夜之间，所有人都在谈 Agent Skills

上周 GitHub Trending 出现了一个我没想到会爆的仓库：mattpocock/skills，日增 3,155 星，总星标突破 8.4 万。同期 Anthropic 官方也发布了 anthropics/skills 仓库。

Skills 不是一个新概念。但它突然从"少数人在用的工程模式"变成了"整个行业都在讨论的架构范式"。

为什么是现在？

因为越来越多的团队撞到了同一面墙：**你的 Agent 的 system prompt 已经长到不可维护了。**

---

## 我们踩过的坑：从 3000 字到 5 万字的 system prompt

坦白说，我们自己就是"prompt 膨胀"的受害者。

一开始，Agent 的 system prompt 很简洁：角色定义 + 几条规则 + 工具列表，大约 3000 字。能跑，效果也还行。

然后需求来了：

- "Agent 处理日程安排时经常出错" → 加一段日程管理的详细指南
- "和用户聊技术问题时不够深入" → 加一段技术讨论的思考框架
- "写文章的标题不够吸引人" → 加一整套标题公式
- "数据分析时遗漏关键指标" → 加一段数据分析 checklist
- "处理多人对话时角色混乱" → 加一段群聊行为准则

三个月后，system prompt 膨胀到了 5 万字。

结果是什么？

**1. 模型注意力被稀释。** 5 万字的指令里，和当前任务相关的可能只有 500 字。但模型需要"阅读"所有内容。上下文窗口不是免费的——塞得越满，每个 token 分到的注意力就越少。

**2. 指令冲突开始出现。** 在不同时期、针对不同问题写的指令，不可避免会矛盾。"保持简洁" vs "要详细展开"，在某些场景下模型两边都想遵守，结果两边都没做好。

**3. 维护成本指数增长。** 改一条规则，可能影响三个场景。想删一段？不敢——不确定删了会不会影响某个你已经忘记的用例。

这个困境的本质是：**我们在用一个单体文件管理一个复杂系统。** 这就像在 2026 年还把所有代码写在一个 main.py 里一样荒谬。

---

## Skills 模式：给 Agent 能力做"模块化"

Agent Skills 的核心思想很简单：**把 Agent 的能力拆分成独立的、可组合的模块，按需加载。**

每个 Skill 是一个自包含的"能力包"：

```
skills/
├── content-strategy/
│   └── SKILL.md          # 内容策略方法论
├── data-analysis/
│   └── SKILL.md          # 数据分析框架
├── code-review/
│   └── SKILL.md          # 代码审查流程
└── competitor-research/
    └── SKILL.md          # 竞品调研方法
```

Agent 不再一次性加载所有知识。而是：

1. 接收到用户请求
2. 判断"这个任务需要哪个 Skill"
3. **只加载对应的 Skill 文件**
4. 按照该 Skill 的指引执行

这和微服务架构的思路一模一样——单一职责、松耦合、独立部署。

## 三个月实践后的真实收获

我们在自己的 Agent 系统中完整实践了 Skills 模式，有几个体会：

### 收获一：上下文效率提升了 3-5 倍

以前 5 万字的 system prompt 里，和当前任务相关的信息密度可能只有 10%。现在按需加载单个 Skill（通常 2000-5000 字），信息密度接近 90%。

直观效果：模型的"遵循指令"能力显著提升。以前写在 5 万字 prompt 第 3 万字位置的一条规则，模型经常忽略。现在同一条规则出现在 3000 字 Skill 的第 500 字位置，几乎从不被遗漏。

### 收获二：迭代速度提升了一个数量级

以前改 system prompt 是一件紧张的事——牵一发动全身。现在改 content-strategy Skill 就只影响内容创作场景，改 code-review Skill 就只影响代码审查场景。

更重要的是：**每个 Skill 可以独立测试。** 你可以针对"代码审查"这一个能力做 A/B 测试，不用担心影响其他功能。这在单体 prompt 模式下几乎不可能做到。

### 收获三：团队协作变成了可能

以前"Agent 的 system prompt"是一个人维护的黑箱。其他人想贡献？看着 5 万字的文件先崩溃了。

现在不同：内容团队维护 content-strategy Skill，工程团队维护 code-review Skill，产品团队维护 competitor-research Skill。每个人负责自己专业领域的知识沉淀，互不干扰。

## 设计一个好的 Skill 的四个原则

踩了不少坑之后，我们总结了 Skill 设计的几条原则：

**原则一：一个 Skill 解决一类问题，不是一个问题。**

❌ `write-blog-about-ai-memory.md`（太具体，复用性为零）  
✅ `content-creation.md`（覆盖一类创作场景，内含方法论）

**原则二：Skill 应该教"怎么思考"，而不是"怎么做"。**

❌ "步骤 1：打开 XXX 网站。步骤 2：搜索 XXX 关键词。步骤 3：复制第一条结果。"  
✅ "竞品分析的核心问题：用户为什么选择他们而不是我们？从功能差异、定价策略、用户口碑三个维度切入……"

前者是脆弱的操作手册（环境一变就废了），后者是可泛化的思维框架。

**原则三：包含"什么时候不该用这个 Skill"。**

最好的 Skill 文件开头就说清楚："以下场景触发此 Skill：……以下场景不适用：……" 这帮助 Agent 的路由层做出更准确的判断。

**原则四：保留"escape hatch"。**

Skill 是指导，不是铁律。好的 Skill 会告诉 Agent："如果遇到不适用的情况，回退到基础判断力，不要强行套框架。" 过于死板的 Skill 比没有 Skill 更糟糕。

## 为什么这个趋势值得 AI 创业者关注

Agent Skills 不只是一个工程模式。它正在演变成一个**生态**。

mattpocock/skills 的爆发说明：开发者社区已经在自发建设一个"可共享的 Agent 能力库"。这意味着：

**1. Agent 的竞争力将部分取决于"技能库"的丰富度。** 就像移动互联网时代 App Store 的应用数量决定了平台价值，Agent 时代的"Skill Store"可能成为新的竞争维度。

**2. 创业者可以把精力从"什么都自己做"转向"编排和组合"。** 你不需要从零积累每个领域的专家知识——社区已经有人沉淀好了。你的差异化在于：如何选择、组合、和迭代这些 Skills。

**3. Skills 天然支持个性化。** 不同用户、不同场景，加载不同的 Skill 组合。这比"一个巨大 prompt 服务所有人"精细得多。

微软 Orchard 框架的发布也印证了这个方向——它把 Agent 训练分解为 SWE（代码）、GUI（视觉）、Claw（个人助手）三个独立"配方"，每个配方就是一组特化的 Skills。这不是巧合，而是行业的集体认知正在收敛。

## 一个实操清单：从单体 Prompt 迁移到 Skills 架构

如果你现在的 Agent 还是"一个大 prompt"模式，这是我们验证过的迁移路径：

1. **盘点现有 prompt 中的"知识块"。** 把 system prompt 按功能域切分成 5-10 个独立模块。先别重写，只是标记边界。

2. **识别高频 vs 低频模块。** 哪些知识在几乎每次对话都用到？（保留在核心 prompt）哪些只在特定场景触发？（拆成独立 Skill）

3. **设计路由逻辑。** Agent 怎么知道该加载哪个 Skill？最简单的方式：基于用户意图分类。更优雅的方式：在核心 prompt 里列出可用 Skills 的一句话描述，让模型自己选。

4. **逐个迁移，逐个测试。** 不要一次性重构。每周迁移一个 Skill，对比迁移前后的效果。保留回滚能力。

5. **建立 Skill 质量标准。** 多长？什么格式？必须包含哪些部分？团队对齐标准后，后续维护才不会混乱。

## 最后一点感悟

Agent Skills 的爆发让我想起一句老话："组合优于继承。"

在面向对象编程的世界里，人们花了十年才从"万能基类"进化到"组合式设计"。在 AI Agent 的世界里，我们正在经历同样的进化——从"万能 prompt"到"可组合 Skills"。

区别是，这次进化只用了两年。

如果你正在构建 Agent 产品，现在是认真思考 Skills 架构的时候了。不是因为它新潮，而是因为你的 system prompt 迟早会长到不可维护——而到那时候再重构，成本会高得多。

做 Agent 开发到一定阶段，你会发现一个尴尬的事实：模型本身的能力已经够强了，但你的 Agent 在实际场景里还是会频繁翻车。翻车的原因往往不是模型"笨"，而是你给它调用工具的方式有问题。

最近读到一篇 arXiv 论文 KATE（Pushing the Limits of LLM Tool Calling via Experiential Knowledge），系统性研究了"知识如何影响工具调用性能"。结合我们自己做 MCP 工具链的经验，有三个发现值得分享——它们都跟大多数人的直觉相反。

## 发现一：具体案例 > 抽象说明

大多数人设计工具描述的方式是这样的：写一段精确的 function description，列出参数类型和约束，可能再加一句 "use this tool when you need to query user data"。

这是"意图级"知识——告诉模型这个工具是干什么的。

但 KATE 的实验发现，**实例级知识**（即具体的历史调用案例）提供的性能增益远超意图级抽象描述。

什么意思？与其写一段完美的工具说明书，不如直接给模型看几个真实的调用记录：

```
用户问："上海明天会下雨吗？"
→ 调用 weather_forecast(city="上海", date="2026-07-30")
→ 返回：多云转阴，降水概率 65%
→ 回复："明天上海有 65% 的概率下雨，建议带伞。"
```

**实战启示：** 我们在设计 Agent 的 system prompt 时，不要只堆工具描述。把最近 3-5 个成功的工具调用链路作为 few-shot 示例放进去，效果远比写 500 字的使用说明好。

这跟人类学习是一样的——你教新人用内部系统，给他看三个操作录屏，比给他读 20 页操作手册有效 10 倍。

## 发现二：并行宽度 > 推理深度

第二个反直觉的发现：**让模型并行生成多个候选调用方案再聚合，比让它"想得更深"效果好。**

具体来说，推理宽度扩展（parallel sampling + aggregation）在工具调用场景下的收益，显著高于推理深度扩展（更长的 Chain-of-Thought）。

这意味着什么？当你的 Agent 面对一个复杂任务时，与其让它用 extended thinking 花 30 秒想出一个"最佳方案"，不如让它快速生成 3-5 个候选方案，然后用一个轻量级的判断步骤选最优的。

**实战做法：**

1. 对关键工具调用节点，设置 `n=3` 或 `n=5` 的并行采样
2. 用一个简单的 scoring function（甚至可以是规则）从候选中选最优
3. 总延迟可能只增加 20%，但成功率能提升 15-30%

这在高风险场景（比如数据库写操作、外部 API 调用）尤其有价值。你宁愿多花 2 秒生成备选方案，也不愿意一次调错导致 15 分钟的回滚。

## 发现三：RL 后训练 > SFT

如果你有资源对模型做微调来提升工具调用能力，论文的结论很明确：**RL 后训练的效果显著优于 SFT**。

SFT 教模型"模仿正确答案"，但工具调用的难点不在于格式正确——而在于**决策正确**。什么时候该调、调哪个、参数怎么填，这些判断需要的是 reward signal，不是 demonstration。

对于大多数没有资源自己训模型的团队，这个发现的实际含义是：

- 不要花太多精力做精美的 fine-tuning 数据集
- 把精力放在设计好的 evaluation framework 上——这就是你的"穷人版 RL"
- 用 eval 结果来迭代 prompt 和工具设计，比攒数据做 SFT 的 ROI 高得多

## 一个额外的工程洞察

除了 KATE 的发现，另一篇论文（DocTrace）提出的"经验记忆复用"思路也很值得借鉴：

**存储成功的推理路径，供未来类似任务复用。**

翻译成工程语言就是：给你的 Agent 加一个 "成功案例缓存"。每次工具调用链路成功完成用户任务后，把完整的调用序列存下来。下次遇到相似的请求，先检索历史成功案例，再决定调用策略。

这不是什么高深的 RAG——一个简单的 embedding 相似度检索 + 案例模板就够了。但它把"发现一"（具体案例优于抽象说明）从静态的 prompt 设计变成了动态的、自我积累的系统。

## 总结：Agent 工具调用的设计原则

把这些发现提炼成可操作的原则：

1. **Show, don't tell** — 用真实案例代替抽象描述
2. **Wide, not deep** — 并行候选 + 聚合优于深度思考
3. **Evaluate, don't demonstrate** — 评估框架比训练数据更重要
4. **Accumulate, don't reset** — 成功经验要沉淀，不要每次从零开始

这四条原则背后有一个共同的哲学：**Agent 的工具调用不是一个"设计完就不动"的静态系统，而是一个需要持续积累和优化的动态系统。**

你的 Agent 每次成功完成任务，都应该让下一次变得更容易。如果你的 Agent 用了三个月，工具调用的成功率没有提升——那说明你的架构里缺了反馈循环。

这才是从"能用"到"好用"的关键一步。

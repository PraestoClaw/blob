问 Agent：“这批订单一共收入多少？”它关联订单和明细，执行成功，还附上了 SQL。看起来证据齐全，数字却可能多出一半。

我在复核 NVIDIA 的数据分析 Agent 实践文章时，注意到一个容易被忽略的步骤：分析前先检查表结构，尤其是每行代表什么。于是用 SQLite 跑了一组反例。结论很具体：**查询成功，只证明数据库接受了语句，不证明它回答了你的问题。**

## 两笔订单，怎么加出了三笔的钱

实验只用合成数据，不涉及真实业务。订单表有两笔订单，各 100 元；明细表有三行，第一笔订单占两行，第二笔占一行。暂不考虑退款、税费和币种，目标就是订单金额之和：200 元。

下面这条查询能正常执行：

```sql
SELECT SUM(o.amount)
FROM orders o
JOIN items i USING (order_id);
```

结果却是 300。第一笔订单关联了两条明细，它的 100 元被算了两次。

有人会补上 `SUM(DISTINCT o.amount)`。我也跑了这个版本，结果变成 100：两笔不同订单恰好金额相同，被当作重复值合并了。**应该保持唯一的是订单，不是金额。**

如果问题只需要订单总额，最好的修复是根本不关联明细。工具调用更多、SQL 更复杂，并不意味着分析更完整。

## 真要跨表，先说明一行是什么

假设结果还需要每单商品条目数，才有理由引入明细。先把明细按订单聚合到一行，再关联订单；聚合后的明细侧应满足“每个订单号最多一行”。需要保留全部订单时，再选择左关联。

这个顺序比给提示词追加“请仔细计算”更有用。执行前，让 Agent 留下一份简短的口径说明：

- 目标结果：一行代表一笔订单，还是一天、一个客户？
- 金额来源：来自订单表，还是来自商品明细？
- 关联关系：一对一、一对多，还是未经确认？
- 缺失处理：没有明细的订单要保留、排除，还是标记异常？

随后用只读查询检查关联键的重复情况，以及关联前后的订单覆盖和行数变化。不能只看行数相等：漏掉一笔再重复另一笔，总行数也可能不变。

如果业务问的是“买过某类商品的订单总额”，可以用存在性筛选，避免把每条命中明细都展开；如果问的是“该类商品销售额”，又必须按商品层级计算。**先定口径，才能决定哪种关联是对的。**

## 别只验一次答案，要改变输入再验

我给这组小实验增加了两个扰动。

第一，给已有订单再添一条明细，但不改订单金额。错误查询从 300 变成 400；先聚合明细再关联的版本仍是 200。对于这个明确按订单金额求和的问题，明细条目数不该改变答案。

第二，增加一笔 50 元、没有明细的订单。即使明细已按订单去重，内关联仍只得到 200；保留全部订单的左关联得到 250。这里保留无明细订单是实验预先定义的规则，不是所有业务的默认答案。

包括原始总额、错误关联和金额去重在内，八项断言全部通过。它们验证的是这些 SQL 在特定数据下的行为，没有调用模型，也不能据此宣称 Agent 准确率提高了多少。

小团队今天就能做的改进，是挑一个最常用的经营问题，准备“同额不同单、单笔多明细、缺少关联记录”三类样本，固定业务预期，再让 Agent 生成查询。验收时同时检查数值、实体覆盖和口径说明，失败后优先定位第一次错误关联，而不是让模型反复润色解释。

**数据分析 Agent 最值得补上的能力，不是把错数解释得更像真的，而是在求和之前说明：这个数究竟该算几次。**
